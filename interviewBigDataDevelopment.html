01 Hadoop 基础

Q
介绍一下大数据生态圈的整体架构？🔥 高频

从数据链路看，大数据生态可以分成五层：

  • 数据采集层：Flume（日志）、Sqoop/DataX（关系库）、Canal（Binlog 实时）、Kafka（消息缓冲）
  • 存储层：HDFS（分布式文件系统）、HBase（NoSQL 列式）、Kafka（消息存储）、Redis（缓存）
  • 计算层：MapReduce（批处理）、Spark（内存计算）、Flink（流式计算）、Hive（SQL 化）
  • 调度层：YARN（资源调度）、Oozie/Airflow/DolphinScheduler（任务调度）
  • 服务层：数据仓库（Hive 数仓）、即席查询（Presto/Impala/Doris）、OLAP（ClickHouse/Doris）
采存储计算调服务，一条链路五层走；采 Flume 存 HDFS、算 Spark 调 YARN、服务上层数仓出
Q
Hadoop 三大核心组件是什么？各自负责什么？🔥 高频
  • HDFS：分布式存储系统，主从架构（NameNode + DataNode），把大文件切块冗余存储
  • MapReduce：分布式计算框架，分而治之：Map 阶段并行处理，Reduce 阶段汇总
  • YARN：资源调度与任务管理平台，负责给计算任务分配 CPU/内存资源

一句话：存储（HDFS）+ 计算（MR）+ 调度（YARN）三件套组成 Hadoop 大数据底座。

HDFS 存、MR 算、YARN 管资源；存算分离各干各的活
Q
Hadoop 小文件问题是怎么产生的？有什么危害和解决办法？🔥 高频
  • 产生原因：业务本身大量小文件、Spark/Hive 分区过多、Flume 频繁落地、MR 输出 reduce 数量多且每个输出小
  • 危害：① NameNode 内存被打爆——每个文件都要一条元数据（约 150 字节）；② 任务启动 Map 过多，调度开销大；③ 磁盘寻道次数多，读写效率低
  • 解决思路：源头合并（写入时合并）、运行期合并（CombineTextInputFormat / Hive merge 参数）、存储层小文件治理（定期合并成 ORC/Parquet 大文件）
小文件三宗罪：元数据占 NN 内存、Map 数爆炸、寻道慢；治理就一个字「合」
Q
数据倾斜的成因和通用解决办法？🔥 高频
  • 成因：key 分布不均，如热点 key（某大品牌商品）、null 值聚集、join 的关联键大量重复
  • 症状：个别 Task 运行极慢、OOM、整个 job 被一个任务拖死（木桶效应）
  • 通用解法：① null 值打散——加随机前缀再过滤；② 热点 key 加盐——随机前缀摊到多 reduce；③ 两阶段聚合（局部聚合 + 全局聚合）；④ map 端 join 小表广播，避免 reduce join；⑤ 增大 reduce 并行度
倾斜三招：null 打散、热点加盐、两段聚合；小表广播走 map 端 join
Q
Hadoop 1.x / 2.x / 3.x 有什么区别？
  • 1.x：MRv1 架构，JobTracker 既管资源又管任务，单点故障，最多支持约 4000 节点
  • 2.x：引入 YARN 资源调度与 MR 解耦，支持 NameNode HA（Active/Standby + JournalNode）
  • 3.x：支持多 NameNode（Federation 完善）、纠删码（节省 50% 存储）、YARN 支持 GPU 等异构资源、MR 优化（Task 本地运行等）
1.x 单点扛不住，2.x YARN+HA，3.x 纠删码多 NN；版本越新越抗造

02 HDFS 深入

Q
HDFS 写数据的完整流程？🔥 高频
  • ① 客户端向 NameNode 发起写请求，NN 检查权限与空间，返回可写 DataNode 列表
  • ② 客户端按 128MB 切块，逐块向第一个 DataNode 传输数据
  • ③ 第一个 DN 收到后流水线复制给第二个、第三个 DN（副本数默认 3）
  • ④ 每块写完后，DN 逐级ack 确认回传客户端；全部块写完后关闭输出流
  • ⑤ 客户端通知 NN 提交完成，NN 更新元数据
问 NN 要名单 → 切块流水线写 → 逐级 ack → 提交元数据；写流程靠管道接力，边写边确认
Q
HDFS 读数据的流程？🔥 高频
  • ① 客户端向 NameNode 请求文件元数据（块位置列表）
  • ② NN 返回每个块所在的 DataNode 地址列表（按距离排序）
  • ③ 客户端就近读取：优先本机 → 同机架 → 跨机架，直接从 DataNode 拉数据
  • ④ 读完一个块接着读下一个块，全部读完合并返回；读失败会换副本重试
先问 NN 拿地图，再找最近的 DN 拉货；就近原则优先本机同机架
Q
HDFS 副本放置策略是什么？🔥 高频
  • 默认 3 副本，放置策略：第一个副本放在客户端所在节点（非客户端则随机选一个节点）
  • 第二个副本放在与第一个副本不同机架的节点（容灾）
  • 第三个副本放在与第二个副本同机架的另一节点（平衡容灾与带宽）
  • 读写时通过机架感知计算节点距离，实现就近访问
一本地二异架三同架；一防单点、二防机架、三保带宽，三者平衡
Q
NameNode 的职责？元数据存在哪里？🔥 高频
  • 职责：管理文件系统命名空间（目录树）、维护文件与块的映射关系、处理客户端读写请求、管理副本与 DataNode 心跳
  • 元数据存储：内存为主（读写快），磁盘上以 fsimage（镜像）+ edits（编辑日志）持久化
  • 不存数据：真正的数据块都在 DataNode 上，NN 只存「指针」（块位置信息由 DN 上报）
  • DataNode 每 3 秒发一次心跳，超时 10 分钟判定宕机
NN 是目录管理员：管目录树、管块映射、不存数据；内存为主 fsimage+edits 兜底
Q
NameNode 的 HA 是怎么实现的？与 Federation 有什么区别？🔥 高频
  • HA（高可用）：一对 Active/Standby NN + JournalNode 集群（奇数台，如 3 台），Active 写 edits 到 JournalNode，Standby 实时同步；Active 挂了由 ZKFC（ZK Failover Controller）自动切换
  • Federation（联邦）：多个 NN 分管不同命名空间（目录），解决单 NN 内存瓶颈，横向扩展
  • HA 解决可用性，Federation 解决容量扩展，两者可叠加使用
HA 靠 JournalNode 同步 + ZKFC 切换，保可用；Federation 多 NN 分地盘，扩容量
Q
什么是 HDFS 安全模式（SafeMode）？
  • NN 启动时进入只读安全模式：等待 DataNode 上报块信息，期间不允许写操作
  • 当可用副本数达到阈值（默认满足最小副本的块占 99.9%）自动退出安全模式
  • 手动操作：hdfs dfsadmin -safemode enter/leave/get；异常时通常由「大量块缺副本」或「DN 未正常启动」导致
启动先自检：DN 报数、副本达标才放行；只读不写，齐了自动退出
Q
fsimage 和 edits 的作用？SecondaryNameNode 干什么？
  • fsimage：元数据快照镜像（某时刻的完整状态）；edits：操作增量日志（每次写操作的记录）
  • NN 启动时加载 fsimage + 重放 edits 恢复内存元数据；edits 过大会拖慢启动
  • SecondaryNameNode（2.x 前）/ Checkpoint 机制：定期把 fsimage + edits 合并成新 fsimage，并清空 edits，控制日志规模
fsimage 是照片、edits 是流水账；定期合并换新照片，账本才不会越记越长
Q
什么是机架感知（Rack Awareness）？
  • 通过配置网络拓扑（如 /default-rack），让系统知道每个节点所在的机架/机房
  • 据此计算节点间距离（同一节点 0、同机架 2、跨机架 4、跨数据中心 6），实现副本分布与就近读写
  • 作用：提高数据可靠性（副本分散机架）、降低网络带宽消耗
给每台机器贴门牌号，距离越近读得越快；副本跨架存放不怕整架停电

03 MapReduce

Q
MapReduce 的整体执行流程？🔥 高频
  • ① Input：输入分片（Split），每个 Split 启动一个 MapTask
  • ② Map：读取 (key, value) 对，执行 map 逻辑，输出到内存环形缓冲区
  • ③ Shuffle：缓冲区 80% 溢写，分区、排序、合并（Combiner），最终按分区写到磁盘
  • ④ Reduce：每个分区一个 ReduceTask，拉取对应分区数据，归并排序后执行 reduce 逻辑
  • ⑤ Output：reduce 结果写入 HDFS（part-r-xxxxx）
分片 → Map → Shuffle（分排合）→ Reduce → 落盘；Map 出力、Reduce 汇总、Shuffle 是中间搬运工
Q
Shuffle 阶段具体做了什么？🔥 高频
  • Map 端：输出写进环形缓冲区（默认 100MB，80% 触发溢写）→ 溢写前分区 + 排序（按 key）→ 可做 Combiner 合并 → 多次溢写合并成一个文件（归并排序）
  • Reduce 端：从各 MapTask 的对应分区拉取数据（拷贝阶段，可并行）→ 内存不够落磁盘 → 归并排序成有序的 (key, list[value]) → 交给 reduce 函数
  • 可调参数：缓冲区大小、溢写阈值、reduce 拉取并发数、压缩（snappy 减少 IO）
Map 端：缓冲→分区排序→合并；Reduce 端：拉取→归并→喂给 reduce；Shuffle 就是排序+搬运的中间层
Q
Combiner 和 Partitioner 的作用？🔥 高频
  • Partitioner：决定每个 (key, value) 进哪个分区（默认按 key 的 hash 取模），分区数 = ReduceTask 数
  • Combiner：Map 端的局部 Reduce，先合并一次再传输，减少网络 IO 和磁盘 IO；本质是 mini-reducer，必须满足交换律与结合律（如求和、计数、取最大）
  • 典型例子：WordCount 中 Combiner 先按词求和，reduce 端汇总；求平均值不能直接当 Combiner（需改造）
Partitioner 分地盘（决定去哪个 reduce），Combiner 先减负（本地先合一遍）；能合才合，平均要小心
Q
MapReduce 中 Join 有哪几种实现方式？🔥 高频
  • Reduce Join：在 map 端给数据打来源标签，以关联键分区，reduce 端分组合并；通用但shuffle 量大、易倾斜
  • Map Join：小表加载到内存（DistributedCache 分发），map 端直接查表拼接；适合一大一小，无 shuffle
  • Semi Join：先对关联键去重过滤（小表键集合广播），减少大表 shuffle 数据量，是 Reduce Join 的优化版
Reduce Join 通用慢，Map Join 小表快，Semi Join 先去重减量；一图流：小表进内存、大表走 map
Q
MapReduce 有哪些常见优化手段？
  • 输入优化：CombineTextInputFormat 合并小文件、压缩格式（snappy/lzo）减少读盘
  • Map 优化：合理设置 mapreduce.map.memory.mb、环形缓冲调大、开启Combiner 减少传输
  • Reduce 优化：调大拉取并行数、合理设置 reduce 数量（约为 0.95 或 1.75 × 节点数）
  • 其他：开启压缩输出、推测执行处理慢任务、数据本地性（计算移动数据不移动）
输入合小文件、中间做压缩、Reduce 数量有公式；调内存调并发，慢任务开推测执行
Q
MapReduce 为什么要求自定义序列化（Writable）？和 Java 序列化比呢？
  • 序列化：把对象转成字节流，跨节点传输 / 落盘；MR 网络传输频繁，序列化效率直接决定性能
  • Java 原生 Serializable 序列化：会带大量类信息，体积大、慢，不适合
  • Hadoop 用 Writable 接口：只序列化数据字段，紧凑高效；write() 写出、readFields() 读入，配合 WritableComparable 可比较排序
  • 常见实现：IntWritable、Text、LongWritable 等，自定义 Bean 需重写 write/readFields/toString/compareTo
Java 序列化带家当太重，Writable 只带干粮；write 出 read 进，够用且快
Q
推测执行（Speculative Execution）是什么？
  • 同一作业的多个 Task 中，若个别任务明显慢于平均（进度落后阈值），框架会在其他节点启动备份任务，谁先完成用谁的结果
  • 作用：缓解木桶效应、节点性能不均、任务卡死问题；代价是占用额外资源
  • 注意：reduce 端有 get 依赖不适合开推测；数据倾斜导致的慢任务开了也没用（根因不是节点问题）
慢任务不傻等，另起一个赛跑；跑赢的算数——但倾斜和 reduce 场景要关掉

04 YARN

Q
YARN 的架构和核心组件？🔥 高频
  • ResourceManager（RM）：全局老大，负责资源分配与调度（含 ApplicationManager）
  • NodeManager（NM）：每台节点的管家，管理本机容器（Container）、监控资源、上报心跳
  • ApplicationMaster（AM）：每个应用一个包工头，向 RM 申请资源、协调任务的执行与失败重试
  • Container：资源分配的最小单位（CPU + 内存的封装），Task 在 Container 中运行
RM 老大分资源、NM 管家管机器、AM 包工头管任务、Container 就是干活的窝
Q
YARN 有哪三种调度器？区别是什么？🔥 高频
调度器特点适用
FIFO先进先出，一个队列，先来先服务，会阻塞后面作业单用户测试
Capacity（容量）多队列按百分比预分配容量，队列内 FIFO，可弹性借用空闲生产默认
Fair（公平）多队列动态均衡资源，作业平均分配，谁资源少补谁多租户共享
  • Capacity 与 Fair 都支持队列隔离与优先级；Fair 比 Capacity 更注重公平性
  • Hadoop 3.x 默认 Capacity，生产中常按部门/业务划分队列隔离资源
FIFO 排队一个队、Capacity 分田到户、Fair 实时调济；生产用 Capacity、共享用 Fair
Q
一个作业提交到 YARN 的完整流程？
  • ① 客户端向 RM 提交作业（jar + 配置）
  • ② RM 的 ApplicationManager 启动 AM（放到某个 NM 的 Container 里）
  • ③ AM 向 RM 的 ResourceScheduler 申请资源（Container）
  • ④ RM 分配资源，AM 让对应 NM 启动 Task Container 执行任务
  • ⑤ Task 运行、汇报进度给 AM，AM 汇总给 RM；全部完成 AM 注销，释放资源
提交→起 AM→AM 要资源→NM 开 Task→完事收工；AM 是中间跑腿的包工头
Q
YARN 如何做资源隔离？Container 是什么？
  • 内存隔离：通过 cgroups / 线程监控 限制 Container 内存使用，超限杀进程（默认内存超限 OOM 直接杀）
  • CPU 隔离：通过 cgroups 设置 CPU 份额（Hadoop 3.x 支持 yarn.nodemanager.resource.cpu-vcores 精细化控制）
  • Container：资源封装的最小单位，规格 = CPU 核数 + 内存大小，由 AM 申请、NM 启动；隔离避免任务互相影响
内存超限杀进程、CPU 用 cgroups 限份额；Container 就是「几核几 G」的资源套餐

05 Hive

Q
Hive 的架构和执行流程？为什么说它是「数仓工具」而非数据库？🔥 高频

数仓为什么要分层？ODS/DWD/DWS/ADS 各层做什么？🔥 高频
  • 分层好处：① 结构清晰（责任单一）；② 数据血缘可追踪；③ 复用性（下游不重复计算）；④ 屏蔽原始数据变动影响

ODS 原样存、DWD 洗一洗、DWS 按主题汇总、ADS 出报表；层越多越清晰、越往上越收敛

Hive SQL 有哪些常用优化手段？🔥 高频

06 Spark Core

Q
Spark 的整体架构？相比 MapReduce 快在哪？🔥 高频
  • 架构：Driver（应用主控，含 SparkContext）→ Cluster Manager（Standalone/YARN/Mesos/K8s）→ Executor（工作节点上的进程，跑 Task、缓存数据）
  • 快的原因：① 内存计算——中间结果优先放内存，MR 每步落盘；② DAG 调度——一个 DAG 内多次计算不落盘；③ 多轮复用——RDD 可缓存复用，迭代计算（ML）优势巨大；④ 启动快（Executor 常驻，MR 每次起进程）
  • Executor 通过 BlockManager 管理缓存与 shuffle 数据，Driver 通过 DAGScheduler / TaskScheduler 调度
Driver 指挥、Executor 干活、缓存是提速关键；MR 一步一落盘、Spark 内存里一路跑完
Q
RDD 的五大特性是什么？🔥 高频
  • ① 分区列表：RDD 由若干分区（Partition）组成，是并行计算的基本单位
  • ② 分区计算函数：每个分区通过 compute 函数计算（懒加载，行动算子才触发）
  • ③ 依赖关系：记录父 RDD 的血缘（宽依赖/窄依赖），用于容错与阶段划分
  • ④ 分区器：Partitioner（Hash/Range），决定 key 的去向（仅 key-value RDD 有）
  • ⑤ 首选位置：数据本地性——优先把任务调度到数据所在节点，减少网络传输
分区、计算函数、依赖、分区器、首选位置——五大特性一句话：有分区能并行、有血缘能容错
Q
Transformation 和 Action 的区别？为什么 Spark 要「懒执行」？🔥 高频
类型示例触发
Transformationmap、filter、flatMap、reduceByKey、join不执行，只构建 DAG
Actioncollect、count、saveAsTextFile、foreach触发 Job，真正跑计算
  • 懒执行好处：① 构建完整 DAG 后统一优化（如合并 shuffle、裁剪算子）；② 避免中间结果落盘；③ 出错时可重新计算
  • 没有 Action 的 Transformation 不会执行任何计算，也不会产出结果
转换只画图纸、行动才动工；先攒 DAG 再统一优化，省工又省料
Q
Spark 宽依赖和窄依赖的区别？🔥 高频
  • 窄依赖：父 RDD 每个分区只被一个子分区使用（map、filter、union、coalesce），无 shuffle，可管道式在节点内串联执行
  • 宽依赖：父 RDD 分区被多个子分区使用（groupByKey、reduceByKey、join），产生 shuffle，需数据跨节点重排
  • 宽依赖是 Stage 划分的边界；容错时窄依赖只需重算丢失分区，宽依赖要重算整个父 RDD
窄依赖一个萝卜一个坑（无 shuffle 可流水线），宽依赖一父多子（shuffle 是分水岭）
Q
Spark 的血缘（Lineage）机制是怎么容错的？🔥 高频
  • RDD 记录完整的转换链（谁生出来的、经过了哪些算子），这就是血缘
  • 分区数据丢失时，沿血缘从源头重新计算，无需备份数据（对比 MR 靠落盘容错）
  • 局限：血缘链过长时重算代价大，所以配合 Checkpoint 斩断血缘（落盘 + 断链）
  • 代价权衡：窄依赖重算便宜（只算丢的部分），宽依赖重算贵（要重算整个 shuffle 上游）
血缘是族谱，丢了沿族谱重造；族谱太长就 Checkpoint 立碑断链，省得从头再来
Q
Spark 的 Stage 是怎么划分的？Job/Task 的关系？🔥 高频
  • 一个 Action 触发一个 Job；Job 按 宽依赖（shuffle）切分成多个 Stage
  • 划分方式：DAGScheduler 从后往前回溯，遇到宽依赖就切一刀；Stage 内是窄依赖的流水线计算
  • 每个 Stage 中的并行任务数 = 该 Stage 最后一个 RDD 的分区数，一个分区 = 一个 Task
  • 典型：WordCount 两个 Stage（shuffle 前后各一个），ShuffleMapStage 输出分区文件供 ReduceStage 拉取
Action 开 Job、宽依赖切 Stage、分区数定 Task；从后往前找 shuffle 一刀一刀切
Q
Spark 缓存和 Checkpoint 的区别？🔥 高频
维度Cache/persistCheckpoint
存储内存/磁盘，保留血缘落盘到 HDFS，斩断血缘
容错丢失后按血缘重算直接读检查点，不重算
用途多次复用的中间数据（加速）血缘过长 / 宽依赖重算贵的 RDD
  • 缓存级别：MEMORY_ONLY（默认）、MEMORY_AND_DISK、DISK_ONLY 等，unpersist() 手动释放
  • Checkpoint 建议在缓存后执行（persist + checkpoint），避免重算两次
Cache 是备忘录（记着怎么来的），Checkpoint 是备份（不认账重来）；复用用 Cache、长血缘用 Checkpoint
Q
Spark Shuffle 的发展演进（Hash / Sort / Tungsten）？🔥 高频
  • Hash Shuffle（1.x 早期）：每个 Map 给每个 Reduce 一个文件，文件数 = M × R，小文件爆炸；后续引入 Consolidate 合并
  • Sort Shuffle（1.2+ 默认）：map 端按分区排序，一个 Task 只输出 2 个文件（数据 + 索引），文件数 = M × 2，大幅减少小文件；支持 bypass 模式（reduce 数少且无聚合时走 hash 逻辑）
  • Tungsten Shuffle（2.x 实验）：基于 Unsafe 内存直接操作二进制数据，减少序列化/GC，性能更高
  • 关键参数：spark.shuffle.file.buffer、spark.shuffle.memoryFraction、spark.shuffle.compress
Hash 一桶一文件太多，Sort 一个 Task 俩文件，Tungsten 走底层二进制；文件越来越少、越来越快
Q
广播变量和累加器的作用？
  • 广播变量：把只读大变量（如维表）分发到每个 Executor 只存一份，所有 Task 共享，避免每个 Task 都传输一份（默认 broadcast 阈值 10MB）
  • 累加器：Driver 端的共享只写变量，Task 只能累加、不能读，Driver 最后读汇总值（如计数、求和）；自定义累加器可扩展
  • 注意：广播变量不能太大（内存压力）；累加器在 Action 内才会真正执行（Transform 中可能重复计算）
广播 = 大文件一次分发全员共享，累加器 = 各干各的只报数；都别在 transform 里搞小动作
Q
Spark 任务提交到执行的完整流程？
  • ① spark-submit 提交应用，Driver 启动（--deploy-mode client/cluster）
  • ② SparkContext 初始化，向 Cluster Manager 申请 Executor
  • ③ Executor 反向注册，Driver 的 DAGScheduler 把 Action 的 DAG 切成 Stage
  • ④ TaskScheduler 把 Stage 的任务（TaskSet）按数据本地性分发到 Executor 执行
  • ⑤ Task 在 Executor 中运行（launchTask），结果回传 Driver；全部完成应用结束、释放资源
提交起 Driver → 申请 Executor → DAG 切 Stage → 按本地性发 Task → 跑完收工
Q
Spark 常见 OOM 怎么排查和解决？
  • Driver OOM：collect() 拉回数据太大 → 改为分区处理 / 写文件；广播变量太大 → 换方式
  • Executor OOM：数据倾斜（个别分区巨大）→ 加盐 / 两段聚合；mapPartitions 一次性加载过多 → 分批处理
  • Shuffle OOM：shuffle 数据量超过内存 → 调大 spark.shuffle.memoryFraction、开启压缩、增大 Executor 内存、减少并行度过大问题
  • 统一思路：先看 UI 的 Stages 详情定位是哪个 Stage、哪个 Task 峰值内存高；再针对性调：加内存、减并行、换算子、治倾斜
Driver 大 collect、Executor 大分区、Shuffle 大流量是三大坑；看 UI 定位、倾斜加盐、内存不够调并行

Catalyst 优化器做了哪些优化？🔥 高频
  • 流程：SQL/AST → 逻辑计划（Logical Plan）→ 优化（规则优化 RBO）→ 物理计划（Physical Plan）→ 生成 RDD 代码
  • RBO 规则优化：谓词下推（先过滤）、列裁剪（只取需要的列）、常量折叠、子查询/join 重排、消除无用算子

Spark SQL 有哪些 Join 策略？🔥 高频
  • Broadcast Hash Join：小表（默认 10MB，可调 spark.sql.autoBroadcastJoinThreshold）广播到各 Executor 内存哈希 join，无 shuffle，最快
  • Sort Merge Join：两边按 key 排序后归并，有 shuffle，适合两大表（默认策略）
  • Shuffle Hash Join：两边按 key 哈希分发后，一侧建哈希表一侧探测，适合「一大一中」
  • 选择依据：表大小 + 是否可广播；AQE 可动态把 SMJ 转为 BHJ
小表广播免 shuffle 最快、大表归并排排序、一中一大量大哈希；广播阈值决定用哪个
Q
AQE（自适应查询执行）是什么？Spark 3.0 的哪些特性？🔥 高频
  • AQE：运行时根据真实统计信息动态优化（spark.sql.adaptive.enabled=true），三大能力：
  • ① 动态合并 Shuffle 分区：根据 shuffle 数据量自动调整 reduce 分区数（避免小分区过多）
  • ② 动态调整 Join 策略：运行中发现某侧变小，自动从 SMJ 切换为 BHJ
  • ③ 动态优化倾斜 Join：检测到数据倾斜的 key，自动拆分成多个任务并行处理
  • Spark 3.0 还引入 Dynamic Partition Pruning（DPP）：join 时动态裁剪分区
AQE 三招：分区自动合并、join 动态降级广播、倾斜自动拆分；一切以运行时实测数据为准
Q
Tungsten 引擎做了什么？
  • 内存管理：基于 Off-heap（堆外）/Unsafe 直接操作二进制内存，避免 Java 对象开销与 GC 停顿
  • 缓存友好的 Row 表示：列式缓存，按列存储提高缓存命中率
  • 全阶段代码生成（WholeStage Codegen）：把整个 Stage 的算子编译成一段 Java 代码，消除虚函数调用，性能提升数倍
  • 与 Catalyst 配合：Catalyst 定计划、Tungsten 提执行效率
堆外内存免 GC、列式缓存命中高、整段代码编译跑得快；Catalyst 出计划、Tungsten 出力气
Q
Spark UDF 怎么用？有什么性能注意点？

  • 注意：每行调用一次、Python UDF 要走 JVM-Python 序列化（慢），大任务建议用 Pandas UDF（矢量化）或 SQL 内置函数替代
  • 能用内置函数（when/case when、开窗）就别写 UDF；Spark 3.x 支持 SQL 标量 UDF 注册（CREATE FUNCTION）
UDF 一行行跑还带序列化开销；内置函数优先、Pandas UDF 次之、自定义兜底

Spark SQL 如何与 Hive 结合？Spark on Hive 是什么？
  • Spark on Hive：用 Spark SQL 引擎跑 Hive 的数仓 SQL，复用 Hive 的 Metastore 与表定义，但计算引擎换成 Spark（比 Hive on MR 快）
  • 配置：spark.sql.warehouse.dir + 指向 Hive 的 hive-site.xml，enableHiveSupport() 开启
  • 好处：无缝读写 Hive 表（内部/外部、分区、分桶），SQL 兼容性好；数仓升级引擎零迁移
  • 对比：Hive on MR / on Tez / on Spark 是执行引擎的选择，Metastore 始终是 Hive 的
借 Hive 的户口本（Metastore）、用 Spark 的算力；SQL 不用改、速度翻几倍

Q
Spark Streaming 的微批次模型？DStream 是什么？🔥 高频
  • 微批次：把连续的数据流按固定间隔切分成小批次（如 5s），每个批次就是一个 RDD，交给 Spark 批处理引擎计算
  • DStream：离散化数据流，本质是一连串 RDD 的序列（每个时间片一个 RDD），对 DStream 的算子就是对每个 RDD 的算子
  • 优势：复用批处理生态（SQL、MLlib 都能用）；劣势：延迟高（至少一个批次间隔）、不是真流式
把河水分成桶（批次），一桶一桶用批处理算；DStream 就是桶的序列，秒级延迟可接受
Q
Spark Streaming 的窗口操作怎么理解？🔥 高频
  • 窗口长度（window length）：统计的时间范围（如近 1 小时）
  • 滑动间隔（slide interval）：多久算一次（如每 10 分钟）；两者必须是最小批次的整数倍
  • 滑窗会把多个批次的数据聚合在一起，窗口内有重叠时数据被重复计算（滑动 > 窗口时无重叠）
  • 例：reduceByKeyAndWindow(func, invFunc, win, slide) 支持增量计算优化
窗口=看多久，滑动=隔多久看一次；窗口滑动的整数倍，重叠数据重复算
Q
Spark Streaming 如何保证精确一次（Exactly-once）？🔥 高频
  • 三要素：输入端 + 计算端 + 输出端 都要精确一次
  • 输入：Kafka 的 offset 由 Spark 自己管理（checkpoint 存储），配合 Kafka 的 offset 对比去重
  • 计算：微批次 RDD 具有确定性，失败重算结果一致
  • 输出：写 HDFS 用原子写/幂等写（如分区目录覆盖）；写 MySQL 用事务 + 唯一键去重；Kafka sink 用事务 API
  • 常见做法：enable.auto.commit=false + 作业成功后手动提交，或在输出时记录 offset 做幂等
输入管理 offset、计算确定可重算、输出幂等或事务；三端齐了才是真精确一次
Q
Flink 和 Spark Streaming 的核心区别？🔥 高频
维度Spark StreamingFlink
模型微批次（秒级延迟）真流式（毫秒级延迟）
窗口基于处理时间为主事件时间 + Watermark 精确乱序处理
状态借助外部存储 / 无原生状态原生状态管理 + Checkpoint
容错RDD 血缘重算分布式快照（Chandy-Lamport）
吞吐高（批处理优化）高（流水线 + 异步 IO）
Spark 批量小桶（秒级）、Flink 涓涓细流（毫秒级）；要精确乱序和状态就选 Flink
Q
Spark Streaming 的背压（Backpressure）机制？
  • 问题：数据生产速率 > 消费速率时，批次堆积、延迟越来越大
  • 机制：spark.streaming.backpressure.enabled=true，根据当前处理速率动态调节消费速率（通过反馈控制）
  • 配合 spark.streaming.kafka.maxRatePerPartition 设最大消费速率上限，防止突发流量打爆
  • 对比 Flink：Flink 通过网络缓冲水位天然传导反压，无需动态限速
吃不下就放慢筷子：按处理速度动态限消费速率，再加个最大速率兜底
Q
Spark Streaming 的状态管理怎么实现？
  • 无状态：每批次独立计算（如 WordCount 每批一次）
  • 有状态：updateStateByKey（全量更新，性能差）或 mapWithState（增量更新，只处理变化的 key，推荐）
  • 状态通过 Checkpoint 持久化到 HDFS，故障恢复时从检查点恢复状态
  • 注意：状态会随 key 无限增长，需要设定超时清理（如 7 天无更新的 key 移除）
updateState 全量慢、mapWithState 增量快；状态靠 Checkpoint 保命、设超时防膨胀

09 Flink

Q
Flink 的架构和核心组件？🔥 高频
  • JobManager：主控，负责作业调度、Checkpoint 协调、故障恢复（类似 Driver）
  • TaskManager：工作节点，运行 Task 槽位（Slot），管理内存与状态
  • JobGraph → ExecutionGraph：由 Client/JobManager 构建 DAG；Task 之间通过网络流（shuffle）连接
  • 并行度：每个算子可设并行度，算子实例 = Subtask，分布在 Slot 上运行
  • 部署：Standalone / YARN / Kubernetes / 云；资源由 Cluster Manager 提供
JobManager 指挥、TaskManager 干活、Slot 是工位；Subtask 是算子的分身，并行度决定几个分身
Q
Flink 的三种时间语义？🔥 高频
  • 事件时间（Event Time）：数据产生的时间（业务真实时间），最准确，但要处理乱序
  • 摄入时间（Ingestion Time）：数据进入 Flink 的时间，介于两者之间
  • 处理时间（Processing Time）：算子处理时刻的系统时间，最快但结果不确定（受机器负载影响）
  • 生产场景：默认用事件时间 + Watermark 处理乱序；窗口计算都基于事件时间
事件时间看「出生证」、处理时间看「现在几点了」、摄入时间看「进门时间」；要准就事件时间
Q
Watermark（水位线）的原理和作用？🔥 高频
  • 作用：处理乱序数据——表示「事件时间 ≤ 水位线的数据已全部到达」，用来触发窗口计算
  • 生成方式：周期生成 / 每个事件生成；watermark = max(seen_event_time) - 允许乱序延迟
  • 窗口触发：窗口结束时间 ≤ 当前水位线时，窗口触发计算；迟到的数据默认丢弃，可用侧输出流（sideOutputLateData）或 allowedLateness 处理
  • 注意：水位线要单调递增（不能倒退），按分区生成时取最小水位线作为全局水位
水位线 = 已到数据的最大时间 - 容差；到了窗口截止就触发，晚到的走侧输出或等一等
Q
Flink 窗口有哪几种分类？🔥 高频
按驱动类型说明
时间窗口Tumbling（滚动）固定大小不重叠（每 5 分钟一次）
Sliding（滑动）固定大小可重叠（窗口 10 分钟、滑动 5 分钟）
计数窗口Count按元素个数触发（每 100 条一次）
会话窗口Session按不活跃间隔切分（30 分钟无数据则结束）
  • 全局窗口（Global）+ 自定义 Trigger 可做高级控制；窗口计算用 window/apply、aggregate、process
滚动不重叠、滑动有重叠、计数按条数、会话按空闲；四大窗口按需求选
Q
Flink 的 Checkpoint 和 Savepoint 是什么？🔥 高频
  • Checkpoint：基于 Chandy-Lamport 分布式快照算法（Barrier 对齐），周期性自动把算子状态+数据源偏移量存到外部（HDFS），用于故障自动恢复
  • Savepoint：手动触发的 Checkpoint，用于版本升级、作业迁移、代码修改后恢复，可以跨作业恢复
  • Barrier 对齐保证 exactly-once（对账机制）；配置 state.backend（RocksDB / FsState / Memory）与间隔
  • 恢复：TaskManager 挂掉 → JobManager 从最近 Checkpoint 重启整个作业并恢复状态
Checkpoint 是自动存档（定期、故障用），Savepoint 是手动存档（升级迁移用）；Barrier 对账保精确一次
Q
Flink 如何实现端到端精确一次？🔥 高频
  • Source：Kafka 连接器记录 offset 到状态，从 Checkpoint 恢复时从记录的 offset 续读
  • 计算：Checkpoint 快照保证状态不重不丢（Barrier 对齐）
  • Sink：两阶段提交（2PC）——Flink 提供 TwoPhaseCommitSinkFunction（Kafka 事务、JDBC 事务）；Checkpoint 成功时预提交 → 所有算子确认后提交
  • 注意：外部系统必须支持事务/幂等（Kafka 事务、MySQL 事务、HBase 幂等写入）；两阶段提交期间数据有可见延迟（未提交不可见）
Source 记 offset、中间靠快照、Sink 走两阶段提交；三端闭环才能端到端精确一次
Q
Flink 状态有哪些类型？状态后端怎么选？
  • 托管状态：Keyed State（ValueState、ListState、MapState、ReducingState，按 key 隔离）+ Operator State（算子级，如 offset）
  • 状态后端：① MemoryStateBackend（内存，测试用）；② FsStateBackend（状态在 TaskManager 内存、Checkpoint 落 HDFS）；③ RocksDBStateBackend（磁盘 KV 存储，状态可超内存，生产推荐）
  • RocksDB 支持增量 Checkpoint、大状态；代价是读写比内存慢（序列化开销）
  • 状态 TTL：设置过期时间自动清理，防止状态无限增长
Keyed 按 key 分格、Operator 算子级；状态大选 RocksDB 磁盘兜底，小状态内存就够
Q
Flink 的反压机制是怎么工作的？
  • 下游处理慢 → 网络缓冲池占满 → 上游 send 阻塞 → 反压逐级向上传导直到 Source（Kafka 消费变慢）
  • 依赖 Credit-based 流控：下游向上游申请信用额度，有额度才发数据，实现背压
  • 优势：无需停流、天然自适应；反压是临时状态，下游恢复后自动解除
  • 排查：看 WebUI 的 BackPressure 指标；处理：加大并行度、优化算子（异步 IO）、调大缓冲或减少单条数据处理耗时
下游塞车就传话上游慢点发，信用额度机制自动刹车；反压是交通拥堵，不是故障
Q
Flink CEP 是什么？适合什么场景？
  • CEP（Complex Event Processing）：在流中匹配复杂事件模式（如「A 后 5 分钟内出现 B 和 C」）
  • API：pattern(...).where(...).followedBy(...).within(时间) 定义模式，输出匹配到的事件序列
  • 典型场景：风控（登录异常序列）、实时营销（加购-支付漏斗）、监控告警（指标连续超阈值）、反欺诈
  • 实现：基于 NFA（非确定有限自动机）+ 状态存储，匹配状态也可纳入 Checkpoint
CEP 在流里「找剧本」：定义模式、匹配事件串；风控营销监控告警都用它
Q
Flink 有哪几种部署/运行模式？
  • Standalone：独立集群，简单但资源无隔离、不适合生产大集群
  • YARN Session：先起常驻集群，多个作业共享；适合小作业、快速验证
  • YARN Per-Job / Application：每个作业独立集群，资源隔离好、互不影响，生产推荐
  • Kubernetes：容器化部署，弹性扩缩容，云原生趋势；原生 K8s（Native）与 Flink Operator 两种方式
  • Application 模式与 Per-Job 区别：main 方法在 Cluster 中执行（Application 模式 jar 提交更轻）
Standalone 测试、Session 共享、Per-Job 隔离、K8s 弹性；生产隔离选 Per-Job/Application

10 Kafka

Q
Kafka 的核心架构和概念？🔥 高频
  • Broker：Kafka 服务器节点，集群由多个 Broker 组成；Controller（一个 Broker 兼任）负责分区首领选举等元数据管理
  • Topic：消息的逻辑分类；Partition：Topic 的物理分片，消息按追加顺序写入，一个分区内有序
  • Offset：消息在分区内的位移，消费者靠它定位消费位置
  • Producer / Consumer / Consumer Group：生产者、消费者、消费者组（组内负载均衡消费、组间广播）
  • ZooKeeper（旧版）/ KRaft（3.x 去 ZK）：集群元数据协调
Topic 分类、Partition 分片、Offset 定位、Group 分摊；Broker 集群加 Controller 管天下
Q
Kafka 的分区和副本机制？🔥 高频
  • 每个分区有 1 个 Leader + N 个 Follower（副本数默认 1，生产建议 3）
  • 所有读写都走 Leader，Follower 只做同步备份（从 Leader 拉取数据），保证一致性
  • 分区内追加写保证有序；分区数决定并行度（消费者数 ≤ 分区数才能分摊）
  • 副本分布在不同 Broker / 机架上，Leader 挂了由 Controller 从 ISR 中选新 Leader
  • 分区数不是越多越好：分区多 → 文件句柄、网络连接、选举开销都增大
一主多从、读写只找 Leader；Follower 默默备份，Leader 挂了 ISR 里顶上来
Q
ISR 是什么？Leader 选举机制？🔥 高频
  • ISR（In-Sync Replicas）：与 Leader 保持同步的副本集合；同步落后超过阈值（replica.lag.time.max.ms，默认 30s）会被踢出 ISR
  • 选举：Leader 挂了，Controller 从 ISR 中选第一个存活的副本当新 Leader（优先 ISR，不丢数据）
  • ISR 为空（极端情况）：可开启 unclean.leader.election.enable 选非同步副本（可能丢数据，换取可用性）
  • ACK 机制关联：acks=all 要求 ISR 全部确认才算写入成功
ISR 是「跟得上进度的小弟名单」，Leader 挂了从名单里挑；名单空才允许乱选（丢数据换可用）
Q
Kafka 怎么保证消息不丢失？🔥 高频

从三端分别保证：

  • Producer：acks=all（ISR 全部确认）+ retries 重试 + enable.idempotence=true 幂等
  • Broker：副本数 ≥ 3、min.insync.replicas ≥ 2、同步刷盘（log.flush.interval.messages=1）或依赖 OS 刷盘 + 副本冗余；Leader 选举不选非 ISR
  • Consumer：处理成功后再提交 offset（enable.auto.commit=false 手动提交）；避免「先提交后处理」丢数据
  • 注意 acks=all 与 min.insync.replicas 配合：ISR 少于最小值时写入直接失败（宁可不可用不丢数据）
生产端全确认重试幂等、存储端多副本加 ISR 门槛、消费端先处理后提交；三段都守才不丢
Q
Kafka 如何保证消息的顺序性？🔥 高频
  • Kafka 只能保证分区内有序，跨分区不保证
  • 保证方式：按业务 key 分区（如订单号 hash 到同一分区）→ 同一 key 的消息有序写入、顺序消费
  • 消费端注意：单分区内单消费者顺序处理；不要并发处理同一分区的消息（乱序）
  • 全局有序：只能1 个分区 1 个消费者，牺牲并行度，通常不用
  • 配合事务可做到「顺序 + 不重」：enable.idempotence 保证重试不产生重复消息
一个 key 进一个分区、一个分区只一个消费者顺序读；全局有序=单分区单消费者，代价是慢
Q
Kafka 幂等和事务机制？🔥 高频
  • 幂等（Idempotence）：enable.idempotence=true 后，Producer 给每条消息加 序列号，Broker 端去重——解决单分区内「重试产生重复」问题（PID + seq）
  • 事务（Transaction）：transactional.id + initTransactions()，实现跨分区原子写入；配合 read_committed 消费者只读已提交消息
  • 幂等覆盖「单分区不重」，事务覆盖「多分区原子 + 精确一次消费」
  • 配合 Flink：Flink Kafka Sink 用事务写入实现端到端精确一次
幂等管单分区不重复，事务管多分区原子性；一个 PID+seq、一个 transaction 全家桶
Q
消费者组和 Rebalance 机制？🔥 高频
  • 一个 Topic 的每个分区只能被同组的一个消费者消费；组内分区均匀分配（分区数 ≥ 消费者数时每人至少一个）
  • Rebalance：消费者加入/退出/崩溃或分区变化时，重新分配分区的过程
  • 触发：新消费者加入、消费者心跳超时（session.timeout）、订阅变更、分区数调整
  • 问题：Rebalance 期间全体停止消费（stop-the-world），反复 Rebalance 是「rebalance 风暴」，常见原因是消费太慢导致心跳超时
  • 优化：调大 max.poll.interval.ms、降低 max.poll.records、提升处理速度、用增量协调式 Rebalance（2.4+ 静态成员）
分区按组摊、组员变动就重分；重分全员停摆，慢消费者是风暴之源
Q
Kafka 的位移（offset）提交有哪几种方式？
  • 自动提交：enable.auto.commit=true（默认），定期提交（auto.commit.interval.ms）；可能重复消费（提交前崩溃）
  • 手动提交同步：commitSync()，提交失败会重试，但阻塞
  • 手动提交异步：commitAsync()，不阻塞但失败不重试，可能丢位移
  • 最佳实践：处理成功后手动提交（at-least-once），配合幂等消费达到 exactly-once 效果
自动省事会重复，同步稳但堵，异步快但会丢；先处理后提交是黄金法则
Q
Kafka 有哪些常见调优点？
  • 吞吐：批量（batch.size、linger.ms）、压缩（compression.type=lz4/snappy）、acks=1 提吞吐（丢可靠性）
  • 延迟：减小批大小、提高网络线程、分区数匹配消费者
  • 存储：合理设置日志保留（retention.ms）与段大小（log.segment.bytes）；页缓存依赖 OS 内存，预留足够
  • 资源：Broker 用 SSD + 大内存（页缓存）、分区数与磁盘数对齐、JVM 堆别开太大（留内存给页缓存）
  • 监控：关注 ISR 收缩、消息积压（消费 lag）、分区 leader 分布是否均匀
吞吐靠批量压缩、延迟靠小批快发、存储靠保留策略；SSD 大内存、页缓存是亲儿子
Q
Kafka 和 RocketMQ 的区别？
维度KafkaRocketMQ
模型分区 + 消费者组（拉模式）队列 + 消费组（拉模式）
顺序分区内有序队列内有序，全局顺序更易支持
延迟毫秒级毫秒级
事务事务 API（2PC）半消息机制（事务消息更成熟）
生态大数据流计算事实标准（Flink/Spark 无缝）Java 中间件生态，定时/延时消息、消息轨迹
定位高吞吐日志/流式管道业务消息（金融级可靠性）
大数据管道选 Kafka、业务消息选 RocketMQ；一个为吞吐而生、一个为可靠而活

11 数仓与建模

Q
维度建模是什么？事实表和维度表的区别？🔥 高频
  • 维度建模（Kimball）：从业务分析角度设计模型，核心是「事实表 + 维度表」两层结构，围绕业务过程建模
  • 事实表：记录业务过程的事实（可度量），如订单事实表（订单金额、件数、外键维度）；每行是一次业务事件，粒度是核心
  • 维度表：描述事实的分析角度（上下文属性），如时间维、用户维、商品维；表小、字段多、有主键
  • 事实表不断追加（越来越大），维度表缓慢变化（相对稳定）
  • 建模步骤：选择业务过程 → 声明粒度 → 确定维度 → 确定事实（四步法）
事实表记「发生了啥」（金额数量）、维度表管「从啥角度看」（时间用户商品）；建模四步：过程→粒度→维度→事实
Q
星型模型、雪花模型、星座模型的区别？🔥 高频
模型结构特点
星型事实表在中心，维度表直接连接（不规范化）查询快（join 少）、冗余多、生产首选

  • SCD2（新增行）：变化时插入新行，用生效/失效时间（或版本号、当前标志）标记——保留完整历史，最常用（拉链表）
  • SCD3（新增列）：加「原值/现值」两列，只保留最近一次变化——折中方案
  • 选型：需要历史分析用 SCD2，只要当前状态用 SCD1，轻量回溯用 SCD3

  • 查询某日快照：where start_dt <= '2026-08-27' and end_dt >= '2026-08-27'

public class WordCount {
    // Mapper：每行拆词，输出 (word, 1)
    public static class WCMapper
        extends Mapper<LongWritable, Text, Text, IntWritable> {
        private Text word = new Text();
        private IntWritable one = new IntWritable(1);
        protected void map(LongWritable key, Text value, Context ctx)
                throws IOException, InterruptedException {
            for (String w : value.toString().split("\\s+")) {
                word.set(w);
                ctx.write(word, one);
            }
        }
    }
    // Reducer：相同 key 求和
    public static class WCReducer
        extends Reducer<Text, IntWritable, Text, IntWritable> {
        protected void reduce(Text key, Iterable<IntWritable> values, Context ctx)
                throws IOException, InterruptedException {
            int sum = 0;
            for (IntWritable v : values) sum += v.get();
            ctx.write(key, new IntWritable(sum));
        }
    }
    // Driver：组装作业
    public static void main(String[] args) throws Exception {
        Job job = Job.getInstance();
        job.setJarByClass(WordCount.class);
        job.setMapperClass(WCMapper.class);
        job.setReducerClass(WCReducer.class);
        job.setOutputKeyClass(Text.class);
        job.setOutputValueClass(IntWritable.class);
        FileInputFormat.setInputPaths(job, new Path(args[0]));
        FileOutputFormat.setOutputPath(job, new Path(args[1]));
        System.exit(job.waitForCompletion(true) ? 0 : 1);
    }
}

    }
}
public static class JoinReducer extends Reducer<Text, Text, Text, Text> {
    protected void reduce(Text key, Iterable<Text> values, Context ctx)
            throws IOException, InterruptedException {
        String user = "";
        List<String> orders = new ArrayList<>();
        for (Text v : values) {
            String[] f = v.toString().split(",", 2);
            if (f[0].equals("1")) user = f[1];      // 用户表
            else orders.add(f[1]);                  // 订单表
        }
        for (String o : orders)
            ctx.write(key, new Text(user + "\t" + o));
    }
}

-- 1. 连续登录 3 天以上用户（经典）
SELECT user_id
FROM (
    SELECT user_id, dt,
           DATE_SUB(dt, ROW_NUMBER()
               OVER (PARTITION BY user_id ORDER BY dt)) AS grp
    FROM login_log
    GROUP BY user_id, dt          -- 先去重一天多次登录
) t
GROUP BY user_id, grp
HAVING COUNT(*) >= 3;

-- 2. 次日留存率（某日活跃用户中次日还活跃的比例）
SELECT t1.dt,
       COUNT(DISTINCT t2.user_id) / COUNT(DISTINCT t1.user_id) AS retention
FROM active t1
LEFT JOIN active t2
  ON t1.user_id = t2.user_id AND t2.dt = DATE_ADD(t1.dt, 1)
GROUP BY t1.dt;

-- 3. 行转列（多行聚一列）：collect_list / concat_ws
SELECT user_id, CONCAT_WS(',', COLLECT_LIST(item)) AS items
FROM orders GROUP BY user_id;
-- 4. 列转行（一行炸多行）：LATERAL VIEW + EXPLODE
SELECT user_id, item
FROM t LATERAL VIEW EXPLODE(SPLIT(items, ',')) t2 AS item;

// 思路：随机撒点，落在单位圆内点数 / 总点数 ≈ π/4
val NUM = 100000
val count = sc.parallelize(1 to NUM).map { _ =>
    val x = math.random
    val y = math.random
    if (x * x + y * y <= 1) 1 else 0
}.reduce(_ + _)
val pi = 4.0 * count / NUM
println(s"Pi ≈ $pi")
