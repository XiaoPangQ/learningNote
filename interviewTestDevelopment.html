01测试基础与理论

Q
什么是软件测试？测试的目的是什么？🔥 高频

定义：使用人工或自动手段来运行或测定系统的过程，检验它是否满足规定的需求，并识别预期结果与实际结果之间的差异。

目的不是证明「没有 bug」，而是尽早发现缺陷、验证需求符合度、评估质量风险、提供质量信心。

两个关键视角：

  • 验证（Verification）：做对了没有？（需求 → 实现）
  • 确认（Validation）：做的是对的东西吗？（产品 → 用户需求）
「找错 ≠ 证明没错」；验证是「对不对」，确认是「该不该」
Q
软件测试的七大原则是什么？🔥 高频
  1. 测试显示存在缺陷：只能证明有 bug，不能证明没 bug
  2. 穷尽测试不可能：组合无限，要按风险与优先级取舍
  3. 尽早测试：缺陷越早发现，修复成本越低（10 倍定律）
  4. 缺陷集群性：80% 的缺陷集中在 20% 的模块（二八定律）
  5. 杀虫剂悖论：同一批用例反复跑，发现缺陷能力下降，需持续更新
  6. 测试依赖上下文：电商 App 与银行系统的测试重点完全不同
  7. 不存在缺陷的谬论：满足不了用户需求，没 bug 也没用（可用性）
口诀「显穷早集杀上无」——显示缺陷、穷尽不能、尽早、集群、杀虫剂、上下文、无缺陷谬论
Q
测试级别和测试类型如何划分？

按级别（从小到大）：

  • 单元测试：测最小模块（函数/类），开发自测
  • 集成测试：测模块间接口与交互，找对接问题
  • 系统测试：测整个系统功能与非功能，环境最接近生产
  • 验收测试：用户/业务方确认是否满足需求（α 内测 / β 公测）

按类型（测什么）：功能测试、性能测试、安全测试、兼容性测试、易用性测试、可靠性测试、可移植性测试等。

级别看「粒度与时机」：单集系统验收；类型看「关注维度」：功能性能安全易用
Q
V 模型与 W 模型有什么区别？🔥 高频

V 模型：把测试阶段与开发阶段一一对应——需求分析 ↔ 验收测试、概要设计 ↔ 系统测试、详细设计 ↔ 集成测试、编码 ↔ 单元测试。

  • 优点：阶段清晰，测试有明确依据
  • 缺点：测试仍然在编码之后，属「事后测试」，缺陷发现晚、成本高

W 模型（双 V）：开发 V 与测试 V 并行，测试伴随开发全流程——需求阶段就开始测试设计，编码阶段就做单元测试。

  • 优点：测试左移，尽早介入、尽早发现
  • 缺点：对测试人员技能与流程要求高
V 是「开发完再测」，W 是「边开发边测」；核心差异就一句：测试是否从需求阶段就介入
Q
什么是测试金字塔？为什么推荐金字塔模型？🔥 高频

测试金字塔（Mike Cohn）把测试按成本与数量分层：

  • 底层：单元测试（数量最多，最快最便宜，覆盖核心逻辑）
  • 中层：服务/接口测试（数量适中，验证系统间契约）
  • 顶层：UI 端到端测试（数量最少，最慢最贵、最不稳定）

为什么推荐：UI 测试成本高、执行慢、易 flaky，把大量用例压在单元层可以快速反馈 + 低成本回归；UI 只保留关键链路。

另一种观点：测试蜜蜂——各层都要有，UI 测试虽少但不可省，像蜜蜂传粉一样发挥关键作用。

「底单元、中接口、顶 UI」；UI 贵而脆，逻辑压底层；别把金字塔倒过来（全 UI 测试）
Q
什么是测试左移和测试右移？🔥 高频

测试左移（Shift-Left）：把测试活动提前到需求、设计、编码阶段——需求评审、静态代码检查、开发自测、TDD、代码 review，尽早发现缺陷降低成本。

测试右移（Shift-Right）：把测试延伸到生产环境——线上监控、灰度发布验证、A/B 测试、用户行为分析、生产日志与故障演练，验证真实场景下的质量。

两者结合：左移「提前发现问题」，右移「上线后持续保障」。

左移省钱（早发现），右移兜底（线上验）；左移管开发期，右移管生产期
Q
常用的测试度量指标有哪些？🔥 高频

度量分「过程指标」与「结果指标」：

  • 用例执行率：已执行用例 / 计划用例，反映测试进度
  • 用例通过率：通过用例 / 已执行用例，反映当前质量状态
  • 缺陷密度：缺陷数 / KLOC（千行代码），反映模块质量
  • 缺陷逃逸率：线上缺陷 / 全部缺陷，衡量测试覆盖有效性（越低越好）
  • 缺陷发现率（DDE）：缺陷数 / 执行用例数，反映用例的有效性
  • 需求覆盖率：已测需求 / 全部需求
  • 修复率与遗留缺陷：反映缺陷处理与发布风险
看进度看执行率、看状态看通过率、看质量看逃逸率；逃逸率是测试的「KPI 之王」
Q
在敏捷开发中，测试如何介入整个流程？

敏捷测试强调全程参与、持续反馈：

  • 迭代规划会：提前理解需求、评估可测性、识别风险
  • 需求评审：站在用户角度提疑问，把模糊需求问清楚
  • 开发过程中：测试用例设计先行，配合 TDD/结对
  • 每日站会：同步测试进度与阻塞
  • 迭代结束：迭代验收、回归、回顾会总结改进

敏捷测试与传统最大的区别：测试不是独立阶段，而是融入每个 Sprint；测试用例随需求变化持续演进。

「规划懂需求、评审挑毛病、迭代边测边回归」——测试是敏捷的一等公民，不是最后一道关卡

02测试用例设计

Q
什么是等价类划分法？如何应用？🔥 高频

思想：把输入域划分为若干等价类，同一等价类中的输入对测试来说「等效」——测一个代表即可，从而用少量用例覆盖大量输入。

  • 有效等价类：符合需求、合理的输入
  • 无效等价类：不符合需求、非法的输入（至少每个无效类都要测）

以「1-100 的整数」为例：有效类 = 1~100；无效类 = 小于 1、大于 100、非整数、非数字。

设计原则：一条用例尽量只覆盖一个无效等价类，因为无效输入往往触发错误提示，混在一起无法定位是哪个条件失败。

「同类的测一个就够，无效的每个都要测，一条用例只测一个无效类」
Q
边界值分析法是什么？与等价类的关系？🔥 高频

思想：大量缺陷发生在输入边界附近（如 if 的 <= 写错成 <），所以重点测边界值及其左右。

对「1-100 的整数」：要测 0、1、2 和 99、100、101，即边界点 + 刚过边界的点。

与等价类的关系：边界值是等价类的补充——等价类取「类内代表值」，边界值取「边界上与边界外的值」；实践中常组合使用，边界值用例更高概率发现缺陷。

开闭区间要特别注意：(1,100] 时 1 本身是无效的，但 2 有效；判断边界的「有效/无效」要看需求原文。

「两边三值」：上点、离点、内点；边界最容易翻车，先画数轴再取值
Q
判定表法适合什么场景？如何构造？

适用场景：输入条件不多（一般 ≤ 4 个条件）、条件之间存在组合逻辑、且每个组合有不同动作的规则类需求（如优惠计算、权限判断）。

构造步骤：

  1. 列出所有条件与条件的取值（如：是否会员、金额是否满 100）
  2. 列出所有动作（如：打 8 折、不打折）
  3. 列出条件组合的全部排列（2^n 条规则）
  4. 为每条规则填动作，合并相同动作的规则（化简）
  5. 每条规则转成一条用例

条件多时组合爆炸，此时改用正交实验法抽样。

「条件少逻辑杂，判定表把组合一网打尽」；条件多了上正交
Q
因果图法怎么用？

思想：从输入条件（因）推导输出结果（果），分析因果关系后转换成判定表生成用例，适合输入输出之间有复杂逻辑关系的情况。

基本符号：恒等（因→果）、非、或（至少一个成立）、与（全部成立）；约束包括互斥、包含、唯一等。

步骤：找原因与结果 → 画因果图 → 加约束 → 转判定表 → 生成用例。

因果图是判定表的「前置分析工具」：先画因果、再转判定表、最后出用例
Q
正交实验法是什么？适合什么场景？

思想：用数学上的正交表（如 L9(3^4)）从全量组合中抽取「均匀分散、齐整可比」的代表性组合，用很少的用例覆盖主要组合。

适用场景：因素多、水平多、组合爆炸的场景（如兼容性测试：浏览器 × 系统 × 分辨率；配置项测试）。

步骤：确定因素与水平 → 选正交表 → 查表生成组合 → 补充必要的边界/业务用例。

「多因素多水平，全组合测不完，正交表抽代表」；两两组合（Pairwise）也是同类思想
Q
场景法是什么？如何设计？🔥 高频

思想：从用户操作流出发设计用例，适合业务流程清晰、有多个分支路径的系统（电商下单、转账、审批流）。

核心概念：

  • 基本流：从开始到结束的「happy path」，一条主线
  • 备选流：主线上的分支（如余额不足、库存不足、取消订单）
  • 用例 = 基本流 + 一个或多个备选流组合

以「登录」为例：基本流 = 输入正确账号密码进入；备选流 = 密码错误、账号不存在、连续输错锁定、忘记密码等。

「主线走一遍，支线全都要走到」；每条备选流都是独立的测试场景
Q
测试用例包含哪些要素？评审标准是什么？🔥 高频

用例要素（8 要素）：用例编号、所属模块、用例标题、前置条件、测试步骤、测试数据、预期结果、优先级。

评审标准：

  • 可执行性：步骤清晰无歧义，别人能照着跑
  • 可判定性：预期结果可判断通过/失败，不写「运行正常」这种模糊话
  • 可追溯性：每条用例能对应到需求
  • 覆盖充分：正向、反向、边界、异常都有
  • 无重复：同一条路径不被多条用例重复覆盖

评审参与人：测试、开发、产品、用例作者。

「标题前置加步骤，数据预期别缺失」；评审看三性：可执行、可判定、可追溯

03功能测试与缺陷管理

Q
功能测试的完整流程是什么？
  1. 需求理解与分析：参加评审，明确功能点与验收标准
  2. 测试计划：范围、资源、进度、风险
  3. 用例设计：等价类/边界值/场景法等产出用例
  4. 用例评审：与开发、产品对齐口径
  5. 环境准备：搭建测试环境、准备测试数据
  6. 用例执行：冒烟 → 功能 → 回归，记录结果
  7. 缺陷提交与跟踪：提单、验证关闭、回归
  8. 测试报告：覆盖情况、缺陷统计、质量结论、上线建议
「需求→计划→设计→评审→环境→执行→缺陷→报告」八步走，报告是终点也是下一轮的起点
Q
冒烟测试、回归测试、验收测试有什么区别？🔥 高频
类型测什么时机特点
冒烟测试主流程是否跑通提测后第一时间快，冒烟不过直接打回
回归测试改动是否影响已有功能每次修复/迭代后范围随改动风险评估
验收测试是否满足需求与用户期望上线前α 内测 / β 公测，业务方参与

冒烟是「能不能进」，回归是「有没有倒退」，验收是「该不该放」。

冒烟看「跑得通」，回归看「没退步」，验收看「该放行」
Q
缺陷的生命周期是什么？🔥 高频

标准流程：

  • 新建（New/Open）：测试提交缺陷
  • 确认（Confirmed）：开发/负责人确认是缺陷
  • 处理中（In Progress）：开发开始修复
  • 修复完成（Resolved/Fixed）：开发改完，等待验证
  • 验证关闭（Closed）：测试复测通过后关闭
  • 重新打开（Reopen）：复测不通过，打回重开

其他状态：延期（Deferred）、重复（Duplicate）、无效（Invalid）、不予修复（Won't Fix）、无法复现（Cannot Reproduce）。

「提→认→修→验→关」五步主线，验不过就「重开」；打回理由要写清，别让开发猜
Q
缺陷的严重程度与优先级如何区分？🔥 高频

严重程度（Severity）：缺陷造成的影响大小，一般四级：

  • 致命（Blocker）：系统崩溃、数据丢失、主流程不可用
  • 严重（Critical）：主要功能错误，有替代方案但体验差
  • 一般（Major）：次要功能问题，不影响主流程
  • 轻微（Minor）：界面错别字、样式问题、提示不友好

优先级（Priority）：修复的紧迫程度——P1 立即修复、P2 本迭代修复、P3 尽快安排、P4 有空再修。

注意两者不一定正相关：一个影响很小的错别字若出现在用户注册协议上，可能优先级很高；严重的低频缺陷优先级也可能排后。

严重度看「破坏力」，优先级看「紧迫度」；致命不一定最急，错别字也可能必须马上改
Q
一份好的缺陷报告包含哪些要素？
  • 标题：一句话说清「在哪、什么操作、什么问题」
  • 环境信息：操作系统、浏览器版本、App 版本、网络
  • 前置条件：需要的数据与状态（如已登录、库存为 0）
  • 复现步骤：一步一步可复现，从打开页面开始
  • 预期结果：按需求应该发生什么
  • 实际结果：实际发生了什么
  • 证据：截图、录屏、日志、抓包
  • 其他：严重度、优先级、模块、指派给谁

好标题示例：【登录】已登录用户进入支付页后点击返回，提示重新登录——要素齐全。

「标题环境加前置，步骤预期实际三件套，截图日志是铁证」
Q
常用的缺陷分析方法有哪些？🔥 高频
  • 二八原则（帕累托）：80% 缺陷集中在 20% 模块——重点分析高频模块
  • 缺陷趋势分析：按时间统计新增/关闭曲线，评估收敛态势（收敛才能上线）
  • 缺陷分布分析：按模块/阶段/类型/引入原因分布，找出薄弱环节
  • ODC 缺陷分类：按缺陷类型（功能/接口/数据/逻辑）、触发条件、影响分类，定位过程改进点
  • 根因分析（5 Why / 鱼骨图）：追到开发流程或需求层面的根因
  • 缺陷逃逸分析：线上缺陷反查为什么没被测出来，补用例防再犯
「看分布找重灾区、看趋势判收敛、看逃逸补用例」；分析的目的不是追责而是改进
Q
如何评估缺陷管理做得好不好？

从三个维度看：

  • 流程规范性：提单信息完整率、重复提单率、无效缺陷率（无效高说明测试质量差或沟通不足）
  • 处理效率：缺陷平均修复时长、平均关闭时长、长时间未处理积压数
  • 闭环质量：重开率（修一次没修好）、遗漏率、线上逃逸率

关键平衡：宁缺毋滥（信息完整可复现）与 及时闭环（催办 + 验证）并重。

管理看三率：重复率、重开率、逃逸率；数字背后是流程，流程背后是人

04接口测试

Q
什么是接口测试？主要测什么？🔥 高频

定义：直接对接口（API）发起请求并校验响应，不通过 UI 界面，主要测后端逻辑与数据。

测什么（5 类）：

  • 功能正确性：参数合法时返回是否正确
  • 参数校验：必填、类型、长度、枚举、边界值的异常处理
  • 业务逻辑：状态流转、金额计算、权限判断等核心逻辑
  • 异常与容错：参数非法、服务异常时的错误码与提示
  • 安全与性能：鉴权、越权、SQL 注入、响应时间、并发

为什么接口测试重要：接口层是业务逻辑核心，UI 变了接口不变；接口测试快、稳、能前置，发现问题比 UI 早。

接口测试 = 绕过 UI 直接验「参数、逻辑、异常、安全」；UI 会骗人，接口不会
Q
接口测试的流程是怎样的？
  1. 接口文档评审：确认路径、方法、参数、返回结构、错误码
  2. 分析接口：依赖关系、鉴权方式、数据流
  3. 用例设计：正常、边界、异常、业务场景、安全用例
  4. 选择工具：Postman / Apifox / Jmeter / 自研框架
  5. 执行与断言：校验状态码、响应体、业务字段
  6. 持续集成：接口用例接入 CI，回归自动化

接口用例要点：断言不能只查 status=200，要校验业务字段（如订单金额、状态码 message）。

「文档评审→用例设计→工具执行→断言业务→接入 CI」；200 不是通过，业务字段对才算
Q
常见的接口协议有哪些？
协议特点典型场景
HTTP/HTTPS文本协议、无状态、易调试Web/移动端 RESTful
WebSocket全双工长连接、服务端可主动推送聊天、行情、协同编辑
gRPCHTTP/2 + Protobuf 二进制、高性能强类型微服务内部调用
DubboJava RPC、注册中心 + 序列化Java 微服务集群
MQ（Kafka/RabbitMQ）异步消息、解耦削峰订单、日志、事件驱动

RPC 类接口用 grpcurl / 泛化调用测，消息类要验证消费成功与顺序。

同步用 HTTP/gRPC，异步用 MQ；协议不同，测试工具与断言方式也不同
Q
HTTP 常见状态码有哪些？🔥 高频
  • 2xx 成功：200 OK、201 Created（创建成功）、204 No Content（无返回体）
  • 3xx 重定向：301 永久重定向、302 临时重定向、304 Not Modified（缓存）
  • 4xx 客户端错误：400 参数错误、401 未认证、403 无权限、404 不存在、405 方法不允许、429 请求太频繁
  • 5xx 服务端错误：500 内部错误、502 网关错误、503 服务不可用、504 网关超时

接口测试重点：401 vs 403（没登录 vs 没权限）、429 限流、500 要查服务日志。

「2 成 3 跳 4 错 5 崩」；401 没证件、403 有证件没权限
Q
RESTful 接口设计有哪些规范？🔥 高频
  • 资源用名词复数：/users、/orders/123，不用动词
  • 方法表达动作：GET 查、POST 新增、PUT 整体更新、PATCH 部分更新、DELETE 删除
  • 状态码表达结果：200/201/204/400/404 语义化
  • 无状态：每次请求携带完整信息（token）
  • 版本化：/v1/users，兼容升级
  • 返回结构统一：如 {code, message, data}，错误信息友好
  • 过滤、排序、分页：用 query 参数（?page=1&size=10&sort=time）

测试时注意：GET 不应修改数据（幂等），POST 应做幂等性讨论。

「名词资源、动词方法、状态码表达结果」；URL 里没有动词，动词全在方法里
Q
Postman 常用的功能有哪些？🔥 高频
  • 集合（Collection）：按模块管理接口，可一键批量执行
  • 环境变量（Environment）：区分 dev/test/prod，用 {{baseUrl}} 占位
  • 全局变量与动态变量：{{$timestamp}}、{{$randomInt}} 造数据
  • 断言（Tests 脚本）：JS 校验状态码、响应体字段、token 非空
  • 前置脚本（Pre-request Script）：请求前生成签名、时间戳
  • 数据驱动：Runner 搭配 CSV/JSON 数据文件批量跑用例
  • 鉴权：支持 Bearer Token、Basic、OAuth，可配自动携带 token
  • Newman：命令行执行集合，可接入 CI
「集合管接口、变量管环境、脚本管断言、Runner 管批量、Newman 管 CI」
Q
如何处理接口之间的依赖与数据关联？

典型场景：登录后拿 token，下单需要 订单号，查询需要上一个接口的 ID。

处理方式：

  • 提取响应值：在上游接口断言中提取字段（如 token），存入环境/全局变量
  • 下游引用：下游请求参数直接写 {{token}}、{{orderId}}
  • 脚本动态提取：复杂解析（如 JSON 嵌套、正则）写在前置/后置脚本
  • 造数前置：先调用造数接口或直连数据库准备数据

注意：用例要能独立重跑——依赖数据最好用例内自造自清，避免环境污染。

「上游提取存变量，下游引用 {{变量}}」；用例自给自足，别吃别人的剩饭
Q
什么是 Mock？接口 Mock 的用途与实现方式？🔥 高频

Mock 定义：用模拟对象/服务替换真实依赖，返回预设的响应。

接口 Mock 的用途：

  • 前后端并行开发：后端没写好，前端/测试先用 Mock 联调
  • 测试异常场景：模拟超时、500、返回 null、慢响应（真实环境难造）
  • 解除依赖：第三方支付、短信、外部系统不可控时用 Mock
  • 压测隔离：把次要服务 Mock 掉，聚焦被测系统

实现方式：代码内 Mock（unittest.mock）、Mock 服务（Mockoon、WireMock、Moco）、代理抓包改响应（Charles/Fiddler 断点）、前端框架 Mock（vite-plugin-mock）。

Mock 三用途：等开发、造异常、解依赖；记住「Mock 只用于测试，别把假数据带上线」

05自动化测试

Q
什么样的项目适合做自动化测试？🔥 高频

适合自动化：

  • 需求稳定：功能不再频繁变更，脚本不会天天重写
  • 回归频繁：每次迭代都要重复测的存量功能
  • 周期长：项目长期维护，投入产出比高
  • 可脚本化：UI 稳定、有稳定 ID/属性，接口层面更好做

不适合：一次性项目、UI 频繁大改、探索性/视觉类测试、短期活动页。

常见误区：盲目追求 UI 自动化覆盖率——应该「接口自动化为主，UI 自动化覆盖关键链路」。

「需求稳、回归频、周期长」三要素；自动化不是替代手工，是解放手工做更有价值的事
Q
Selenium 的工作原理是什么？🔥 高频

架构三件套：

  • 测试脚本（Client）：用 Python/Java 等写自动化代码
  • WebDriver：浏览器厂商实现的驱动（ChromeDriver/GeckoDriver），是「翻译官」
  • 浏览器：实际执行页面操作

流程：脚本通过 WebDriver JSON Wire Protocol（HTTP 协议）发送命令 → 驱动转成浏览器原生指令执行 → 返回结果给脚本。

新版 W3C WebDriver 协议取代了旧协议，命令通过 REST API 交互。

核心要点：Selenium 不是模拟浏览器，而是调用真实浏览器，所以能完整执行 JS、渲染页面。

「脚本发指令 → 驱动翻译 → 浏览器执行」；Selenium 是遥控器，浏览器才是电视
Q
元素定位有哪些方式？优先级怎么排？🔥 高频

定位方式（8 种）：id、name、class_name、tag_name、link_text、partial_link_text、xpath、css_selector。

优先级建议：

  1. id：唯一且稳定，最快
  2. name / class_name：稳定时优先
  3. CSS Selector：如 #btn-submit、[data-testid=login]，快且灵活
  4. XPath：功能最强但慢、易碎，用于无 id/class 时

避坑：不要用绝对路径 XPath（/html/body/div[3]/...），一改版就碎；优先 相对定位 + 语义属性，推荐开发加 data-testid。

「id 第一、class 第二、CSS 兜底、XPath 最后」；定位越语义化，脚本越耐改版
Q
Selenium 三种等待方式的区别？🔥 高频
  • 强制等待（time.sleep）：固定睡 N 秒，无脑但浪费时间和不稳定——快慢机器表现不一
  • 隐式等待（implicitly_wait）：全局设置，每次 findElement 时若元素未出现则轮询等待，直到超时；不能解决元素出现但不可点击/未加载完成的问题
  • 显式等待（WebDriverWait + ExpectedConditions）：针对某个条件轮询等待，如元素可见、可点击、文本出现；最精准、最推荐

最佳实践：隐式等待兜底 + 关键操作显式等待；避免混用隐式 + 显式导致等待时间叠加。

强制是「盲等」，隐式是「全局等」，显式是「等条件」；能用显式别用 sleep
Q
什么是 Page Object 模式？有什么好处？🔥 高频

思想：把每个页面抽象成一个类，页面元素定位与操作方法封装在类里，测试用例只调方法不直接碰定位器。

分层：

  • Page 层：元素定位 + 页面操作（login_page.py 里的 input_username()、click_login()）
  • 用例层：业务流 + 断言（test_login_success 只写流程与校验）

好处：

  • 可维护性：元素变了只改一处，用例不用动
  • 可读性：用例像业务文档
  • 复用性：登录方法被 100 条用例共用
「页面变只改 Page 类，用例永远讲业务」；PO 是 UI 自动化的地基，没有 PO 的脚本迟早重写
Q
数据驱动与关键字驱动有什么区别？🔥 高频

数据驱动（Data-Driven）：测试逻辑固定，数据变化——同一套用例代码，从 Excel/CSV/JSON 读取不同测试数据批量执行（如登录 10 组账号密码）。

关键字驱动（Keyword-Driven）：把操作抽象成关键字（open、input、click、assert），用例用「关键字 + 参数」描述，像填表一样编写，业务人员也能上手。

维度数据驱动关键字驱动
变化点数据操作步骤
用例形态代码 + 数据文件关键字表格
维护者测试开发测试/业务

实践中常两者结合：关键字描述流程，数据驱动喂参数。

数据驱动「同一套代码换数据」，关键字驱动「同一张表写操作」；核心都是把变化从代码里抽出来
Q
自动化测试框架一般如何分层？

经典四层：

  • 测试用例层：业务流 + 断言，最上层
  • 业务逻辑层：封装业务操作（下单、支付、登录）
  • 页面对象层：Page Object，元素 + 页面动作
  • 基础封装层：driver 初始化、日志、报告、配置读取、公共工具

配套组件：配置文件（环境/账号）、测试数据管理（YAML/Excel）、报告与通知（Allure + 邮件/企微）、CI 集成。

「用例—业务—页面—基础」四层，上层调下层，下层不依赖上层；分层清楚才经得起长期维护
Q
用例不稳定（Flaky）怎么治理？

Flaky 定义：同一用例在相同环境下时好时坏，结果不可信，比失败更危险（让人忽视失败）。

常见原因与对策：

  • 等待问题：用显式等待替代 sleep；等待条件要精确（可点击 ≠ 可见）
  • 数据问题：用例依赖共享数据被改 → 用例自建自清数据
  • 顺序依赖：用例间有先后依赖 → 用例独立，别共享状态
  • 环境问题：网络抖动、服务重启 → 重试机制 + 环境健康检查
  • 定位不稳定：动态 id、随机文案 → 用稳定的 data-testid
  • 并发冲突：并行跑用例互相干扰 → 隔离数据与账号

治理节奏：先统计复现率定位根因，再修复；不修就禁用的用例要标注原因。

「等不准、数据脏、有依赖、定位飘」四大元凶；Flaky 用例要么修好要么下线，别让它天天骗你
Q
Selenium、Playwright、Cypress 如何选型？🔥 高频
工具优势局限
Selenium生态最成熟、支持所有浏览器/语言、社区大需自己搭等待/截图/报告，速度较慢
Playwright自动等待、多页面/多标签、截图录屏、网络拦截、跨浏览器、快较新，老团队迁移成本
Cypress开箱即用、调试体验好、实时重载、内置断言只支持 Chrome 系、运行在浏览器内（跨域受限）

选型建议：老项目浏览器矩阵广 → Selenium；新项目追求效率 → Playwright；纯前端团队 → Cypress。接口与单元测试仍建议 pytest 等通用框架。

「Selenium 是老江湖、Playwright 是新利器、Cypress 是前端宠儿」；选型看团队栈与浏览器要求

06单元测试与代码质量

Q
单元测试主要测什么？由谁写？🔥 高频

测什么：最小的可测试单元（函数/方法/类）——输入输出正确性、边界条件、异常分支、复杂逻辑（算法、计算、状态转换）。

由谁写：开发自测为主（最了解实现细节）；测试工程师主要负责设计思路、评审用例、补充关键逻辑用例、推动覆盖率达标。

好单元测试的特点：

  • 快：毫秒级，能频繁运行
  • 独立：不依赖数据库/网络/文件，可并行
  • 可重复：跑 100 次结果一样
  • 自验证：断言明确，通过/失败一目了然

FIRST 原则：Fast 快、Independent 独立、Repeatable 可重复、Self-validating 自验证、Timely 及时。

单测口诀「快独复自时」（FIRST）；写单测是在给代码买保险，不是走过场
Q
pytest 的核心功能有哪些？
  • 断言简洁：原生 assert，失败自动显示详细 diff
  • fixture：依赖注入，setup/teardown 复用，yield 实现前后置
  • 参数化：@pytest.mark.parametrize 一组数据跑多遍
  • 分组与跳过：@pytest.mark.smoke 标记分组、skip/xfail
  • conftest.py：共享 fixture 与钩子，自动发现
  • 插件生态：pytest-html/Allure 报告、pytest-xdist 并行、pytest-cov 覆盖率、pytest-mock
  • 命令行：-k 过滤、-x 失败即停、--maxfail、-q
「assert 原生、fixture 注入、parametrize 批量」三件套；pytest 是 Python 单测的事实标准
Q
Mock 与打桩（Stub）有什么区别？🔥 高频

Stub（桩）：提供预设的返回值，只回答「被调用时返回什么」，不关心怎么被调。

Mock（模拟对象）：不仅能返回预设值，还能验证调用行为——方法被调了几次、传了什么参数、调用顺序。

一句话：Stub 管「返回」，Mock 管「验证」；Mock 是 Stub 的超集。

Python 中 unittest.mock 用 patch 替换依赖，用 assert_called_once_with() 校验行为；pytest 用 pytest-mock 更顺手。

「桩只答不查，Mock 又答又查」；验证行为是 Mock 独有的超能力
Q
代码覆盖率有哪些指标？覆盖率越高越好吗？🔥 高频

指标分级：

  • 行覆盖率：被执行的代码行占比（最常用）
  • 函数/方法覆盖率：被调用的函数占比
  • 分支覆盖率：if/else、switch 分支被走到的占比（比行覆盖更严格）
  • 条件覆盖率：每个布尔子条件的真/假都被覆盖
  • 路径覆盖率：所有可能路径，最严格成本最高

不是越高越好：

  • 100% 覆盖率 ≠ 无缺陷——没断言、没测边界照样漏
  • 高覆盖背后可能是「假覆盖」（跑到了但没校验）
  • 追求边际收益：一般 行覆盖 80%+、核心逻辑分支 90%+ 是比较合理的目标
覆盖率看「行、函数、分支」三级，重点盯分支；覆盖率是手段不是目标，断言到位才算数
Q
TDD、BDD、ATDD 有什么区别？🔥 高频

TDD（测试驱动开发）：红-绿-重构循环——先写失败测试，再写代码让它通过，最后重构。针对开发实现，粒度最小。

BDD（行为驱动开发）：用自然语言描述行为（Given-When-Then 三段式），开发、测试、产品共同语言，工具如 Cucumber/Behave。

ATDD（验收测试驱动开发）：先和业务方定义验收标准（用户视角的验收测试），再开发实现。

维度TDDBDDATDD
关注点实现逻辑系统行为验收标准
语言代码业务语言业务语言
参与者开发开发+测试+产品开发+测试+产品
TDD 先写码后写码（测试先行）、BDD 讲故事（Given-When-Then）、ATDD 先立规矩（验收标准先行）
Q
JUnit 常用的注解有哪些？
  • @Test：标记测试方法
  • @BeforeEach / @AfterEach：每个用例前后执行（JUnit4 是 @Before/@After）
  • @BeforeAll / @AfterAll：整个测试类前后执行一次，必须 static
  • @ParameterizedTest：参数化测试，配合 @ValueSource、@CsvSource
  • @DisplayName：自定义用例显示名
  • @Disabled：跳过用例（相当于 @Ignore）
  • assertThrows / assertAll / assertTimeout：断言异常、聚合断言、超时断言

配套：Mockito 做 mock，AssertJ 写流畅断言，JaCoCo 统计覆盖率。

「Test 是主体，Before/After 管前后，Parametrized 喂数据」；All 类只跑一次，要 static
Q
如何提升代码的可测性？

从设计层面入手：

  • 依赖注入：对象通过构造/参数传入，而不是内部 new，便于替换 Mock
  • 单一职责：函数只做一件事，纯函数（无副作用）最好测
  • 避免静态方法/全局状态：难 Mock、用例互相污染
  • 接口抽象：依赖接口而非具体实现，测时换实现
  • 返回值优先：少用全局变量传递结果，多用返回值（好断言）
  • 错误处理显式化：异常与错误码清晰，测试好断言错误分支

可测性差的代码通常也耦合度高——提升可测性本身就是重构。

「依赖注入、单一职责、少静态、多返回」；代码好不好测，是设计问题不是测试问题

07数据库测试与 SQL

Q
测试工程师为什么要懂数据库？

原因 1：验证数据正确性——UI 上看到的只是结果，数据落库是否准确要靠 SQL 验证（金额、状态、时间戳）。

原因 2：构造测试数据——接口依赖的数据可以直连数据库造，比走流程快得多。

原因 3：清理测试数据——测试后还原环境，避免数据污染影响下次测试。

原因 4：定位缺陷——前端报错时，查库确认是数据问题、接口问题还是页面问题。

原因 5：性能与数据一致性测试——核对缓存与库的一致性、检查慢 SQL。

「验证结果、造数、清数、定位、一致性」五件事；不会 SQL 的测试只能「隔屏观花」
Q
常用 SQL 语句有哪些？
  • 查询：SELECT 字段 FROM 表 WHERE 条件 GROUP BY 字段 HAVING 条件 ORDER BY 字段 LIMIT n
  • 增：INSERT INTO 表 (字段) VALUES (...)
  • 改：UPDATE 表 SET 字段=值 WHERE 条件（必须带 WHERE）
  • 删：DELETE FROM 表 WHERE 条件；清空表 TRUNCATE；删表 DROP
  • 聚合：COUNT / SUM / AVG / MAX / MIN，配合 GROUP BY
  • 去重：SELECT DISTINCT
  • 模糊：LIKE '%关键词%'（% 任意多字符，_ 单字符）
  • 排序：ORDER BY 字段 DESC/ASC，多字段用逗号

测试必会三连：查数据 SELECT、改状态 UPDATE、统计 COUNT。

UPDATE/DELETE 三思而后行——没写 WHERE 就是删全表，测试环境也不例外
Q
内连接、左连接、右连接、全连接的区别？🔥 高频
  • INNER JOIN（内连接）：只返回两边都匹配的行
  • LEFT JOIN（左连接）：返回左表全部 + 右表匹配的行，右表无匹配则补 NULL
  • RIGHT JOIN（右连接）：返回右表全部 + 左表匹配的行，左表无匹配补 NULL
  • FULL OUTER JOIN（全连接）：返回两边的全部，无匹配补 NULL（MySQL 不支持，用 LEFT + UNION + RIGHT 模拟）

高频考题：查「没下过单的用户」→ LEFT JOIN + WHERE 订单表.ID IS NULL。

「内连接取交集，左连接左全右补空，右连接右全左补空，全连接全都要」；谁全就按谁算
Q
索引的原理是什么？哪些情况索引会失效？🔥 高频

原理：索引是有序的数据结构（MySQL InnoDB 用 B+ 树），把「全表扫描」变成「树查找」，复杂度从 O(n) 降到 O(log n)。

失效场景：

  • 对列使用函数：WHERE YEAR(create_time)=2024 → 用 create_time BETWEEN
  • 隐式类型转换：WHERE phone = 13800000000（phone 是 varchar）→ 写字符串
  • 左模糊：LIKE '%abc' 失效，LIKE 'abc%' 可用
  • OR 连接非索引列：全 OR 都走索引才行
  • 最左前缀：联合索引 (a,b,c) 必须从 a 开始，跳过 a 直接用 b 失效
  • NOT IN / <>：往往走不上索引（优化器判断全扫更优时）
「函数、隐式转换、左模糊、OR、跳最左」五杀索引；查慢先 EXPLAIN，看 type 是不是全表扫
Q
事务的 ACID 特性与隔离级别？🔥 高频

ACID：

  • 原子性（A）：全部成功或全部回滚
  • 一致性（C）：事务前后数据符合约束（余额不为负）
  • 隔离性（I）：并发事务互不干扰
  • 持久性（D）：提交后不丢失

四种隔离级别（从松到严）：

  • 读未提交：可读到未提交数据 → 脏读
  • 读已提交：解决脏读，但同查询两次结果不同 → 不可重复读（Oracle 默认）
  • 可重复读：解决不可重复读，但可能有幻读（MySQL 默认，MVCC + 间隙锁解决）
  • 串行化：全部串行，最安全最慢
ACID 记「原一持隔」；隔离级别从松到严记「读未、读已、可重、串行」，越严越慢
Q
数据库锁有哪些？什么是死锁？

按粒度：表锁（锁整表，开销小并发差）、行锁（锁单行，并发好，InnoDB 支持）、页锁。

按性质：

  • 共享锁（S 锁/读锁）：多个事务可同时读，不可写
  • 排他锁（X 锁/写锁）：独占，其他事务不可读写
  • 意向锁：表级标记，告诉别人「表里某行被锁了」

死锁：两个事务互相持有对方需要的锁，互相等待不释放。解决：按固定顺序加锁、缩短事务、超时回滚（innodb_lock_wait_timeout）、死锁检测。

「读加 S、写加 X、防死锁按序加」；测试时并发写同一条数据最容易触发死锁
Q
测试数据如何构造与管理？🔥 高频

构造方式：

  • 接口造数：走业务接口创建（最真实，推荐）
  • SQL 造数：直连库 INSERT/UPDATE（快，适合批量与状态机数据）
  • 造数工具/脚本：Faker 生成随机数据、数据工厂、复制生产脱敏数据
  • 备份还原：从生产脱敏后导入测试库

管理要点：

  • 数据隔离：测试数据打标（如手机号前缀 199 测试号），避免误触生产
  • 自建自清：用例用完删除，保持环境干净可重复
  • 数据版本化：复杂场景数据入库保存，便于复现
  • 脱敏合规：用户真实数据必须脱敏，个保法要求
「能走接口走接口，批量场景用 SQL，敏感数据必脱敏」；数据要自给自足、用完即清
Q
如何做数据库数据一致性校验？🔥 高频

场景：页面显示、接口返回、数据库落库三方数据必须一致。

校验方法：

  • 接口响应 vs 库表：请求接口后，SQL 查库比对字段（金额、状态、数量）
  • 多表一致性：主表与从表（订单表 vs 订单明细表）金额合计是否相等
  • 缓存一致性：Redis 缓存与 DB 是否一致（改库后缓存是否更新）
  • 上下游一致性：下单后 MQ 消息、库存扣减、流水记录是否对得上
  • 对账：日终对账脚本核对总账与明细

技巧：先记「操作前快照」，操作后对比差异；金额类用 SUM 与明细交叉验证。

「页面、接口、数据库三方对齐；主表明细对得上、缓存库表不打架」

08性能测试

Q
性能测试有哪些类型？🔥 高频
  • 负载测试：在预期压力下看系统表现，验证能否满足目标（最常用）
  • 压力测试：不断加压直到崩溃点/拐点，找到系统上限
  • 并发测试：多个用户同时操作，验证并发正确性（不超卖、数据不错乱）
  • 稳定性测试（疲劳测试）：长时间（如 7×24 小时）中高压运行，发现内存泄漏、连接泄漏
  • 容量测试：在可接受性能下系统能支撑的最大业务量（用户数/数据量）
  • 尖峰测试：瞬间流量激增（秒杀、双 11）系统是否扛得住
「负载看达标、压力找上限、并发查错乱、稳定抓泄漏、容量算支撑、尖峰抗突发」
Q
性能测试的核心指标有哪些？🔥 高频
  • 响应时间：请求发出到收到响应的时间，常用 RT（平均）与 TP95/TP99（95%/99% 请求在多少毫秒内完成，比平均更能反映体验）
  • 吞吐量：TPS（每秒事务数）、QPS（每秒查询数）、RPS（每秒请求数）
  • 并发数：同时处理的请求/用户数
  • 错误率：失败请求占比，一般要求 < 0.1%
  • 资源利用率：CPU、内存、磁盘 IO、网络带宽（一般 CPU < 70%、内存无持续增长）
  • 其他：GC 频率与停顿、连接池使用率、数据库慢查询数

注意：并发不是压出来的数字，而是由 TPS × 平均响应时间推算（并发 ≈ TPS × RT）。

「响应看 TP99、吞吐看 TPS、质量看错误率、资源看 CPU」；并发数 = TPS × 平均响应时间
Q
用 JMeter 做性能测试的基本流程？🔥 高频
  1. 创建测试计划：添加 线程组（设置线程数、Ramp-Up 启动时间、循环次数）
  2. 配置请求：HTTP 请求（路径、参数、Header）、HTTP Cookie 管理器
  3. 添加参数化：CSV 数据文件驱动不同账号/参数
  4. 添加断言：响应断言校验 200 与业务字段
  5. 添加监听器：聚合报告（TPS/RT/错误率）、结果树、TPS 曲线
  6. 运行与分析：逐步加压，观察拐点
  7. 监控服务器：配合 ServerAgent/PerfMon 看 CPU 内存

常用：阶梯加压（Ultimate Thread Group）找拐点；分布式压测（Master-Slave）解决单机瓶颈；CLI 模式 jmeter -n -t 脚本.jmx -l 结果.jtl 正式执行。

「线程组压人、断言验对、聚合看数据、PerfMon 看资源」；正式压测别开 GUI，用 CLI 模式
Q
性能测试场景如何设计？

场景来源：业务量预估（日活 × 平均请求数 × 峰值系数）、线上历史流量、目标 SLA。

经典场景：

  • 单接口基准测试：单用户、小并发，看基础性能
  • 核心链路混合场景：按真实占比混跑（登录 5%、查询 60%、下单 15%…）
  • 峰值加压：从低并发阶梯升到预估峰值，找拐点
  • 稳定性场景：峰值 80% 压力跑 4~8 小时
  • 异常场景：缓存失效、依赖服务抖动时的表现

设计要点：压测数据要与线上特征一致（数据量、分布、热点），否则结果失真。

「基准→混合→峰值→稳定→异常」五场景；数据不像线上，结果不可信
Q
如何定位性能瓶颈？🔥 高频

定位思路：分层排查，自底向上：

  1. 看监控数据：CPU、内存、磁盘、网络、GC——先定资源层
  2. 看应用层：慢日志（如 Nginx access log、应用 trace）、线程栈（jstack 找卡点）、连接池状态
  3. 看数据库：慢 SQL（show processlist + 慢查询日志）、锁等待、连接数打满
  4. 看中间件：Redis 命中率、MQ 积压、缓存穿透/雪崩
  5. 看外部依赖：第三方接口慢、DNS 解析慢

常用工具：Arthas（线上诊断）、JProfiler/VisualVM（Java）、top/vmstat/iostat（系统）、慢查询分析工具。

常见瓶颈分布：数据库（SQL/锁/连接）> 应用线程 > 外部依赖。

「先资源后应用再数据库，一层一层剥洋葱」；瓶颈八成在数据库，先查慢 SQL
Q
数据库常见的性能问题有哪些？
  • 慢 SQL：缺索引、索引失效、大表全扫、深分页（LIMIT 100000,20）
  • 连接数打满：连接池配置过小或连接泄漏，应用报「too many connections」
  • 锁竞争：大量写同一条数据，行锁排队；间隙锁扩大锁范围
  • 缓存穿透/击穿/雪崩：查不存在数据打库（穿透）、热点 key 过期（击穿）、大量 key 同时过期（雪崩）
  • 大事务：长事务持有锁时间长，阻塞其他事务
  • 主从延迟：读写分离下从库跟不上，读到旧数据

测试视角：压测时观察DB 侧指标（连接数、慢查询数、锁等待时长），配合应用侧 TPS 下降拐点定位。

「慢 SQL、连接满、锁竞争、缓存三兄弟」四大坑；压测必配 DB 监控
Q
常见的性能优化手段有哪些？🔥 高频
  • 缓存：Redis 缓存热点数据，减少 DB 压力（注意一致性）
  • 异步化：非核心操作走 MQ 异步（发短信、写日志、扣积分），削峰填谷
  • 数据库优化：加索引、优化 SQL、分库分表、读写分离、连接池调优
  • 代码层：减少循环内查库（N+1）、批量操作、对象复用、避免大对象
  • 并发与限流：线程池合理配置、限流（令牌桶）保护下游、熔断降级
  • 静态资源优化：CDN、压缩、懒加载、HTTP 缓存
  • 架构层：负载均衡、水平扩容、多级缓存（本地 + Redis）

优化顺序：先改代码与 SQL（零成本），再上缓存，最后扩容。

「缓存扛读、异步扛峰、SQL 扛底、限流护体」；能用代码解决别急着加机器
Q
容量规划怎么做？

目标：回答「什么配置下能支撑多大的业务量」，为扩容与采购提供依据。

步骤：

  1. 预估业务量：日活、峰值 QPS、数据量增长（如双 11 的 5 倍峰值）
  2. 压测单机能力：单台应用/单库能扛多少 TPS、多少数据量
  3. 推算资源：节点数 = 峰值总量 / 单机能力 × 冗余系数（如 1.5 倍）
  4. 留余量：CPU 不超 70%、内存不超 80%，预留故障转移能力
  5. 验证与监控：扩到目标后回归压测，上线后监控持续校准
「先估业务量，再测单机力，乘上冗余系数就是答案」；容量规划是估算不是精确值，要留缓冲
Q
性能测试报告包含哪些内容？
  • 测试概述：目的、范围、时间、环境（硬件/软件/网络拓扑）
  • 测试模型：业务占比、场景设计、数据量说明
  • 执行结果：各场景的 TPS、RT（平均/TP95/TP99）、错误率、并发数
  • 资源数据：CPU、内存、磁盘、网络的趋势与峰值
  • 瓶颈分析：发现的瓶颈点与定位过程（慢 SQL、线程等）
  • 结论与建议：是否达标、风险点、优化建议、上线放行建议

好的报告要能回答三个问题：达没达标、瓶颈在哪、能不能上线。

「环境模型结果分析结论」五段式；报告不是数据堆砌，是要给出上线结论

09移动端与专项测试

Q
移动端测试需要关注哪些点？🔥 高频

除功能测试外，移动端独有专项：

  • 兼容性：Android/iOS 版本、机型分辨率、刘海屏/折叠屏
  • 网络：弱网（2G/3G/4G/5G/WiFi）、断网重连、弱网下的超时提示
  • 中断测试：来电、短信、通知、锁屏、切后台、横竖屏切换
  • 资源专项：耗电量、内存占用与泄漏、流量消耗、发热
  • 安装升级：首次安装、覆盖安装、卸载、升级（数据保留）
  • 权限：相机/定位/通讯录授权、拒绝授权后的表现
  • 安全：本地存储加密、越权、重放攻击、防调试
  • 体验：启动速度、卡顿、ANR 闪退、手势操作
「兼容网络中断资源，安装权限安全体验」八专项；移动端一半的坑在「环境」不在「功能」
Q
App 测试与 Web 测试有什么区别？🔥 高频
维度Web 测试App 测试
环境浏览器 + 系统机型 + 系统版本 + 网络环境，组合爆炸
安装升级刷新即生效安装/覆盖安装/升级/卸载
专项浏览器兼容弱网、中断、耗电、推送、手势
工具Selenium、浏览器 DevToolsadb、Appium、抓包（Charles）、Monkey
发布灰度上线、随时回滚应用商店审核、版本回滚难

共同点：后端接口、业务逻辑、数据一致性测试几乎一样——这也是「接口自动化优先」的原因。

「Web 看浏览器，App 看机型网络中断」；App 多出来的全是环境测试
Q
adb 常用命令有哪些？🔥 高频
  • adb devices：查看连接的设备
  • adb install / uninstall 包名：安装 / 卸载应用
  • adb shell am start -n 包名/Activity：启动指定页面
  • adb shell am force-stop 包名：强制停止
  • adb logcat：查看日志（-s Tag 过滤，| grep 关键字）
  • adb shell dumpsys meminfo 包名：查看内存
  • adb shell dumpsys battery：电池状态
  • adb shell screencap /sdcard/x.png + adb pull：截图
  • adb shell input keyevent 4：模拟返回键（其他：3 Home、26 电源）
  • adb shell wm size：查看分辨率；adb reverse 端口转发
「装看 logcat，测看 meminfo，截图 screencap，操作 input」；adb 是安卓测试的瑞士军刀
Q
Monkey 测试是什么？

定义：Android 自带的随机事件压力工具，向 App 随机发送点击、滑动、按键等事件，用于稳定性测试——找崩溃、ANR、内存泄漏。

常用命令：

              
              # 发送 5000 个随机事件，包名限定被测应用
adb shell monkey -p com.example.app 5000

# 指定事件间隔与 seed（可复现）
adb shell monkey -p com.example.app --throttle 300 -s 12345 5000

# 限制点击类事件比例，忽略崩溃继续跑
adb shell monkey -p com.example.app --pct-touch 50 --ignore-crashes 10000

产出物：Monkey 日志（找 crash 堆栈）、崩溃现场截图/日志。Monkey 是「暴力测试」，用例不可控，配合 Appium 等可控自动化互补。

Monkey 是「乱拳打死老师傅」，专门打崩溃；随机测试 + seed 可复现是关键
Q
弱网测试怎么做？🔥 高频

测什么：弱网/断网下的提示友好性（加载中、重试按钮）、数据一致性（半途失败不能脏数据）、恢复能力（网络恢复后自动重试/续传）、超时策略（请求超时时间与重试次数）。

模拟方式：

  • Charles/Fiddler：Throttle 设置限速（3G 模板：几百 KB/s）、断点控制请求时机
  • 系统弱网：Android 开发者选项「网络限速」、iOS 网络链路调节器
  • 微信「真机调试」弱网模式：小程序弱网场景
  • 自建代理：tc（Linux 流量控制）脚本模拟丢包、延迟、抖动

典型用例：弱网下单重复提交 → 是否重复扣款；弱网加载一半断网 → 页面是否有兜底。

弱网三必测：提示友好、数据不脏、恢复能续；「断网一瞬间」永远是好用的测试场景
Q
兼容性测试怎么做？🔥 高频

覆盖维度：

  • 操作系统：Android（主流版本 8-15）、iOS（当前两个大版本 + 历史版本）
  • 机型/厂商：华为、小米、OPPO、vivo、苹果、三星；关注屏幕尺寸与刘海/挖孔/折叠屏
  • 分辨率/DPI：小屏 720p、主流 1080p、2K；布局是否错乱
  • 浏览器/Webview：Chrome、Safari、微信内置浏览器
  • 系统特色：iOS 的深色模式、Android 的分屏、返回手势

做法：先按用户分布数据确定优先级矩阵（Top 机型 + Top 系统版本），用真机 + 云测平台（腾讯云测、Testin）组合，自动化脚本批量跑冒烟，重点问题真机复现。

「按分布定矩阵、云测跑批量、真机复现重点」；不要全机型，要按用户占比排优先级
Q
中断测试与交叉事件测试是什么？

中断测试：App 运行中被外部事件打断，验证状态保持与恢复：

  • 来电、短信、通知栏消息
  • 锁屏 / 解锁、切后台 / 回前台（数据是否丢失、页面状态是否保留）
  • 横竖屏切换（布局、输入内容、视频播放是否正常）
  • 低电量提醒、充电 / 拔电

交叉事件：多个事件同时发生（来电 + 切后台、推送 + 支付中），验证不崩溃不丢数据。

典型用例：输入一半来电话 → 挂断后输入内容是否还在；播放视频时锁屏 → 声音是否停止。

「打断不丢状态、恢复能续上」；来电锁屏切换，App 的「记忆」全靠中断测试验
Q
埋点测试怎么测？

埋点定义：在 App/页面中埋入统计代码，上报用户行为（曝光、点击、浏览时长）供数据团队分析。

测试要点：

  • 触发时机：在正确的时机触发（进入页面即曝光、点击按钮才上报）
  • 字段正确性：事件名、页面名、参数（商品 id、来源渠道）与埋点文档一致
  • 次数准确：只触发一次 vs 多次（避免重复点击重复上报）
  • 上报通道：数据是否到达服务端（抓包验证请求，查数据后台/日志）
  • 边界场景：杀掉进程、弱网、快速滑动时埋点是否丢失或重复

工具：Charles 抓包看上报请求、adb logcat 过滤 SDK 日志、数据后台查数。

埋点三查：时机对不对、字段全不全、次数准不准；「用户每点一下，后台都要有数」

Q
SQL 注入的原理与防御？🔥 高频

原理：用户输入被拼接到 SQL 语句中执行，输入中的引号/关键字改变了 SQL 语义。如：

              
              # 用户输入 1' OR '1'='1 时拼接成：
SELECT * FROM users WHERE id = '1' OR '1'='1'

测试用例：单引号 '、1' OR '1'='1、注释 --、报错注入 ' AND extractvalue(...)、布尔盲注 1 AND 1=1 / 1 AND 1=2、时间盲注 SLEEP(5)。

防御：

  • 参数化查询（PreparedStatement）：输入只当数据不当代码（首选）
  • 输入校验：白名单校验类型与长度
  • 最小权限：DB 账号不授予 DROP 等高危权限
  • 错误信息脱敏：不把 SQL 报错直接返回给用户
「参数化打底、白名单加固、最小权限兜底」；注入本质是「数据当代码执行」
Q
XSS 有哪几种类型？如何防御？🔥 高频

XSS（跨站脚本）：把恶意 <script> 注入页面，在用户浏览器执行，偷 Cookie、钓鱼、篡改页面。

  • 反射型：恶意脚本拼在 URL 参数中，服务端原样返回——需要诱导用户点击链接
  • 存储型：恶意脚本存到数据库，所有访问页面的人都被攻击（评论、昵称）——危害最大
  • DOM 型：纯前端漏洞，JS 读 URL/本地数据后直接插入 DOM 执行

防御：输出编码（转义 < > " '）、输入校验、CSP（内容安全策略）、HttpOnly Cookie（防偷 Cookie）、过滤危险标签。

「反射骗一次、存储害一片、DOM 纯前端」；防御三板斧：输出编码 + HttpOnly + CSP
Q
CSRF 攻击的原理与防御？

原理：用户已登录站点 A（浏览器有 A 的 Cookie），攻击者诱导用户访问恶意页面 B，B 中隐藏表单/图片自动向 A 发请求——浏览器自动携带 Cookie，服务端误以为是用户本人操作。

典型场景：诱导用户点击链接触发「转账」「改密码」等敏感操作。

防御：

  • CSRF Token：请求携带服务端下发的随机 token，第三方页面拿不到（主流）
  • SameSite Cookie：Cookie 标记 SameSite=Strict/Lax，跨站请求不带 Cookie
  • 校验 Referer/Origin：判断请求来源域名
  • 敏感操作二次校验：验证码、短信验证

与 XSS 区别：XSS 偷 Cookie 冒充你，CSRF 借你的 Cookie 自动发请求。

「CSRF 是借刀杀人，Token 断刀、SameSite 锁刀、Referer 验刀」；敏感操作必上二次校验
Q
文件上传漏洞如何测试与防护？

漏洞原理：上传功能未校验文件内容，攻击者上传 WebShell（如 .php/.jsp 一句话木马）获得服务器执行权限。

测试方法（绕过思路）：

  • 改扩展名：shell.php.jpg、shell.php5、大小写 .PhP、双写 .pphphp
  • 改 Content-Type 为合法类型；抓包改名上传
  • 文件头伪造（GIF89a 图片头 + 恶意代码）绕过内容校验
  • 上传 .html 存 XSS、.svg 存脚本、超大文件测限制

防护：白名单扩展名 + 校验文件头 + 重命名存储（随机名）+ 目录不可执行 + 单独静态域名 + 杀毒扫描。

「白名单扩展名、校验真实内容、随机重命名、目录禁执行」；上传检测要查「里面是什么」而不是「名字叫什么」
Q
越权测试怎么做？🔥 高频

越权类型：

  • 水平越权：普通用户 A 访问普通用户 B 的资源（改 URL 中 id 看别人的订单）
  • 垂直越权：低权限用户调用高权限接口（普通用户调管理员删除接口）

测试方法：

  1. 登录普通账号 A，抓取接口（如 /order/1001）
  2. 换登录账号 B，重放同样的请求（或改 id），看能否访问
  3. 测试直接调用管理接口（改方法、加参数、试目录）看是否校验权限
  4. 关注服务端校验：前端隐藏按钮不算防护，必须服务端鉴权

防护：服务端对每个资源做属主校验 + RBAC 权限校验，接口不信任前端传的 id。

「水平换 id 看别人，垂直小号调大号」；防护就一句：服务端必须自己校验，别信前端
Q
常见的安全测试工具与用法？
  • Burp Suite：抓包改包神器——代理拦截、Repeater 重放、Intruder 爆破、扫描器
  • sqlmap：自动化 SQL 注入检测与利用（sqlmap -u "url?id=1" --batch）
  • Nmap：端口与服务扫描（nmap -sV -p- 目标）
  • xray / AWVS / AppScan：Web 漏洞扫描器
  • fiddler/Charles：抓包与改包（客户端为主）
  • dirsearch：目录扫描；hydra：口令爆破；nuclei：漏洞模板扫描
  • 移动端：drozer（Android 安全）、MobSF（静态分析）

测试注意：扫描器会产生流量与破坏性操作，需授权、在测试环境执行。

「Burp 抓改、sqlmap 打注入、Nmap 探端口、扫描器兜底」；安全测试记得先授权

Q
什么是 CI、CD、DevOps？测试如何融入？🔥 高频
  • CI（持续集成）：代码频繁合并到主干，每次提交自动构建 + 跑自动化测试，尽早发现问题
  • CD（持续交付/部署）：持续交付 = 随时可发布；持续部署 = 通过测试自动上线
  • DevOps：开发与运维协作的文化 + 自动化流程，目标是「快速、可靠、可回溯地发布」

测试的融入：

  • 提交触发：单元测试 + 静态检查（秒级反馈）
  • 合入触发：接口测试 + 关键 UI 冒烟
  • 发布前：全量回归 + 性能冒烟 + 安全扫描
  • 发布后：线上监控 + 生产验证（测试右移）
「CI 把测试变成流水线的一环，测试要跑在每一次提交里」；测试不是卡点，是质量流水线
Q
Jenkins 流水线是怎么组织的？

触发方式：代码提交（GitHub/GitLab webhook）、定时（Build Periodically）、手动、参数化触发。

经典阶段：

  • 拉取代码 → 构建（mvn/npm build）→ 单元测试 → 静态检查（SonarQube）→ 打包 → 部署到测试环境 → 接口/UI 自动化 → 质量门禁 → 生成报告与通知

Pipeline 两种写法：自由风格（界面配置，简单）与 Jenkinsfile（代码即流水线，推荐）——放进代码库可版本管理、可评审。

              
              pipeline {
  agent any
  stages {
    stage('Build')   { steps { sh 'mvn clean package' } }
    stage('Test')    { steps { sh 'mvn test' } }
    stage('Deploy')  { steps { sh 'deploy.sh' } }
  }
}
「触发—构建—测试—部署—门禁」五阶段；Jenkinsfile 是流水线的「乐谱」，代码化可评审可回溯
Q
Docker 在测试中有哪些应用？🔥 高频
  • 测试环境标准化：镜像即环境，避免「在我机器上是好的」——环境与代码一起交付
  • 一键起依赖：docker-compose up 拉起 MySQL/Redis/MQ，本地与 CI 环境一致
  • CI 隔离执行：每个流水线任务在独立容器里跑，互不污染，用完即毁
  • 测试数据容器：用临时数据库容器跑测试，快且干净（docker run --rm mysql）
  • 并行测试：多容器并行跑不同浏览器/环境（Selenium Grid + Docker）
  • 部署一致性：测试环境跑的就是生产同款镜像，发布风险小

注意：容器是进程级隔离不是虚拟机；测试要关注镜像版本管理与资源限制。

「镜像即环境、容器即隔离」；Docker 解决了测试最大的痛——环境不一致
Q
测试环境如何管理？环境不够用怎么办？🔥 高频

环境分级：开发环境（自测）→ 测试环境（功能测试）→ 预发布环境（验收/回归，接近生产）→ 生产。

管理要点：

  • 环境隔离：数据、配置、域名相互独立，测试数据不污染生产
  • 一键部署：脚本/CI 自动部署，避免手工配置漂移
  • 环境监控与健康检查：服务状态、接口可用性自动化巡检
  • 变更通知：环境发布/回滚要通知测试，避免「测到一半环境变了」

环境不够用：按优先级排队 + 容器化动态环境（每迭代/每分支拉起一套 Docker 环境，用完即回收）+ 环境预约制度。

「分级隔离、一键部署、动态分配」；环境是测试的战场，战场乱了仗没法打
Q
蓝绿发布与金丝雀发布是什么？
  • 蓝绿发布：准备两套完全相同的环境（蓝 + 绿），新版本部署到空闲的那套，验证通过后流量整体切换，出问题一键回滚到旧环境
  • 金丝雀发布（灰度发布）：新版本先让一小部分用户/流量使用，观察指标没问题再逐步放量到 100%

区别：蓝绿是「整池切换」，金丝雀是「渐进放量」；金丝雀更平滑，蓝绿回滚更快。

测试视角：灰度期间要监控错误率与关键指标，配置自动化回滚条件；灰度用户的数据隔离要设计好。

「蓝绿换池子、金丝雀放水」；发布越平滑，测试右移越重要
Q
什么是质量门禁？一般设置哪些？🔥 高频

定义：流水线中的自动检查关卡，不满足条件就阻断发布，把质量要求「硬编码」进流程。

常见门禁：

  • 单元测试通过率：全部通过（或失败率 < 阈值）
  • 代码覆盖率：新增代码行覆盖 ≥ 80%
  • 静态检查：SonarQube 阻断级别问题为 0
  • 接口测试通过率：核心用例 100% 通过
  • 性能基线：关键接口 RT/TP99 不超过基线
  • 安全扫描：高危漏洞为 0，依赖漏洞不新增

设计原则：门禁要「少而硬」——只拦真正影响发布的红线，太多门禁会让流程寸步难行、被手动绕过。

「单测覆盖静态扫，接口性能安全扫」；门禁贵在坚持，软门禁等于没门禁
Q
测试环境问题怎么排查？

分层排查：

  1. 服务是否在跑：进程、容器状态（docker ps）、端口监听（netstat）
  2. 服务是否健康：健康检查接口、启动日志有没有报错（连接 DB 失败、配置缺失）
  3. 网络与配置：域名解析、网关转发、环境变量/配置中心是否指向本环境
  4. 数据是否就绪：依赖的初始化数据、造数脚本是否执行
  5. 依赖服务：MySQL/Redis/MQ 是否可达、是否被其他任务占用
  6. 最近变更：刚部署/回滚了什么、配置中心最近改了什么——查变更记录最快

万能起点：看日志 + 看最近变更；排查要「先环境后代码」。

「先看活没活、再看日志错没错、最后查最近改没改」；环境问题八成是变更引起的

12测试场景与逻辑题

Q
如何测试一个登录功能？🔥 高频

按「功能-安全-异常-体验」四维度展开：

功能：

  • 正确账号密码登录成功；空账号/空密码/两者皆空的提示

              # 迭代法（推荐，O(n) 时间 O(1) 空间）
def fib_iter(n):
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a

# 递归法（有重复计算，需记忆化）
def fib_recur(n, memo=None):
    if memo is None:
        memo = {}
    if n in memo:
        return memo[n]
    if n <= 1:
        return n
    memo[n] = fib_recur(n-1, memo) + fib_recur(n-2, memo)
    return memo[n]

# 生成器版本
def fib_gen(n):
    a, b = 0, 1
    for _ in range(n):
        yield a
        a, b = b, a + b

assert fib_iter(10) == 55
assert fib_recur(10) == 55
assert list(fib_gen(10))[-1] == 55
迭代是「滚动赋值 a,b = b,a+b」；递归必配 memo，否则指数级爆炸

              def is_palindrome(s: str) -> bool:
    """忽略大小写与空白，判断是否回文"""
    # 清洗：保留字母数字，转小写
    clean = ''.join(ch.lower() for ch in s if ch.isalnum())
    # 双指针从两端向中间比较
    left, right = 0, len(clean) - 1
    while left < right:
        if clean[left] != clean[right]:
            return False
        left += 1
        right -= 1
    return True

# 简洁写法：反转比较
def is_palindrome_simple(s: str) -> bool:
    clean = ''.join(ch.lower() for ch in s if ch.isalnum())
    return clean == clean[::-1]

assert is_palindrome("A man, a plan, a canal: Panama") is True
assert is_palindrome("race a car") is False

              def merge_sorted(nums1, m, nums2, n):
    """把 nums2 合并进 nums1（nums1 尾部预留 n 个空位）"""
    # 从后往前填，避免移动元素
    i, j, k = m - 1, n - 1, m + n - 1
    while j >= 0:
        if i >= 0 and nums1[i] > nums2[j]:
            nums1[k] = nums1[i]
            i -= 1
        else:
            nums1[k] = nums2[j]
            j -= 1
        k -= 1
    return nums1

nums1 = [1, 2, 3, 0, 0, 0]
assert merge_sorted(nums1, 3, [2, 5, 6], 3) == [1, 2, 2, 3, 5, 6]

要点：从尾部向前归并，谁大谁放最后，天然避免覆盖。

SELECT user_id,
       COUNT(*)                    AS order_cnt,
       SUM(amount)                 AS total_amount
FROM orders
GROUP BY user_id;

FROM orders
WHERE status = 'PAID'

SELECT user_id, amount
FROM (
    SELECT user_id, amount,
           ROW_NUMBER() OVER (
               PARTITION BY user_id ORDER BY amount DESC
           ) AS rn
    FROM orders
    WHERE status = 'PAID'
) t
WHERE rn <= 3;

              import re
from collections import Counter

def top_words(filename, k=10):
    with open(filename, encoding='utf-8') as f:
        text = f.read()
    # 用正则提取单词（忽略大小写）
    words = re.findall(r"[a-zA-Z']+", text.lower())
    # Counter 一行统计词频
    return Counter(words).most_common(k)

def top_words_manual(words, k=10):
    """不用 Counter 的手写版"""
    freq = {}
    for w in words:
        freq[w] = freq.get(w, 0) + 1
    # 按词频降序排序
    return sorted(freq.items(), key=lambda x: -x[1])[:k]

words = ["a", "b", "a", "c", "a", "b"]
assert top_words_manual(words, 2) == [("a", 3), ("b", 2)]
print("词频统计 OK")

要点：Counter.most_common(k) 是标准答案；手写版体现对 dict.get 与排序的理解。

「正则分词 + Counter 统计 + most_common 取 TopK」三行搞定
