01 内网穿透概述

1.1 什么是内网穿透

内网穿透（NAT Traversal / Intranet Penetration）是一种让外网设备能够访问处于内网（局域网）中的服务的技术。

简单来说：你家里的电脑跑了一个网站，但因为没有公网 IP，外面的人无法直接访问。内网穿透就是在公网服务器和你家里的电脑之间建立一条"隧道"，让外网流量通过这条隧道到达你的内网服务。

外网用户 → 公网服务器(中转) ←→ 隧道 ←→ 你的内网电脑(服务)

1.2 为什么需要内网穿透

  • 远程访问家庭设备：NAS、智能家居、开发服务器、树莓派
  • 本地开发调试：微信/支付宝回调、Webhook、第三方 API 联调
  • 演示本地项目：给客户看还没上线的网站/小程序
  • 远程桌面/SSH：在公司连家里电脑，或反向访问
  • 游戏联机：Minecraft、自建私服等
  • 物联网：让部署在现场的设备能被云端管理
  • 临时文件共享：把本地文件快速分享给别人下载

1.3 核心术语

术语说明
NAT网络地址转换，路由器把内网私有 IP 映射为公网 IP
FRPFast Reverse Proxy，最流行的开源内网穿透工具
隧道（Tunnel）公网服务器与内网客户端之间建立的加密连接
中转/中继流量经过公网服务器转发（与 P2P 直连相对）
打洞（Punching）NAT 穿透技术，让两台内网设备直接通信
反向代理代理服务器接收外部请求，转发给内部服务
VPS虚拟专用服务器，有公网 IP，用作中转节点

1.4 内网穿透 vs 其他技术

技术区别
端口映射（端口转发）在路由器上配置，需公网 IP；是最简单的"穿透"，但运营商通常不给公网 IP
VPN把设备加入同一个虚拟局域网，可互相访问；但配置较复杂，适合多设备组网
DDNS动态域名解析，解决公网 IP 变化问题；前提是你有公网 IP
内网穿透不需要公网 IP，通过公网中转服务器建立隧道；最通用
判断你有没有公网 IP：在路由器管理页查看 WAN 口 IP，如果是 10.x、172.16-31.x、192.168.x 开头，说明是运营商内网 IP（CGNAT），需要内网穿透。如果 WAN 口 IP 和你在 ip138.com 看到的 IP 一致，说明你有公网 IP。

02 网络基础与 NAT 原理

2.1 OSI 七层模型与 TCP/IP 四层

OSI 层TCP/IP 层典型协议/设备
应用层应用层HTTP、HTTPS、SSH、FTP、DNS
表示层SSL/TLS、JPEG
会话层RPC、SOCKS
传输层传输层TCP、UDP
网络层网络层IP、ICMP、路由器
数据链路层网络接口层Ethernet、ARP、交换机
物理层网线、光纤、WiFi

2.2 TCP 三次握手与四次挥手

三次握手（建立连接）

客户端 → SYN → 服务端
客户端 ← SYN+ACK ← 服务端
客户端 → ACK → 服务端
连接建立
  • SYN：请求同步
  • ACK：确认
  • 三次是为了双向确认收发能力正常

四次挥手（断开连接）

客户端 → FIN → 服务端
客户端 ← ACK ← 服务端     （服务端可能还有数据要发）
客户端 ← FIN ← 服务端
客户端 → ACK → 服务端
连接断开

四次是因为 TCP 全双工，两个方向要分别关闭，被动方可能需要时间处理剩余数据。

2.3 NAT 原理

NAT（Network Address Translation，网络地址转换）由路由器实现，让多台设备共用一个公网 IP 上网。

NAPT（端口地址转换）流程

内网电脑 192.168.1.100:5000 访问外网 1.2.3.4:80

路由器 NAT 表：
┌──────────────────────────┬─────────────────────────┐
│ 内网地址:端口             │ 公网映射地址:端口        │
├──────────────────────────┼─────────────────────────┤
│ 192.168.1.100:5000      │ 公网IP:50001           │
└──────────────────────────┴─────────────────────────┘

外网返回数据 → 公网IP:50001 → 查NAT表 → 转发到 192.168.1.100:5000
问题在于：NAT 表项是由内网主动发起连接时才创建的。外网主动发起的连接，路由器 NAT 表中没有对应记录，不知道转发给谁，直接丢弃。这就是为什么内网服务无法被外网直接访问。

2.4 NAT 的四种类型

类型特点P2P 打洞难度
Full Cone（全锥形）一旦内网地址:端口映射到公网地址:端口，任何外网主机都能通过该公网地址:端口访问最容易
Restricted Cone（限制锥形）外网主机必须先被内网主机访问过（IP 匹配），才能反向访问可以打洞
Port Restricted Cone（端口限制锥形）IP+端口都必须匹配可以打洞
Symmetric NAT（对称型）每个不同目标映射不同端口，端口不可预测很难/几乎不能 P2P
运营商级 NAT（CGNAT）通常是 Symmetric 或 Port Restricted Cone，这也是为什么家用宽带越来越难 P2P 打洞。FRP 这类中转方案不依赖 NAT 类型，所以更可靠。

2.5 TCP vs UDP

TCPUDP
连接面向连接（三次握手）无连接
可靠性可靠传输、重传、有序不保证可靠
速度较慢快
头部开销20+ 字节8 字节
适用Web、SSH、文件传输DNS、视频、游戏、打洞

03 公网、内网与 IP 地址

3.1 IP 地址分类

公网 IP（Public IP）

由 ISP（运营商）分配，全球唯一，可在互联网上直接路由。

私有 IP（Private IP）

以下三段保留给内网使用，不能在公网上路由：

10.0.0.0    ~ 10.255.255.255    (10/8)
172.16.0.0  ~ 172.31.255.255    (172.16/12)
192.168.0.0 ~ 192.168.255.255  (192.168/16)

特殊地址

  • 127.0.0.1 / localhost：本机回环地址
  • 0.0.0.0：监听所有网卡（包括外网和内网）
  • 169.254.x.x：DHCP 失败时自动分配（链路本地地址）
  • 224.x.x.x：组播地址

3.2 IPv4 与 IPv6

  • IPv4：32 位，约 43 亿地址，已耗尽；靠 NAT 续命
  • IPv6：128 位，地址近乎无限；每个设备可直接获得公网 IPv6 地址
  • 如果运营商分配了 IPv6，且目标设备和客户端都有 IPv6，理论上不需要内网穿透，直接通过 IPv6 访问
  • 但 IPv6 也有防火墙限制，且并非所有网络都支持

3.3 查看自己的 IP 地址

# Linux / Mac
ifconfig        # 或 ip addr
curl ifconfig.me  # 查看公网出口 IP
curl ip.sb

# Windows
ipconfig
curl ifconfig.me

# 查看 DNS 解析
nslookup example.com
dig example.com

3.4 判断是否有公网 IP

  1. 登录路由器管理页面（通常 192.168.1.1 或 192.168.0.1）
  2. 查看 WAN 口状态中的 IP 地址
  3. 在浏览器打开 https://ip138.com 或 https://ifconfig.me
  4. 两个 IP 一致 → 有公网 IP；不一致 → 在 CGNAT 后面，需要内网穿透
如果你有公网 IP，最简单的方案是在路由器上做端口映射/虚拟服务器 + DDNS，不需要 FRP。但现在家宽公网 IP 越来越稀缺（尤其是移动宽带），所以内网穿透仍然是最通用的方案。

04 端口与端口映射

4.1 端口是什么

IP 地址定位到一台设备，端口定位到设备上的具体服务。端口是 0-65535 的数字。

  • 0-1023：知名端口（需要管理员权限监听）
  • 1024-49151：注册端口
  • 49152-65535：动态/临时端口

4.2 常见服务端口

端口协议服务
22TCPSSH
80TCPHTTP
443TCPHTTPS
3306TCPMySQL
6379TCPRedis
8080TCPHTTP 代理/备用 Web
5432TCPPostgreSQL
27017TCPMongoDB
3389TCPRDP 远程桌面
5900TCPVNC

4.3 端口映射（Port Forwarding）

如果你有公网 IP，在路由器上配置"虚拟服务器/端口映射"即可：

外部端口 8080 → 内网 192.168.1.100:80
外部端口 2222 → 内网 192.168.1.100:22

然后外网通过 公网IP:8080 即可访问内网 Web 服务

4.4 查看端口占用

# Linux / Mac
lsof -i :8080          # 查看 8080 端口占用
netstat -tlnp          # 查看所有监听端口
ss -tlnp               # 更现代的 netstat

# Windows
netstat -ano | findstr :8080
tasklist | findstr PID

4.5 测试端口连通性

# telnet
telnet 公网IP 8080

# nc (netcat)
nc -zv 公网IP 8080

# curl
curl http://公网IP:8080

# PowerShell

很多云服务商（阿里云/腾讯云/AWS）有安全组防火墙，需要在控制台放行对应端口，否则即使服务启动了外面也访问不了。同时 Linux 的 firewalld / ufw / iptables 也要放行。

05 快速上手：第一个隧道

5.1 最快体验：用 Cloudflare Tunnel（无需服务器）

如果只是临时用，Cloudflare Tunnel 完全免费，不需要买 VPS：

# 安装 cloudflared
# Linux
wget https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-linux-amd64
chmod +x cloudflared-linux-amd64
sudo mv cloudflared-linux-amd64 /usr/local/bin/cloudflared

# Mac
brew install cloudflared

# Windows (PowerShell 管理员)
winget install Cloudflare.cloudflared

# 一条命令暴露本地 8080 端口
cloudflared tunnel --url http://localhost:8080

# 输出一个 https://xxx.trycloudflare.com 地址，外网即可访问
Cloudflare Tunnel 适合临时开发调试。免费、自动 HTTPS、不需要公网 IP。但 URL 是随机的（免费版），重启会变，且流量经过 Cloudflare。

5.2 最流行方案：FRP 快速体验

需要一台有公网 IP 的 VPS（最便宜的轻量云服务器即可）。

服务端（VPS）配置

# 下载 FRP（注意选对应架构）
wget https://github.com/fatedier/frp/releases/download/v0.61.0/frp_0.61.0_linux_amd64.tar.gz
tar xzf frp_0.61.0_linux_amd64.tar.gz
cd frp_0.61.0_linux_amd64

# 编辑服务端配置 frps.toml
cat > frps.toml << 'EOF'
bindPort = 7000           # frps 监听端口（客户端连接用）
auth.token = "your_token" # 认证令牌
EOF

# 启动
./frps -c frps.toml

客户端（内网机器）配置

# 下载对应平台的 FRP
# 编辑 frpc.toml
cat > frpc.toml << 'EOF'
serverAddr = "你的VPS公网IP"
serverPort = 7000
auth.token = "your_token"

[[proxies]]
name = "web"
type = "tcp"
localIP = "127.0.0.1"
localPort = 80
remotePort = 6000    # 访问 VPS 的 6000 端口就转发到本地 80
EOF

# 启动
./frpc -c frpc.toml

现在外网访问 http://VPS_IP:6000 就能看到你本地 80 端口的服务了。

5.3 验证隧道是否通

# 在 VPS 上确认 frps 监听了 7000 和 6000
ss -tlnp | grep -E '7000|6000'

# 从任意外网机器访问
curl http://VPS_IP:6000

# 查看 frps 日志应有类似：
# [I] proxy [web] start a new tunnel [tcp] listener [VPS_IP:6000]

5.4 常见问题快速排查

  • 连接超时 → VPS 防火墙/安全组没放行 7000/6000
  • token 不匹配 → 两端 auth.token 必须一致
  • remotePort 被占用 → ss -tlnp 检查换端口
  • 本地服务没启动 → curl localhost:80 先确认本地可访问

  • 全流量代理/全局 VPN：WireGuard
  • 国内服务器、不想折腾：花生框/神卓互联等付费 SaaS

07 FRP 核心配置

7.1 FRP 架构

┌──────────┐    连接7000     ┌──────────┐
│  frpc    │ ←─────────────→ │  frps    │
│ (客户端)  │   隧道(加密)     │ (服务端)  │
│ 内网机器  │                 │ VPS      │
└──────────┘                 └────┬─────┘
     ↑                            │
 本地服务                          ↓ 监听 6000/80/443
:80 :22 :3306                 外网用户访问

7.2 服务端配置详解（frps.toml）

# frps.toml — 完整配置示例

bindPort = 7000                    # frpc 连接端口

# 认证
auth.token = "change_me_to_a_strong_token"

# Dashboard（可选，Web 监控面板）
webServer.addr = "0.0.0.0"
webServer.port = 7500
webServer.user = "admin"
webServer.password = "strong_password"

# HTTP/HTTPS 穿透（虚拟主机模式）
vhostHTTPPort = 80
vhostHTTPSPort = 443

# 端口白名单（限制 frpc 可映射的远程端口范围）
allowPorts = [
  { start = 6000, end = 7000 },
  { start = 80, end = 80 },
  { start = 443, end = 443 }
]

# 最大连接数限制
maxPortsPerClient = 10

# 日志
log.to = "/var/log/frps.log"
log.level = "info"
log.maxDays = 30

# 子域名配置（配合 HTTP 穿透）
subDomainHost = "example.com"

7.3 客户端配置详解（frpc.toml）

# frpc.toml

serverAddr = "YOUR_VPS_IP"
serverPort = 7000
auth.token = "change_me_to_a_strong_token"

# 日志
log.to = "./frpc.log"
log.level = "info"

# ===== TCP 代理（最常用）=====
# 把本地 80 端口映射到 VPS 的 6000 端口
[[proxies]]
name = "web"
type = "tcp"
localIP = "127.0.0.1"
localPort = 80
remotePort = 6000

# SSH 映射
[[proxies]]
name = "ssh"
type = "tcp"
localIP = "127.0.0.1"
localPort = 22
remotePort = 6022

# 远程桌面
[[proxies]]
name = "rdp"
type = "tcp"
localIP = "127.0.0.1"
localPort = 3389
remotePort = 6389

# ===== UDP 代理（DNS/游戏等）=====
[[proxies]]
name = "dns"
type = "udp"
localIP = "127.0.0.1"
localPort = 53
remotePort = 6053

7.4 HTTP 类型代理（基于域名）

TCP 模式每个服务占一个端口。HTTP 模式可以多个服务共用 80 端口，通过域名区分：

# frpc.toml
serverAddr = "YOUR_VPS_IP"
serverPort = 7000
auth.token = "your_token"

# 服务 A：通过 nas.example.com 访问
[[proxies]]
name = "nas"
type = "http"
localIP = "127.0.0.1"
localPort = 5000
subdomain = "nas"          # nas.example.com

# 服务 B：通过 blog.example.com 访问
[[proxies]]
name = "blog"
type = "http"
localIP = "127.0.0.1"
localPort = 8080
subdomain = "blog"         # blog.example.com

# 或使用自定义域名
[[proxies]]
name = "app"
type = "http"
localIP = "127.0.0.1"
localPort = 3000
customDomains = ["app.myown.com"]
使用 HTTP 模式需要：① frps 配置 vhostHTTPPort = 80；② 域名 DNS A 记录指向 VPS IP；③ 泛域名 *.example.com 指向 VPS。

7.5 启动与后台运行

临时启动（测试）

# 服务端
./frps -c frps.toml

# 客户端
./frpc -c frpc.toml

Systemd 服务（生产推荐）

# /etc/systemd/system/frps.service
[Unit]
Description=FRP Server
After=network.target

[Service]
Type=simple
ExecStart=/usr/local/bin/frps -c /etc/frp/frps.toml
Restart=on-failure
RestartSec=5
LimitNOFILE=1048576

[Install]
WantedBy=multi-user.target

# 启动并开机自启
sudo systemctl daemon-reload
sudo systemctl enable --now frps
sudo systemctl status frps

客户端同理创建 frpc.service。

08 FRP 高级功能

8.1 STCP：安全的 TCP 代理（不暴露端口）

普通 TCP 代理在 VPS 上开端口，任何人都能尝试连接。STCP（Secret TCP）不在 VPS 上监听端口，只有知道密钥的另一个 frpc 客户端才能访问。

# 服务提供方 frpc（被访问的机器）
[[proxies]]
name = "secret_ssh"
type = "stcp"
secretName = "my_ssh_secret"      # 访问密钥名称
localIP = "127.0.0.1"
localPort = 22

# 访问方 frpc（另一台机器）
[[visitors]]
name = "ssh_visitor"
type = "stcp"
serverName = "secret_ssh"         # 对应上面的 name
secretName = "my_ssh_secret"      # 必须一致
bindAddr = "127.0.0.1"
bindPort = 6000                   # 本地访问 localhost:6000 即连到远程 SSH
STCP 适合不想暴露公网端口的场景，如数据库、SSH。访问者也需要运行 frpc，安全性更高。

8.2 XTCP：P2P 打洞直连

流量不经过 VPS 中转，直接点对点传输，速度更快：

# 服务提供方
[[proxies]]
name = "p2p_ssh"
type = "xtcp"
secretName = "p2p_secret"
localIP = "127.0.0.1"
localPort = 22

# 访问方
[[visitors]]
name = "p2p_visitor"
type = "xtcp"
serverName = "p2p_ssh"
secretName = "p2p_secret"
bindAddr = "127.0.0.1"
bindPort = 6000
# 打洞失败时自动回退到中转
# 开启 keepTunnelOpen 可保持隧道
XTCP 成功率取决于双方 NAT 类型。对称型 NAT 可能打洞失败，此时自动降级为 STCP 中转。FRP 还支持 natHoleSTUNServer 配置 STUN 服务器辅助打洞。

09 SSH 隧道技术

9.1 SSH 隧道三种模式

SSH 自带端口转发功能，不需要额外装软件，是最轻量的隧道方案。

本地端口转发（-L）：把远程端口映射到本地

# 在本地机器执行
# 把 VPS 的 8080 端口映射到本地 8080
# 即访问 localhost:8080 等于访问 VPS:8080
ssh -L 8080:localhost:8080 user@VPS_IP

# 典型场景：VPS 上跑了数据库但只监听 127.0.0.1
# 本地通过 localhost:3306 安全访问远程 MySQL
ssh -L 3306:localhost:3306 user@VPS_IP

远程端口转发（-R）：把本地端口暴露到远程（内网穿透！）

# 在内网机器执行
# 把本地 80 端口映射到 VPS 的 9000 端口
# 外网访问 VPS:9000 即访问内网服务
ssh -R 9000:localhost:80 user@VPS_IP

# 这就是最简单的内网穿透！
# 但默认 VPS 只监听 127.0.0.1:9000
# 需要在 VPS 的 /etc/ssh/sshd_config 中设置：
# GatewayPorts yes
# 然后 sudo systemctl restart sshd
# 才能让外网访问 VPS:9000

动态端口转发（-D）：SOCKS 代理

# 在本地启动一个 SOCKS5 代理
ssh -D 1080 user@VPS_IP

# 然后浏览器配置 SOCKS5 代理 localhost:1080
# 所有流量通过 VPS 出去（科学上网/访问内网）

9.2 保持 SSH 隧道稳定

# 加上保活和后台参数
ssh -R 9000:localhost:80 user@VPS_IP \
  -N \                    # 不执行远程命令（纯转发）
  -f \                    # 后台运行
  -o ServerAliveInterval=60 \   # 每60秒发心跳
  -o ServerAliveCountMax=3 \    # 3次无响应断开
  -o ExitOnForwardFailure=yes \ # 转发失败就退出
  -o StrictHostKeyChecking=no

9.3 用 autossh 自动重连

# 安装
sudo apt install autossh    # Debian/Ubuntu
brew install autossh        # Mac

# 启动（-M 指定监控端口）
autossh -M 0 -R 9000:localhost:80 user@VPS_IP \
  -N -f \
  -o ServerAliveInterval=60 \
  -o ServerAliveCountMax=3

# 配合 systemd 开机自启
# /etc/systemd/system/autossh.service
[Unit]
Description=AutoSSH Tunnel
After=network.target

[Service]
User=your_user
ExecStart=/usr/bin/autossh -M 0 -R 9000:localhost:80 -N -o ServerAliveInterval=60 -o ServerAliveCountMax=3 user@VPS_IP
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target

        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

13 WireGuard 组网穿透

13.1 WireGuard 是什么

WireGuard 是现代 VPN 协议，代码量极小（约 4000 行），性能极强，已合入 Linux 内核。它可以把多台异地设备组成一个虚拟局域网，互相通过内网 IP 访问。

VPS (10.0.0.1) ←── WireGuard 隧道 ──→ 家里电脑 (10.0.0.2)
     │                                      │
     └── 手机 (10.0.0.3) ←──────────────────┘
所有设备像在同一个局域网，可以互相 SSH/HTTP/...

13.2 安装与配置

# 安装（所有节点）
sudo apt install wireguard -y    # Debian/Ubuntu
brew install wireguard-tools     # Mac

# 生成密钥对
wg genkey | tee privatekey | wg pubkey > publickey

VPS 配置（/etc/wireguard/wg0.conf）

[Interface]
Address = 10.0.0.1/24
ListenPort = 51820
PrivateKey = VPS私钥

# 开启 IP 转发
# echo "net.ipv4.ip_forward=1" >> /etc/sysctl.conf
# sysctl -p

PostUp = iptables -A FORWARD -i wg0 -j ACCEPT; iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
PostDown = iptables -D FORWARD -i wg0 -j ACCEPT; iptables -t nat -D POSTROUTING -o eth0 -j MASQUERADE

# 家里电脑
[Peer]
PublicKey = 家里电脑公钥
AllowedIPs = 10.0.0.2/32

# 手机
[Peer]
PublicKey = 手机公钥
AllowedIPs = 10.0.0.3/32

客户端配置（家里电脑）

[Interface]
Address = 10.0.0.2/24
PrivateKey = 家里电脑私钥

[Peer]
PublicKey = VPS公钥
Endpoint = VPS_IP:51820
AllowedIPs = 10.0.0.0/24        # 只走 VPN 访问 10.0.0.x
# AllowedIPs = 0.0.0.0/0       # 全局流量走 VPN（科学上网）
PersistentKeepalive = 25        # NAT 保活

14 打洞技术：P2P 穿透

14.1 为什么需要 P2P 打洞

中转方案（FRP/SSH）流量经过 VPS，受限于 VPS 带宽，且增加延迟。P2P 打洞让两台内网设备直接通信，速度快、不走中转流量。

14.2 UDP 打洞原理（最常见）

设备 A (NAT-A:portA)                设备 B (NAT-B:portB)
       │                                    │
       │ 1. A → STUN服务器 → 获取公网映射     │
       │    公网A = PubIP_A:PortA           │
       │                                    │
       │ 2. B → STUN服务器 → 获取公网映射     │
       │    公网B = PubIP_B:PortB           │
       │                                    │
       │ 3. A 和 B 通过信令服务器交换公网地址  │
       │                                    │
       │ 4. A → 公网B 发 UDP（B的NAT丢弃）   │
       │    B → 公网A 发 UDP（A的NAT丢弃）   │
       │                                    │
       │ 5. 但双方NAT都已"记住"了对方，       │
       │    后续包就能通过了！打洞成功！       │
       │ ←──────── P2P 直连 ──────────────→ │

14.3 STUN / TURN / ICE

  • STUN：帮助设备发现自己的公网映射地址（轻量）
  • TURN：中继服务器，P2P 失败时兜底（流量中转）
  • ICE：综合 STUN/TURN，自动收集候选地址并尝试最佳路径
# 公共 STUN 服务器
stun.l.google.com:19302
stun1.l.google.com:19302
stun.cloudflare.com:3478

# 自建 STUN（用 coturn）
sudo apt install coturn
# /etc/turnserver.conf
listening-port=3478
fingerprint
lt-cred-mech
realm=example.com
user=myuser:mypassword

14.4 TCP 打洞

TCP 打洞更复杂，因为 TCP 有连接状态机。常见方式：

  • 同时发起 TCP 连接（Simultaneous Open），利用 TCP 同时打开特性
  • 利用 TTL trick
  • 实际应用中 UDP 打洞 + 应用层可靠性（如 QUIC/KCP）更常见

14.5 哪些 NAT 能打洞

A \ BFull ConeRestrictedPort RestrictedSymmetric
Full Cone✅ 容易✅✅⚠️ 可能
Restricted✅✅✅⚠️
Port Restricted✅✅✅❌ 困难
Symmetric⚠️⚠️❌❌ 几乎不能
移动宽带和 4G/5G 网络通常是 Symmetric NAT，P2P 成功率很低。因此生产环境一般采用 P2P 优先 + 中转兜底的策略。

14.6 现成 P2P 方案

  • Tailscale/ZeroTier：自动处理 NAT 穿透，P2P 失败走 DERP 中继
  • FRP XTCP：FRP 内置的 P2P 模式
  • N2N：轻量 P2P VPN
  • WebRTC：浏览器端 P2P（数据通道/视频通话），内置 ICE/STUN/TURN

15 安全加固

15.1 内网穿透的安全风险

  • 把内网服务暴露到公网，增加攻击面
  • FRP 认证令牌泄露 → 任何人可接入你的隧道
  • 暴露的服务本身有漏洞（如未授权 Redis、弱密码）
  • 隧道未加密 → 流量可被中间人窃听
  • VPS 被入侵 → 攻击者可访问所有隧道

15.2 FRP 安全配置

# frps.toml — 安全加固

# 强认证令牌（至少 32 位随机字符串）
auth.token = "使用openssl rand -base64 32生成"

# 限制端口范围
allowPorts = [{ start = 6000, end = 6100 }]

# 每客户端最大端口数
maxPortsPerClient = 5

# Dashboard 不要暴露公网，或绑定 127.0.0.1 + SSH 隧道访问
webServer.addr = "127.0.0.1"
webServer.port = 7500

# TLS 强制加密 frpc↔frps 通信
transport.tls.force = true

# 日志审计
log.to = "/var/log/frps.log"
log.level = "warn"  # 生产环境用 warn 减少 IO
# frpc.toml
auth.token = "同上"
transport.tls.enable = true
transport.tls.certFile = ""  # 可选：自签证书
transport.tls.keyFile = ""
transport.tls.trustedCaFile = ""

# 每个代理也可开启加密+压缩
[[proxies]]
name = "secure_service"
type = "tcp"
localIP = "127.0.0.1"
localPort = 8080
remotePort = 6000
transport.useEncryption = true
transport.useCompression = true

15.3 服务层安全

  • 绝不暴露无认证服务：Redis 6379、MongoDB 27017、Elasticsearch 9200 等默认无密码，绝不能直接映射
  • 加密码和认证：所有暴露服务设置强密码、密钥认证
  • 使用 HTTPS：Web 服务必须加密
  • HTTP Basic Auth：FRP HTTP 代理可加 httpUser/httpPassword
  • IP 白名单：通过 Nginx 或防火墙限制来源 IP
  • 优先用 STCP：不监听公网端口，只有授权 frpc 能访问
# Nginx IP 白名单示例
location / {
    allow 1.2.3.4;        # 你的办公 IP
    allow 5.6.7.0/24;     # 公司网段
    deny all;             # 拒绝其他所有
    proxy_pass http://127.0.0.1:6000;
}

15.4 VPS 安全清单

  • ✅ 防火墙只放行必要端口（22/80/443/7000）
  • ✅ fail2ban 防 SSH 暴力破解
  • ✅ 定期系统更新

16 性能优化

16.1 影响速度的因素

  • VPS 带宽：中转模式最大瓶颈，上下行带宽
  • VPS 线路质量：到用户的延迟和丢包率
  • 协议选择：TCP over TCP 性能下降，KCP/QUIC 可能更好
  • 压缩：文本类开压缩省带宽，图片/视频已压缩别再开
  • 加密：TLS 有少量 CPU 开销，现代硬件影响很小

16.2 FRP 传输优化

# 开启压缩（对 HTML/CSS/JS/JSON 效果好）
[[proxies]]
name = "web"
type = "http"
localIP = "127.0.0.1"
localPort = 80
subdomain = "app"
transport.useCompression = true
transport.useEncryption = true

# 对大文件/视频流不要开压缩（已经是压缩格式）

16.3 KCP 协议（弱网优化）

FRP 支持 KCP（基于 UDP 的可靠传输），在丢包率高的网络环境下比 TCP 更快：

# frps.toml
# 额外监听 KCP（UDP）
kcpBindPort = 7000   # 注意是 UDP

# frpc.toml
serverAddr = "VPS_IP"
serverPort = 7000
transport.protocol = "kcp"
# 还需在 VPS 防火墙放行 UDP 7000
KCP 在高延迟/丢包环境（如跨运营商、海外）效果明显，但会额外消耗约 10-20% 带宽。网络稳定时用 TCP 即可。

16.5 P2P 直连减少中转

对大流量服务（文件传输、视频、远程桌面），优先尝试 XTCP P2P：

  • 配置 STUN 服务器辅助打洞
  • 打洞成功后流量不经过 VPS
  • 打洞失败自动降级为中转

16.6 系统内核参数调优

# /etc/sysctl.conf — VPS 上优化网络
# 增大缓冲区
net.core.rmem_max = 16777216
net.core.wmem_max = 16777216
net.ipv4.tcp_rmem = 4096 87380 16777216
net.ipv4.tcp_wmem = 4096 65536 16777216

# BBR 拥塞控制（高延迟链路提速）
net.core.default_qdisc = fq
net.ipv4.tcp_congestion_control = bbr

# 连接跟踪表加大
net.netfilter.nf_conntrack_max = 65536

# 应用
sudo sysctl -p

# 验证 BBR
sysctl net.ipv4.tcp_congestion_control

18 综合实战与排错

18.1 实战：完整的家庭服务器穿透方案

场景

  • 家里有一台 Linux 服务器跑着 Nextcloud（文件）、Jellyfin（媒体）、Gitea（代码）
  • 运营商 CGNAT，没有公网 IP
  • 买了一台 VPS，有域名 home.example.com

架构

外网用户 → HTTPS → Caddy(VPS) → FRPS → FRPC(家里) → 各服务
  nextcloud.home.example.com  → localhost:8080
  jellyfin.home.example.com   → localhost:8096
  gitea.home.example.com      → localhost:3000
  SSH: VPS:6022               → localhost:22 (STCP 更安全)

frps.toml（VPS）

bindPort = 7000
auth.token = "强随机token"
vhostHTTPPort = 8080  # Caddy 反代到这里，不直接暴露80
subDomainHost = "home.example.com"
allowPorts = [{ start = 6000, end = 6100 }]
maxPortsPerClient = 10
transport.tls.force = true
log.to = "/var/log/frps.log"
log.maxDays = 30

frpc.toml（家里）

serverAddr = "VPS_IP"
serverPort = 7000
auth.token = "强随机token"
transport.tls.enable = true

[[proxies]]
name = "nextcloud"
type = "http"
localIP = "127.0.0.1"
localPort = 8080
subdomain = "nextcloud"
transport.useCompression = true

[[proxies]]
name = "jellyfin"
type = "http"
localIP = "127.0.0.1"
localPort = 8096
subdomain = "jellyfin"

[[proxies]]
name = "gitea"
type = "http"
localIP = "127.0.0.1"
localPort = 3000
subdomain = "gitea"

# SSH 用 STCP（不在公网开端口）
[[proxies]]
name = "home_ssh"
type = "stcp"
secretName = "ssh_secret"
localIP = "127.0.0.1"
localPort = 22

Caddyfile

nextcloud.home.example.com {
    reverse_proxy 127.0.0.1:8080
}
jellyfin.home.example.com {
    reverse_proxy 127.0.0.1:8080
}
gitea.home.example.com {
    reverse_proxy 127.0.0.1:8080
}

18.4 学习路径总结

  1. 第1-4章：理解网络基础和 NAT 原理——这是所有穿透技术的根基
  2. 第5-6章：用 Cloudflare Tunnel/FRP 快速跑通第一个隧道，建立直觉
  3. 第7-10章：深入 FRP 配置、SSH 隧道、SaaS 方案，掌握各种工具
  4. 第11-14章：自建服务器、域名 HTTPS、WireGuard 组网、P2P 打洞——进阶能力
  5. 第15-18章：安全、性能、部署、排错——生产环境必备技能
核心建议：内网穿透本质是网络工程，80% 的问题都是防火墙、端口、DNS、认证这四件事。掌握 ss、nc、journalctl、tcpdump 四个调试工具，遇到问题按"客户端→隧道→服务端→防火墙→网络"逐层排查，基本没有解决不了的问题。
写在最后：内网穿透不是什么黑魔法，核心就是"在内网主动向外建立连接，然后在这条连接上双向传输数据"。理解了 NAT 的工作方式和这条隧道的原理，FRP、SSH、WireGuard、Tailscale 这些工具就都是同一思想的不同实现。安全第一，别把没认证的服务直接暴露到公网。
