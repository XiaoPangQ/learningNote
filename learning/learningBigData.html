01 大数据概述与生态全景

1.1 什么是大数据

大数据（Big Data）指规模大到无法用传统单机数据库和工具在可接受时间内处理的数据集合，以及围绕这些数据的采集、存储、计算、分析的技术体系。经典特征是「5V」：

特征 英文 含义
大量 Volume 数据量级 TB → PB → EB，单机存不下、算不动
高速 Velocity 数据产生与处理速度快，要求秒级甚至毫秒级响应
多样 Variety 结构化（表）、半结构化（JSON/日志）、非结构化（图片/视频）
价值密度低 Value 海量数据中有价值比例低，需要挖掘提炼
真实性 Veracity 数据有噪声、缺失、重复，需要清洗治理
简单理解：传统数据库像「一个账本」，账目多了记不下；大数据系统像「一群会计分工记账」——把数据切开放到成百上千台机器上（分布式存储），再把计算任务拆开分给这些机器同时算（分布式计算）。大数据的本质就是分布式存储 + 分布式计算。

1.6 核心术语速查

  • HDFS：分布式文件系统，大数据存储的基石
  • YARN：集群资源调度器，统一分配 CPU/内存
  • Hive：SQL 数仓引擎，SQL 会被翻译成分布式计算任务
  • Spark：基于内存的通用计算引擎
  • Flink：流批一体的流计算引擎
  • Kafka：高吞吐分布式消息队列
  • 数仓分层：ODS/DWD/DWS/ADS，数据加工的流水线
  • 数据湖：支持 ACID 和更新的开放表格式存储（Iceberg 等）
  • 数据倾斜：数据分布不均导致个别任务拖慢全局
  • CDC：Change Data Capture，捕获数据库变更用于实时同步
口诀：「存储 HDFS，调度靠 YARN，离线 Hive+Spark，实时 Flink 走 Kafka，查询选 Doris/CK，采集 DataX 与 CDC」——记住这条主线，整个大数据生态就不会迷路。

03 HDFS 分布式文件系统

3.1 设计目标与架构

HDFS（Hadoop Distributed File System）为一次写入、多次读取的大文件场景设计。核心思想：文件切块、多副本、分机存储。 

                    ┌──────────────┐
   客户端 ────────► │  NameNode    │  元数据：目录树/块位置/权限
     │  读写请求     │  (Master)    │  (内存中，定期快照 + edits 日志)
     │              └──────┬───────┘
     │                     │ 心跳/块报告
     ▼                     ▼
┌──────────┐       ┌──────────┐       ┌──────────┐
│ DataNode │       │ DataNode │  ...  │ DataNode │  实际存储数据块
│ blk_1×2  │       │ blk_1×1  │       │ blk_2×1  │  副本分布在不同节点
└──────────┘       └──────────┘       └──────────┘
  • Block（块）：文件切分单元，默认 128MB。块太大→并行度低，太小→元数据爆炸
  • 副本机制：默认 3 副本（本机一份、同机架一份、跨机架一份），节点宕机自动补副本
  • NameNode 高危：元数据在内存，单点故障 → HA 方案（主备 + JournalNode 同步元数据）
  • 机架感知：副本放置策略兼顾容灾与带宽

3.2 读写流程（面试高频）

写流程

  1. 客户端向 NameNode 请求上传文件，NN 检查权限与是否存在
  2. NN 返回目标 DataNode 列表（按机架感知挑选）
  3. 客户端与 DN 建立管道（pipeline），逐个传输数据包
  4. DN 之间流水线复制副本，全部 ACK 后确认写入成功
  5. 全部块完成后，NN 关闭文件记录

读流程

  1. 客户端向 NN 获取文件块的位置信息（哪个块在哪些 DN 上）
  2. NN 返回时会按距离排序（本节点 > 同机架 > 跨机架）
  3. 客户端就近读取块，本地拼装成完整文件
记忆口诀：「元数据在 NN，数据在 DN；写走管道逐包传，读挑最近的那台；三副本两机架，块大小 128」。

3.4 Java API 操作

import org.apache.hadoop.conf.Configuration;
import org.apache.hadoop.fs.*;

public class HdfsDemo {
    public static void main(String[] args) throws Exception {
        Configuration conf = new Configuration();
        conf.set("fs.defaultFS", "hdfs://node1:8020");
        // 本地调试必须设置用户，否则无权限
        System.setProperty("HADOOP_USER_NAME", "root");
        FileSystem fs = FileSystem.get(conf);

        // 上传
        fs.copyFromLocalFile(
            new Path("D:/access.log"), new Path("/data/logs/"));

        // 下载
        fs.copyToLocalFile(false,
            new Path("/data/logs/access.log"), new Path("./"), true);

        // 遍历目录
        RemoteIterator<LocatedFileStatus> it =
            fs.listFiles(new Path("/data"), true);
        while (it.hasNext()) {
            LocatedFileStatus f = it.next();
            System.out.println(f.getPath() + " " + f.getLen());
        }
        fs.close();
    }
}

3.5 HDFS 为什么不适合存小文件

每个文件至少占一个块、每块约 150 字节元数据常驻 NameNode 内存。1 亿个小文件 = 1 亿条元数据，NN 直接 OOM。治理方案：

  • 写入前合并成大文件（Har 打包 / SequenceFile）
  • 小文件归档任务定期合并分区目录
  • 从源头治理：Flume/Spark 落地时按大小/时间滚动文件

04 MapReduce 与 YARN

4.1 MapReduce 编程模型

MapReduce 把分布式计算抽象成两个阶段：Map（映射）分而治之，Reduce（归约）汇总合并。开发者只需写这两个函数，框架负责并行、容错、分发。

经典 WordCount 流程

输入:  hello spark hello hadoop

Map 阶段（每个节点并行处理自己那份数据切片）
  输入: "hello spark"          输出: (hello,1) (spark,1)
  输入: "hello hadoop"         输出: (hello,1) (hadoop,1)

Shuffle 阶段（按 key 分组、排序、网络传输）
  hello → [1,1]   spark → [1]   hadoop → [1]

Reduce 阶段（对每个 key 的 value 列表聚合）
  输出: (hello,2) (spark,1) (hadoop,1)

4.2 Shuffle 原理（最烧脑也最重要）

Map 端: 输出 → 环形缓冲区(100MB, 80%溢写) → 分区(Spill) → 排序
       → 合并成 map 输出文件 → 等待 Reduce 拉取
Reduce 端: 按分区号拉取(fetch)属于自己的数据 → 归并排序 → 分组
       → 交给 reduce() 方法处理
  • 分区数 = ReduceTask 数，默认 HashPartitioner（key hash % 分区数）
  • 分区不均 = 数据倾斜的雏形
  • 可选优化：Combiner（Map 端先本地聚合，减少网络传输）、压缩 Map 输出

4.3 YARN 资源调度

YARN 是集群的「操作系统」，统一管理 CPU/内存的分配：

┌────────────────────────────────────────────┐
│ ResourceManager (RM)：全局资源老大          │
│   ├─ 调度器 Scheduler：按容量/公平分配资源    │
│   └─ 应用管理器：接收作业提交                │
├────────────────────────────────────────────┤
│ NodeManager (NM)：每台机器的代理             │
│   管理 Container（CPU+内存的资源容器）        │
├────────────────────────────────────────────┤
│ ApplicationMaster (AM)：每个应用一个         │
│   向 RM 申请 Container，指挥任务运行          │
└────────────────────────────────────────────┘
一个作业的完整旅程：客户端提交 → RM 找一台机器开 Container 运行 AM → AM 向 RM 申请 N 个 Container → RM 通知各 NM 启动 Task → Task 汇报进度给 AM → 全部完成，AM 注销。

4.4 为什么 MapReduce 被 Spark 取代

维度 MapReduce Spark
中间结果 写磁盘（HDFS） 优先内存，必要时落盘
表达力 只有 Map/Reduce 两个算子 80+ 算子，函数式编程
多轮迭代 每轮一个作业，磁盘 IO 巨大 DAG 一次规划，内存复用
延迟 分钟级 秒级 / 亚秒级
场景 超大规模离线批处理 批处理、SQL、流、机器学习
尽管如此 MR 依然值得学：Hive 底层（MR 引擎）、思想原型（split → map → shuffle → reduce）在 Spark/Flink 中反复出现。面试问 Spark Shuffle 本质上就是在考你对 MR Shuffle 的理解。

05 Hive 数据仓库

5.1 Hive 是什么

Hive 是构建在 Hadoop 上的数据仓库工具：把结构化数据文件映射为表，把 SQL（HiveQL）翻译成 MapReduce/Spark/Tez 任务执行。核心价值：让会 SQL 的人就能做大数据开发。

  • 元数据（表结构）存 Metastore（通常为 MySQL）
  • 数据文件存 HDFS
  • 计算引擎可插拔：MR / Tez / Spark
  • 本质是「SQL → 分布式计算」的翻译器，不是数据库：延迟高、不适合点查

5.2 内部表与外部表

-- 内部表（管理表）：删表时 HDFS 数据一起删除
CREATE TABLE IF NOT EXISTS student (
  id INT, name STRING, age INT
) ROW FORMAT DELIMITED FIELDS TERMINATED BY ',';

-- 外部表：删表只删元数据，数据文件保留（生产首选！）
CREATE EXTERNAL TABLE IF NOT EXISTS ods_log (
  ip STRING, url STRING, ts BIGINT
) ROW FORMAT DELIMITED FIELDS TERMINATED BY '\t'
LOCATION '/data/ods/ods_log';

-- 查看建表语句 / 表结构
SHOW CREATE TABLE ods_log;
DESC FORMATTED ods_log;
选型规则：原始层（ODS）用外部表——防止误删原始数据；中间结果表可用内部表——方便生命周期自动清理。

5.3 分区与分桶

-- 分区表：按目录物理隔离数据，查询时裁剪全表扫描为目录扫描
CREATE TABLE ods_order (
  order_id STRING, user_id STRING, amount DECIMAL(10,2)
) PARTITIONED BY (dt STRING)
ROW FORMAT DELIMITED FIELDS TERMINATED BY ',';

-- 加载数据到指定分区
LOAD DATA INPATH '/data/20260827.csv'
INTO TABLE ods_order PARTITION (dt='2026-08-27');

-- 动态分区插入
SET hive.exec.dynamic.partition.mode=nonstrict;
INSERT OVERWRITE TABLE dwd_order_p PARTITION (dt)
SELECT order_id, user_id, amount, dt FROM ods_order;

-- 查询时必须带分区条件（否则全表扫描）
SELECT COUNT(*) FROM ods_order WHERE dt='2026-08-27';

-- 分桶表：按列 hash 拆成固定文件数，利于抽样与 join 优化
CREATE TABLE dwd_user_bucket (
  user_id STRING, city STRING
) CLUSTERED BY (user_id) INTO 32 BUCKETS;
分区 vs 分桶口诀：「分区按目录切（常用时间），分桶按 hash 切（常用 ID）；分区治全表扫描，分桶治 join 与抽样」。

6.5 RowKey 设计（HBase 的灵魂）

热点问题：RowKey 连续单调（如时间戳、自增 ID 作为前缀）会导致写入集中到单个 RegionServer，形成写入热点。经典方案：

  • 反转：手机号倒序（尾号天然分散）
  • 加盐：RowKey 前拼哈希前缀 hash(uid)%32_uid
  • 时间反转：Long.MAX_VALUE - timestamp，新数据排前面且打散
  • 组合键：查询维度放前面，如 uid#timestamp（一个用户的时间线连续，scan 高效）
RowKey 口诀：「查询条件做前缀，连续数据加散列；区间扫描靠排序，避免热点靠打散」。

08 Spark Core 核心编程

8.1 Spark 核心概念

  • Application：用户程序，由 Driver + Executors 组成
  • Driver：运行 main()，解析代码生成 DAG，分发任务
  • Executor：工作进程，负责真正执行 Task 并缓存数据
  • RDD：弹性分布式数据集，Spark 最基础的抽象
  • DAGScheduler：按宽依赖切分 Stage
  • TaskScheduler：把 Stage 内的 Task 分发到 Executor 
代码 → RDD 血缘(DAG) → 按宽依赖切 Stage
   → Stage 内并发 TaskSet → 提交 Executor 并行执行
   → 容错：血缘(lineage)重算，不复制数据

8.2 RDD 五大特性

  1. 由一组分区（partition）组成——并行度的单位
  2. 每个函数作用于每个分区——计算并行发生
  3. RDD 之间存在依赖关系（血缘）——容错的基础
  4. (可选) KV 型 RDD 有分区器（Hash/Range）——决定 shuffle 后的去向
  5. (可选)优先位置列表（移动计算不移动数据）——数据本地性

8.3 算子分类

类型 特点 常用算子
Transformation 转换 惰性，返回新 RDD，不触发计算 map、filter、flatMap、mapPartitions、union、distinct、groupBy、reduceByKey、join、repartition、coalesce
Action 行动 触发作业执行，返回结果或写盘 collect、count、first、take、reduce、saveAsTextFile、foreach

8.5 宽窄依赖与 Stage 划分

  • 窄依赖：父分区只被一个子分区依赖（map/filter）——可 pipeline 串联执行，无网络传输
  • 宽依赖：父分区被多个子分区依赖（reduceByKey/groupBy/join）——需要 shuffle，Stage 的边界 
DAG:  textFile → flatMap → map → reduceByKey → collect
      ├──── Stage 1（窄依赖 pipeline）────┤ ├─ Stage 2 ─┤
              无 shuffle                       有 shuffle
口诀：「窄依赖流水线，宽依赖切 Stage；shuffle 一响，黄金万两（性能损耗大）」。写 Spark 代码的优化核心就是：减少 shuffle 次数、减少 shuffle 数据量。

8.6 持久化与检查点

# 缓存：内存中复用，血缘保留（缓存丢了可重算）

rdd.persist(StorageLevel.MEMORY_AND_DISK)

# 释放
rdd.unpersist()
注意：cache 不是立即执行的算子，它也是惰性的——必须在 第一个 Action 之前调用，且要有 Action 触发才算真正缓存成功。checkpoint 需要单独再跑一次 Job，通常「先 cache 再 checkpoint」。

10 Kafka 消息队列

10.1 为什么需要消息队列

  • 解耦：生产者只管发消息，不关心谁消费
  • 削峰：流量洪峰先进队列，下游按自己的能力消费
  • 异步：非核心链路异步处理，接口响应更快
  • 缓冲与重放：数据保留在队列，消费失败可回溯重算

10.2 核心架构

Producer ──┐                        ┌── Consumer Group A
           ├─► Topic（逻辑队列）      │      (C1 C2 C3)
Producer ──┘      │                 └── Consumer Group B
                  ▼                        (独立消费全量)
        ┌──────────────────────────┐
        │ Partition 0  [0][1][2]…  │ ← 每个分区是一个有序队列
        │ Partition 1  [0][1]…     │   数据只追加不修改
        │ Partition 2  [0][1]…     │   副本机制保证高可用
        └──────────────────────────┘

# 关键规则：
# 1. 一个分区只能被同一消费组内的一个消费者消费（组内竞争）
# 2. 不同消费组之间互不影响（组间广播）
# 3. 消费者数 > 分区数 = 有人闲着；分区数 > 消费者数 = 有人身兼多职
# 4. 分区数决定并行度上限

11 Flink 流计算引擎

11.1 为什么流处理选 Flink

Spark Streaming 本质是「微批」（把流切成小批次模拟），延迟秒级。Flink 是 真正的逐条流处理：

维度 Spark Streaming/DStream Flink
模型 微批（Micro Batch） 纯事件驱动，逐条处理
延迟 秒级 毫秒级
时间语义 处理时间为主 事件时间 + Watermark（可处理乱序）
状态管理 弱 原生 Keyed State + RocksDB 大状态
Exactly-Once 端到端受限 Checkpoint 两阶段提交，端到端精确一次
API DataStream（已停止演进） DataStream + Table/SQL 双栈

11.2 核心概念

  • 事件时间 vs 处理时间：用数据自带的时间（事件时间）统计才准；网络延迟会导致乱序到达
  • Watermark（水位线）：「小于时间 T 的数据都到齐了」的承诺，容忍乱序 allowLateness 之外的数据走侧输出流
  • State（状态）：算子在内存/RocksDB 中记住中间结果（如累计的 count）
  • Checkpoint（检查点）：定期把状态快照持久化（HDFS/S3），故障后自动恢复——可靠性的基石
  • Savepoint：手动触发的检查点，用于升级/迁移作业

12 数据仓库建模理论

12.1 为什么要分层

分层不是玄学，是把「数据加工流水线」拆成清晰的车间：清晰复用、统一口径、隔离原始数据、问题定位快。

分层 名称 职责 类比
ODS 贴源层 原始数据原样落库，基本不清洗，保留全量/增量历史 原材料仓库
DWD 明细层 清洗、去重、标准化、维度退化后的明细事实数据 洗净切好的食材
DIM 维度层 统一维表：用户、商品、地区、时间等公共维度 调味料盒
DWS 汇总层 按主题宽表轻度汇总（按天/按用户/按商品粒度） 半成品菜
ADS 应用层 面向报表/大屏/接口的最终结果 端上桌的菜
分层口诀：「ODS 原样进，DWD 洗干净，DIM 管维度，DWS 做汇总，ADS 出结果」。

12.2 维度建模：星型与雪花

  • 事实表（Fact）：记录业务事件，行多、可加数值列（金额、数量、次数）
  • 维度表（Dimension）：描述「谁/什么/哪里/何时」，行少、文本属性列
  • 星型模型：事实表居中，维表直连——join 少，性能好，数仓首选
  • 雪花模型：维表再拆维表——冗余少但 join 多，查询慢

12.4 缓慢变化维（SCD）

  • SCD3 增加列：只保留上一版本（当前值 + 历史值）

15.5 数据重跑的正确姿势

  • 重跑前确认影响范围：查血缘，看下游有哪些表和报表
  • 自上游错误的层开始重跑，不要只补最后一层
  • INSERT OVERWRITE 幂等写入，重跑不产生重复数据
  • 重跑完通知下游与业务方核对数据
  • 复盘归档：为什么错？怎么防再犯？补监控规则
红线：永远不要手动 rm HDFS 上的数仓目录来「修复」数据——先停任务、再确认血缘、用 OVERWRITE 幂等重刷。误删生产数据是大数据最贵的事故之一。

16 数据湖与湖仓一体

16.1 传统数仓的痛点

  • 不能更新/删除：Hive 表改一条数据要重写整个分区
  • 批流割裂：同一份数据，离线走 HDFS、实时走 Kafka，两套链路两倍成本、口径还可能不一致
  • ACID 缺失：任务写一半失败，留下脏数据
  • 锁定单一引擎：数据格式私有，换引擎成本高

16.2 数据湖表格式：给文件系统加上数据库能力

数据湖（Hudi / Iceberg / Delta）本质是开放表格式（Table Format）：在 Parquet 文件之上加一层元数据（快照/清单），实现 ACID、增量、Time Travel：

能力 传统 Hive 表 湖表（Iceberg 等）
事务 ACID ❌ ✅ 快照隔离，写一半可回滚
更新/删除 重写整个分区 ✅ 增量写副本（MOR/COW）
流读 ❌ ✅ 增量消费，批流统一
Time Travel ❌ ✅ 查询历史快照，误操作可回滚
Schema 演进 加列受限 ✅ 安全增删改列

16.3 三大格式对比

格式 出身 特色 国内热度
Apache Iceberg Netflix 元数据设计最完善、引擎中立、隐藏分区 最高（云厂商主推）
Apache Hudi Uber Upsert 生态成熟、CDC 同步顺手 高
Delta Lake Databricks 与 Spark 深度绑定 中等

17.2 案例：实时交易大屏

需求：大促大屏实时展示：每分钟 GMV、各省成交地图、实时订单滚动条（秒级延迟）。 

链路：
MySQL(binlog) ─┐
App 埋点日志 ───┼─► Kafka ─► Flink(清洗/关联维表/聚合) ─► Doris ─► 大屏
                │
维表: Redis 缓存 + Kafka 广播流

-- Flink SQL：维表关联 + 分钟窗口聚合
CREATE TABLE dws_gmv_minute AS
SELECT
  TUMBLE_START(proc_time, INTERVAL '1' MINUTE) AS win,
  r.region_name,
  COUNT(o.order_id) AS order_cnt,
  SUM(o.amount)     AS gmv
FROM orders o
LEFT JOIN region FOR SYSTEM_TIME AS OF o.proc_time AS r
  ON o.city_id = r.city_id        -- 维表关联
GROUP BY TUMBLE(proc_time, INTERVAL '1' MINUTE), r.region_name;

17.3 精确一次与去重

  • 端到端 Exactly-Once = Kafka 可重放 + Flink Checkpoint + Sink 幂等/事务（Doris 主键模型、Iceberg 快照提交）
  • 实时去重：状态里存「今天见过的订单 ID」（Keyed State + TTL），千万级用 RocksDB 状态后端
  • 乱序处理：事件时间 + Watermark；迟到数据侧输出流落湖，次日离线修正

17.4 实时数仓分层（沿用离线思想）

Kafka 原始日志(ODS) → Flink 清洗(DWD) → Kafka 明细主题
   → Flink 轻度聚合(DWS) → Kafka/Doris 聚合主题
   → Flink 应用计算(ADS) → Doris/CK → 大屏/接口

要点：
1. 明细层落 Kafka + 落湖（Iceberg），既给实时也给离线回溯
2. 维表用广播状态或 Redis 缓存，避免每条数据查库
3. 大状态任务：RocksDB Backend + 增量 Checkpoint + TTL
实时数仓三座大山：① 大状态导致 checkpoint 超时（上 RocksDB+TTL）；② 维表关联打爆业务库（上缓存+广播）；③ 上游重发数据导致指标翻倍（幂等 sink + 去重状态）。踩过这三坑，实时链路基本就稳了。
架构选型口诀：「报表为主离线够，大屏风控才上实时；小规模 Kafka+Flink+Doris 一把梭，大规模上湖仓一体批流共享」。不要为了实时而实时——实时链路的运维成本是离线的数倍。

18 前沿趋势与架构演进

18.1 六大趋势

趋势一：批流一体（流批统一）

Flink 一套引擎同时支持流和批；Iceberg 一份存储同时服务两边。「Lambda 双链路」正在被淘汰，开发和运维成本砍半。

趋势二：湖仓一体（Lakehouse）

数据湖的开放性 + 数据仓的 ACID/性能，代表组合：Iceberg + StarRocks/Doris/Trino。

趋势三：云原生与存算分离

  • 存储用对象存储（S3/OSS/COS），计算资源弹性伸缩
  • Serverless 大数据：按 query 付费，不用养集群
  • 云上 EMR / 弹性 MapReduce：开箱即用

趋势四：OLAP 高并发统一入口

Doris/StarRocks 这类实时分析数据库正在成为「一个数据库统一实时+离线+湖上查询」的入口，中小团队可以告别「多引擎拼接」。

趋势五：DataOps 与数据治理平台化

数据地图、血缘、指标口径、质量规则、成本治理产品化（DataHub / OpenMetadata / 云厂商 DataWorks）。

趋势六：大数据 × AI

  • 大模型训练的数据底座：PB 级清洗、去重、特征工程流水线
  • 向量数据库与 RAG 成为大数据平台新组件
  • AI 反哺数据治理：智能元数据补全、异常检测、SQL 生成

18.5 学习路径建议

  1. 第1-2周：Linux + Hadoop 伪分布式，玩熟 HDFS 与 YARN
  2. 第3-4周：Hive 建模与 SQL 实战（重点：分区表、ORC、UDF）
  3. 第5-7周：Scala 基础 + Spark Core/SQL，吃透宽窄依赖与调优
  4. 第8-9周：Kafka 体系与数据采集（DataX/Flume/CDC）
  5. 第10-11周：Flink 流计算 + 数仓分层建模实战
  6. 第12-13周：ClickHouse/Doris + 调度监控，搭一个完整离线+实时项目
  7. 持续：数据湖、湖仓一体、云原生、数据治理
最重要的建议：动手做一个完整项目——比如「电商订单离线数仓 + 实时大屏」：MySQL 造数 → DataX/CDC 采集 → Hive/Spark 离线分层 → Flink 实时链路 → Doris 出报表 → DolphinScheduler 调度。一个项目串起所有组件，胜过看十套教程。
