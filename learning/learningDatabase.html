数据库从入门到精通

一份系统化的数据库学习笔记，从基础概念、SQL 语法到索引、事务、性能优化，再到主从复制、分库分表与 NoSQL 选型，适合从零开始逐步进阶。

19 个章节 SQL · 索引 · 事务 · 分布式 入门 → 精通

01 数据库基础概念

什么是数据库

数据库（Database）就是按一定结构组织、存储和管理数据的"电子仓库"。 你可以把它想象成现实世界里的仓库：数据是货物，表（Table）是货架，数据库管理系统（DBMS）是仓库管理员，负责货物的存取、清点和规则。

术语英文比喻说明
数据库Database仓库数据的集合
数据库管理系统DBMS管理员MySQL、Oracle、SQL Server 等软件
数据库系统DBS仓库 + 管理员 + 规章制度DBMS + 数据 + 应用 + 人员的整体
SQLStructured Query Language和管理员对话的语言操作数据库的标准语言

为什么不用文件或 Excel？

很多人第一反应：存数据用 Excel 或记事本不就行了？当数据量小、只有一个人用时确实可以，但会暴露出致命问题：

  • 并发问题：多人同时改一个文件，谁覆盖谁？数据库用「锁」和「事务」解决。
  • 数据一致性：一个文件写了一半就断电，数据就坏了。数据库有崩溃恢复机制。
  • 查询效率：Excel 里在百万行里找一行很慢，数据库有「索引」可以秒查。
  • 安全与权限：数据库可以精确控制「谁能看、谁能改」。

关系型 vs 非关系型

对比项关系型（SQL）非关系型（NoSQL）
代表产品MySQL、Oracle、PostgreSQL、SQL ServerRedis、MongoDB、ES、HBase
数据结构表（行列固定）键值 / 文档 / 列族 / 图
一致性强（支持 ACID 事务）最终一致性居多
扩展方式垂直扩展为主水平扩展（集群）
适用场景事务型业务（订单、账户）高并发缓存、海量日志、搜索
🧠 口诀
关系型重一致，非关系型重扩展；要事务选 SQL，要高并发选 NoSQL。
💡 提示
本文以 MySQL 为主要示例（最流行、最易上手），但 90% 的 SQL 语法和思想在 Oracle、PostgreSQL、SQL Server 中通用，只差少量方言。

02 关系模型与表结构

表、行、列

关系型数据库把数据组织成一张张表（Table）。表由行和列构成：

  • 列（字段，Column/Field）：数据的属性，比如「姓名」「年龄」，决定了这一列存什么类型的数据。
  • 行（记录，Row/Record）：一条完整的数据实体，比如「张三，25 岁」。

一张 users 表长这样：

idnameagecity
1张三25北京
2李四30上海
3王五28深圳

键（Key）

  • 主键（Primary Key, PK）：唯一标识一行记录的列，不能重复、不能为空。相当于每个人的「身份证号」。
  • 外键（Foreign Key, FK）：引用另一张表主键的列，用来建立表之间的「关系」。
  • 唯一键（Unique Key）：值不能重复，但可以为空（NULL），可以有多个。
🧠 口诀
主键唯一且非空（一张表一个）；唯一键唯一可空（可多个）；外键引用他表主键建立关系。

常见数据类型

类别类型说明
数值INT / BIGINT整数（4 字节 / 8 字节）
DECIMAL(M,D)精确小数，如金额；M 总位数，D 小数位
字符串CHAR(n)定长字符串，固定占 n 个字符
VARCHAR(n)变长字符串，最多 n 个字符，更省空间
TEXT长文本
日期时间DATE日期（YYYY-MM-DD）
DATETIME / TIMESTAMP日期时间；TIMESTAMP 受时区影响且有 2038 上限

约束（Constraint）

  • NOT NULL：不能为空。
  • UNIQUE：值唯一。
  • DEFAULT：默认值。
  • CHECK：取值范围检查（如 age >= 0）。
  • PRIMARY KEY / FOREIGN KEY：主键 / 外键。
⚠️ 避坑
存金额绝不能用 FLOAT/DOUBLE（二进制浮点有精度误差），要用 DECIMAL。经典翻车：0.1 + 0.2 ≠ 0.3。

03 SQL 分类与 DDL 建表

SQL 四大分类

分类全称作用核心关键字
DDLData Definition Language定义结构CREATE / ALTER / DROP / TRUNCATE
DMLData Manipulation Language操作数据INSERT / UPDATE / DELETE
DQLData Query Language查询数据SELECT
DCLData Control Language权限控制GRANT / REVOKE
🧠 口诀
D 建结构、D 改数据、D 查数据、D 管权限 —— 记「建、增删改、查、控」四件事。

创建数据库与表

-- 创建数据库（不存在才创建，指定 utf8mb4 编码）
CREATE DATABASE IF NOT EXISTS shop
  DEFAULT CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;

-- 使用该数据库
USE shop;

-- 创建用户表
CREATE TABLE users (
  id         BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键，自增',
  name       VARCHAR(50)  NOT NULL                COMMENT '用户名',
  age        INT          DEFAULT 0               COMMENT '年龄',
  email      VARCHAR(100) UNIQUE                  COMMENT '邮箱（唯一）',
  created_at DATETIME     DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  PRIMARY KEY (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';

修改与删除表

-- 添加一列
ALTER TABLE users ADD COLUMN phone VARCHAR(20);

-- 修改列类型
ALTER TABLE users MODIFY COLUMN age TINYINT;

-- 重命名列
ALTER TABLE users CHANGE COLUMN name username VARCHAR(50) NOT NULL;

-- 删除一列
ALTER TABLE users DROP COLUMN phone;

-- 添加索引
ALTER TABLE users ADD INDEX idx_name (username);

-- 删除表（连同结构）
DROP TABLE IF EXISTS users;

TRUNCATE vs DELETE

对比TRUNCATEDELETE
本质DDL（清空表）DML（逐行删除）
能否回滚通常不能（隐式提交）在事务内可回滚
自增主键重置为 1不重置
速度快（整表删除）慢（逐行 + 记日志）
能否带 WHERE不能能

04 DML：增删改

INSERT 插入

-- 指定列插入（推荐：明确、不怕表结构变化）
INSERT INTO users (name, age, email) VALUES ('张三', 25, 'zhangsan@example.com');

-- 一次插入多行
INSERT INTO users (name, age, email) VALUES
  ('李四', 30, 'lisi@example.com'),
  ('王五', 28, 'wangwu@example.com');

-- 全列插入（可省略列名，但必须与列顺序一致）
INSERT INTO users VALUES (NULL, '赵六', 22, 'zhaoliu@example.com', NOW());

UPDATE 更新

-- 更新指定行
UPDATE users SET age = 26 WHERE id = 1;

-- 一次更新多列
UPDATE users SET age = age + 1, city = '杭州' WHERE id = 2;

DELETE 删除

-- 删除指定行
DELETE FROM users WHERE id = 3;
⚠️ 避坑（重中之重）
UPDATE 和 DELETE 如果忘记写 WHERE，会修改/删除全表所有数据！生产环境务必：① 先 SELECT 确认要操作的行；② 开启事务，出错可 ROLLBACK；③ 写 WHERE 时习惯性先写。可开启 MySQL 的 sql_safe_updates 模式兜底。

05 DQL：基础查询

SELECT 基本结构

-- 查询所有列（开发中避免，用 * 会拖慢查询、无法命中覆盖索引）
SELECT * FROM users;

-- 查询指定列
SELECT name, age FROM users;

-- 去重 DISTINCT
SELECT DISTINCT city FROM users;

-- 别名 AS（可省略 AS）
SELECT name AS 姓名, age AS 年龄 FROM users;

SELECT 完整语法顺序

SELECT   列 / 表达式 / 函数
FROM     表
WHERE    行过滤条件
GROUP BY 分组字段
HAVING   分组后过滤
ORDER BY 排序字段 ASC|DESC
LIMIT    偏移量, 条数;
🧠 口诀（书写顺序 & 执行顺序）
书写顺序：SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT
执行顺序：FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
关键差异：SELECT 里的别名，在 WHERE 中不可用（WHERE 先执行），但在 ORDER BY 中可用。

常量、表达式与函数

-- 查询常量
SELECT 1, 'hello';

-- 表达式运算（AS 起别名）
SELECT name, age * 10 AS age_x10 FROM users;

-- 调用函数
SELECT name, LENGTH(name) AS name_len FROM users;

06 条件过滤与排序分页

比较运算与逻辑运算

-- 比较：=  !=  <  <=  >  >=  <>
SELECT * FROM users WHERE age >= 25;

-- 逻辑：AND（且） OR（或） NOT（非）
SELECT * FROM users WHERE age >= 25 AND city = '北京';

-- 注意优先级：AND 高于 OR，建议用括号明确
SELECT * FROM users WHERE (city = '北京' OR city = '上海') AND age > 25;

IN / BETWEEN / LIKE / IS NULL

-- IN：值在集合中
SELECT * FROM users WHERE city IN ('北京', '上海', '深圳');

-- BETWEEN：闭区间 [a, b]
SELECT * FROM users WHERE age BETWEEN 20 AND 30;

-- LIKE：模糊匹配  % 任意多字符  _ 单个字符
SELECT * FROM users WHERE name LIKE '张%';   -- 以"张"开头
SELECT * FROM users WHERE name LIKE '_四';   -- 第二个字是"四"

-- IS NULL：判断空值（不能用 = NULL）
SELECT * FROM users WHERE email IS NULL;
SELECT * FROM users WHERE email IS NOT NULL;
⚠️ 避坑：NULL 的三值逻辑
NULL 表示「未知」，email = NULL 的结果既不是真也不是假，而是 NULL，永远查不到结果。判断空值必须用 IS NULL / IS NOT NULL。同理，NOT IN 里若有 NULL 也会导致整个子查询结果异常。

ORDER BY 排序与 LIMIT 分页

-- 升序 ASC（默认） / 降序 DESC
SELECT * FROM users ORDER BY age DESC;

-- 多列排序：先按 age 降序，相同再按 id 升序
SELECT * FROM users ORDER BY age DESC, id ASC;

-- 分页：LIMIT 偏移量, 条数
SELECT * FROM users ORDER BY id LIMIT 0, 10;   -- 第 1 页（跳过 0 条，取 10 条）
SELECT * FROM users ORDER BY id LIMIT 10, 10;  -- 第 2 页（跳过 10 条，取 10 条）
🔔 注意
深分页（LIMIT 1000000, 10）会很慢，因为数据库要跳过前 100 万行。优化方法见第 15 章「深分页优化」。

07 聚合与分组

聚合函数

函数作用备注
COUNT(*)统计行数不忽略 NULL
COUNT(列)统计该列非 NULL 的行数忽略 NULL
SUM(列)求和忽略 NULL，仅数值
AVG(列)平均值忽略 NULL
MAX / MIN最大 / 最小值可用于日期、字符串
 
-- 用户总数、平均年龄、最大年龄
SELECT COUNT(*) AS total, AVG(age) AS avg_age, MAX(age) AS max_age
FROM users;

GROUP BY 分组

-- 按城市分组，统计每城市人数和平均年龄
SELECT city, COUNT(*) AS cnt, AVG(age) AS avg_age
FROM users
GROUP BY city;
🧠 口诀
用了 GROUP BY 后，SELECT 里能出现的列只有两类：分组字段本身和聚合函数，否则在严格模式下会报错（逻辑上也讲不通）。

HAVING vs WHERE

对比WHEREHAVING
作用时机分组前过滤行分组后过滤组
能否用聚合函数不能能（COUNT、SUM 等）
能否用列别名不能可以（MySQL 支持）
 
-- 先筛出 age >= 18 的行，再按城市分组，最后筛出人数 > 2 的城市
SELECT city, COUNT(*) AS cnt
FROM users
WHERE age >= 18
GROUP BY city
HAVING COUNT(*) > 2
ORDER BY cnt DESC;

08 多表连接 JOIN

为什么需要 JOIN

规范化的数据库会把数据拆到多张表（用户表、订单表、商品表），查询时需要用 JOIN 把它们「拼」起来。JOIN 的本质是按条件把两张表的行两两配对。

四种主要 JOIN

类型结果关键词
内连接只保留两表都匹配的行INNER JOIN
左连接保留左表全部 + 右表匹配（无则 NULL）LEFT JOIN
右连接保留右表全部 + 左表匹配（无则 NULL）RIGHT JOIN
全外连接两表全保留（MySQL 不直接支持）FULL OUTER JOIN
交叉连接笛卡尔积（每行都配对）CROSS JOIN
 
-- 假设有两张表：orders(订单) 和 users(用户)，orders.user_id 引用 users.id
-- INNER JOIN：只查有下单记录的用户
SELECT u.name, o.amount
FROM users u
INNER JOIN orders o ON o.user_id = u.id;

-- LEFT JOIN：查所有用户（含没下过单的，amount 为 NULL）
SELECT u.name, o.amount
FROM users u
LEFT JOIN orders o ON o.user_id = u.id;

-- LEFT JOIN 找"没下过单的用户"
SELECT u.name
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;

自连接（Self Join）

一张表连自己，典型场景是「员工-上级」这种层级关系。

-- 员工表 employees(id, name, manager_id)，查每个员工的上级姓名
SELECT e.name AS 员工, m.name AS 上级
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;

ON 与 WHERE 的区别

⚠️ 避坑
在 LEFT JOIN 中，ON 是连接条件，WHERE 是连接后的过滤。若把右表的过滤条件写到 WHERE 里，会把「无匹配」的行也过滤掉，效果就退化成 INNER JOIN 了。所以右表的过滤条件要写在 ON 里。

09 子查询与集合运算

子查询分类

  • 标量子查询：返回单个值，可用于比较。
  • 列子查询：返回一列多行，配合 IN / ANY / ALL。
  • 表子查询：返回一张表，常用于 FROM 后。
-- 标量子查询：查年龄大于平均年龄的用户
SELECT * FROM users WHERE age > (SELECT AVG(age) FROM users);

-- 列子查询 + IN：查下过单的用户
SELECT * FROM users WHERE id IN (SELECT DISTINCT user_id FROM orders);

-- 表子查询：把子查询结果当临时表
SELECT t.city, t.cnt FROM
  (SELECT city, COUNT(*) AS cnt FROM users GROUP BY city) t
WHERE t.cnt > 2;

EXISTS vs IN

-- EXISTS：判断子查询是否有结果（相关子查询）
SELECT * FROM users u
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
场景推荐原因
子查询结果小、外层大IN先执行子查询，小结果集驱动
外层小、子查询大EXISTS找到一条即返回，不必全查

集合运算 UNION

-- UNION 去重合并；UNION ALL 不去重（更快，推荐用 ALL 除非确需去重）
SELECT name FROM users
UNION ALL
SELECT name FROM vip_users;
🧠 口诀
UNION 合并去重、UNION ALL 合并不去重；列数、顺序、类型要一致。MySQL 原生不支持 INTERSECT/EXCEPT（可用 JOIN 或子查询替代）。

字符串函数

函数作用示例

日期函数

函数作用

CASE WHEN 条件分支

-- 写法一：简单 CASE（等值判断）
SELECT name,
  CASE city
    WHEN '北京' THEN '华北'
    WHEN '上海' THEN '华东'
    ELSE '其他'
  END AS region
FROM users;

-- 写法二：搜索 CASE（条件判断，更灵活）
SELECT name,
  CASE
    WHEN age < 18 THEN '未成年'
    WHEN age BETWEEN 18 AND 60 THEN '成年'
    ELSE '老年'
  END AS stage
FROM users;

NULL 处理函数

-- IFNULL(expr, 默认值)：expr 为 NULL 时返回默认值
SELECT name, IFNULL(city, '未知') FROM users;

-- COALESCE(a,b,c)：返回第一个非 NULL 的值（更通用）
SELECT name, COALESCE(city, province, '未知') FROM users;

-- IF(条件, 真值, 假值)：三元判断
SELECT name, IF(age >= 18, '成年', '未成年') AS tag FROM users;

11 视图、存储过程与触发器

视图（View）

视图是一张"虚拟表"，本质是一条被保存下来的 SELECT 查询。你可以像查表一样查视图，但它不存储数据，每次查询都实时执行底层 SQL。 

-- 创建视图：把常用联表查询封装成"表"
CREATE VIEW user_order_v AS
SELECT u.id, u.name, o.amount, o.created_at
FROM users u
LEFT JOIN orders o ON o.user_id = u.id;

-- 之后直接查视图，像查表一样
SELECT * FROM user_order_v WHERE amount > 100;
💡 提示
视图的好处：① 简化复杂查询；② 隐藏底层表结构；③ 做权限隔离（只暴露部分列）。缺点：不能建索引，性能取决于底层 SQL，多层嵌套视图会拖慢性能。

存储过程（Stored Procedure）

存储过程是保存在数据库里的一段可复用的 SQL 程序，可以带参数、写逻辑、返回结果，相当于「数据库里的函数」。 

-- 修改分隔符，避免分号提前结束定义
DELIMITER $$
CREATE PROCEDURE get_users_by_city(IN p_city VARCHAR(50))
BEGIN
  SELECT id, name, age FROM users WHERE city = p_city;
END$$
DELIMITER ;

-- 调用
CALL get_users_by_city('北京');

触发器（Trigger）

触发器是在表发生 INSERT/UPDATE/DELETE 时自动执行的程序，常用于自动记录日志、校验数据、联动更新。 

-- 每次向 users 插入数据后，自动往日志表写一条记录
CREATE TRIGGER trg_users_after_insert
AFTER INSERT ON users
FOR EACH ROW
BEGIN
  INSERT INTO user_log(user_id, action, created_at)
  VALUES (NEW.id, 'INSERT', NOW());
END;
对象本质何时执行典型用途
视图保存的查询被查询时简化查询、权限隔离
存储过程保存的程序被 CALL 时批量处理、业务逻辑下沉
触发器自动执行的程序表数据变动时审计日志、数据校验
🔔 注意
现代互联网公司普遍倾向「把业务逻辑放应用层」，存储过程/触发器因难以调试、难迁移、易隐藏 bug 而用得较少，但传统企业和财务系统仍广泛使用。了解即可，不必过度使用。

12 索引原理与优化

为什么索引能加速查询

没有索引时，数据库要全表扫描，一行一行找；有了索引，就像书的目录，直接定位到相关页。索引的本质是「用空间换时间」——额外维护一份有序的数据结构来加速查找。

B+ 树索引

MySQL 的 InnoDB 引擎默认用 B+ 树存储索引。B+ 树是一棵平衡多叉树：数据只存在叶子节点，叶子节点之间用链表相连。这样既能快速查找（树高很低，几次磁盘 IO 就能定位），又方便范围查询（顺着链表扫）。

聚集索引 vs 非聚集索引

对比聚集索引（聚簇）非聚集索引（二级）
叶子存什么整行数据主键值
每表数量只能 1 个（通常是主键）可有多个
查找流程直接拿到数据拿到主键后再回表查（回表）
🧠 口诀
主键即聚集索引；二级索引叶子存主键，查到后要「回表」拿完整行。若查询的列全在索引里，就不用回表，称为「覆盖索引」，性能最好。

联合索引与最左前缀

-- 建联合索引（按 a, b, c 顺序）
CREATE INDEX idx_abc ON t (a, b, c);

-- 能用上索引（遵循最左前缀）
SELECT * FROM t WHERE a = 1;            -- 命中 a
SELECT * FROM t WHERE a = 1 AND b = 2;  -- 命中 a, b
SELECT * FROM t WHERE a = 1 AND b = 2 AND c = 3; -- 全命中
SELECT * FROM t WHERE a = 1 AND c = 3;  -- 只命中 a（b 断档，c 用不上）

-- 用不上索引（跳过最左列 a）
SELECT * FROM t WHERE b = 2;
SELECT * FROM t WHERE c = 3;
🧠 口诀（最左前缀）
联合索引像「先按姓、再按名排序的电话簿」：跳过姓直接查名，索引就失效。中间字段断档，后面的字段也用不上。

索引失效的常见场景

  • 对索引列做函数运算：WHERE YEAR(created_at) = 2024。
  • 对索引列做隐式类型转换：WHERE phone = 13800000000（phone 是 VARCHAR，应加引号）。
  • 前导模糊：LIKE '%张'（以 % 开头用不上索引；LIKE '张%' 可以）。
  • 违反最左前缀（联合索引跳列）。
  • OR 连接了非索引列。
  • 优化器判断全表扫描更快（数据量小、区分度低时不走索引反而正常）。
⚠️ 避坑
索引不是越多越好：每个索引都要占用存储，且增删改时都要维护索引，会拖慢写入。只在高频查询的 WHERE/ORDER BY/JOIN 字段上建索引，避免低区分度列（如性别）单独建索引。

13 事务与并发控制

事务与 ACID

事务（Transaction）是一组要么全成功、要么全失败的 SQL 操作。经典比喻：转账——从 A 扣钱、给 B 加钱，两步必须同时成功，否则钱就凭空消失。

特性含义说明
原子性 Atomicity不可分割要么全做，要么全不做
一致性 Consistency状态合法转账前后总额不变
隔离性 Isolation互不干扰并发事务之间看不到中间态
持久性 Durability落盘不丢提交后即使宕机也不丢数据
 
-- 手动控制事务
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;      -- 提交（成功）
-- 或 ROLLBACK; 回滚（失败，撤销所有改动）

并发带来的三大问题

问题描述
脏读读到别的事务未提交的数据（可能被回滚）
不可重复读同一事务内两次读同一条数据，结果不同（别人改了）
幻读同一事务内两次查询，行数不同（别人插/删了）

四种隔离级别

隔离级别脏读不可重复读幻读
读未提交 Read Uncommitted可能可能可能
读已提交 Read Committed否可能可能
可重复读 Repeatable Read（MySQL 默认）否否基本解决
串行化 Serializable否否否
🧠 口诀
隔离级别越高，一致性越好，但并发性能越差。MySQL 默认「可重复读」，靠 MVCC（多版本并发控制）+ 间隙锁解决幻读。

MVCC 简介

MVCC（多版本并发控制）的核心思想：读不加锁、写不阻塞读。每次修改不覆盖旧数据，而是生成一个「新版本」，每条记录带上版本号（隐藏列）。读操作通过版本号读到「符合自己事务快照」的旧版本，从而实现高并发下的一致性读。

死锁

⚠️ 避坑
两个事务互相等待对方释放锁就形成死锁。预防：① 事务尽量短小；② 按一致的顺序访问多张表/多行；③ 合理设计索引减少锁范围。发生死锁时 InnoDB 会自动回滚其中一个事务，应用层做好重试即可。

14 数据库设计与范式

ER 模型

设计数据库前，先用 ER 图（实体-关系图）梳理业务：实体（Entity，如用户、订单）画成矩形，属性画成椭圆，关系（如用户「下单」订单）画成菱形，并标注「一对一 / 一对多 / 多对多」。

三大范式

第一范式（1NF）：列不可再分

每列都是原子值，不能存多个值。反例：一列存「手机号1,手机号2」。

第二范式（2NF）：消除部分依赖

在满足 1NF 基础上，非主键列必须完全依赖整个主键（针对联合主键）。反例：成绩表主键是（学号, 课程号），但「学生姓名」只依赖学号，属于部分依赖，应拆出去。

第三范式（3NF）：消除传递依赖

在满足 2NF 基础上，非主键列不能依赖其他非主键列。反例：学生表里有「学号 → 班级号 → 班主任」，班主任通过班级号传递依赖学号，应拆到班级表。

范式核心要求解决什么
1NF列不可再分字段原子性
2NF消除部分依赖联合主键下非键字段冗余
3NF消除传递依赖非键字段间的冗余
BCNF消除主属性间的部分依赖更严格的 3NF
🧠 口诀
「1 拆列、2 拆部分、3 拆传递」。范式的本质是减少冗余、避免更新异常。实际开发中一般做到 3NF 即可。

反范式（适度冗余）

范式不是绝对的。为了查询性能，有时要故意「反范式」——保留冗余字段（比如订单表冗余存「商品名」「单价」），避免每次查询都 JOIN。原则是：以读为主、牺牲一点存储和写一致性换取查询性能。

15 SQL 性能优化实战

用 EXPLAIN 分析执行计划

EXPLAIN SELECT * FROM users WHERE name = '张三';
关键字段含义重点关注
type访问类型（好→差：const > eq_ref > ref > range > index > ALL）出现 ALL 说明全表扫描
key实际使用的索引NULL 表示没走索引
rows预估扫描行数越大越慢
Extra附加信息Using filesort / temporary 需优化

慢查询定位

-- 开启慢查询日志（记录执行超过 1 秒的 SQL）
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;

常用优化策略清单

  • 尽量避免 SELECT *，只查需要的列。
  • 在 WHERE / ORDER BY / JOIN 字段上建合适索引。
  • 小表驱动大表，联表时先过滤再连接。
  • 避免在索引列上做函数、运算、隐式转换。
  • 用 EXISTS 替代部分 IN，用 UNION ALL 替代 UNION。
  • 大表拆分、冷热数据分离、合理归档。

深分页优化

-- 慢：要扫描并丢弃前 100 万行
SELECT * FROM users ORDER BY id LIMIT 1000000, 10;

-- 快：先定位到上次的 id，再往后取（游标式/基于主键）
SELECT * FROM users WHERE id > 1000000 ORDER BY id LIMIT 10;
💡 提示
深分页优化的核心是「避免大偏移量」：用「游标 + 主键/唯一索引」代替 LIMIT offset, n，或先用子查询定位主键再回表。

16 主从复制与高可用

为什么需要主从复制

  • 读写分离：主库写、从库读，分摊压力。
  • 数据备份：从库是天然的热备。
  • 故障转移：主库挂了，从库顶上。

复制原理

  1. 主库把数据变更写入二进制日志 binlog。
  2. 从库的 I/O 线程把主库 binlog 拉过来，写入中继日志 relay log。
  3. 从库的 SQL 线程重放 relay log，完成数据同步。

复制是异步的（默认），因此主从之间可能存在毫秒级延迟。

读写分离架构

应用层通过中间件（如 ShardingSphere、MyCat，或框架自带的路由）把写请求路由到主库、读请求路由到从库。读多写少的场景下能显著提升吞吐。

⚠️ 避坑
读写分离会带来主从延迟：刚写入的数据立刻读从库可能读不到。解决：① 核心读写都走主库；② 业务上允许短暂延迟；③ 或使用半同步复制降低延迟。

高可用方案

方案说明
主从 + 手动切换简单但依赖人工，切换慢
MHA / Orchestrator自动监控、故障切换
MGR（组复制）多主、自动选主、强一致
云数据库 RDS托管高可用，自动主备切换（生产首选）

17 分库分表与分布式

什么时候需要分库分表

单表数据量过大（如上亿行）、单库连接数和 IO 达到瓶颈时，就要考虑分库分表。核心思想是把大问题拆成小问题，让数据分散到多个库、多张表。

垂直拆分 vs 水平拆分

维度垂直拆分水平拆分
怎么拆按业务/按列拆（把宽表拆成多张）按行拆（把行分散到多表/多库）
典型用户表拆成：基础信息表 + 扩展信息表订单表按用户 id 分 16 张表
解决问题单表过宽、单库过大单表数据量过大

分片键（Sharding Key）的选择

  • 尽量选择查询频繁、区分度高的字段（如用户 id、订单号）。
  • 让大部分查询都能命中单个分片，避免跨分片查询。
  • 避免用会变化的字段做分片键（如状态）。
  • 常见算法：取模、范围、哈希（一致性哈希）。

分布式 ID

分库分表后，单表自增主键会重复，需要全局唯一 ID：

  • 雪花算法（Snowflake）：64 位，时间戳 + 机器号 + 序列号，趋势递增、高性能。
  • 数据库号段：集中发号，一次取一批。
  • UUID：简单但无序，影响索引性能（一般不用做主键）。

常见中间件

中间件类型特点
ShardingSphere框架/JDBC 层Apache 顶级项目，生态好，Java 首选
MyCat代理层独立进程，对应用透明
🔔 注意
分库分表是「最后手段」，代价很大（跨库 JOIN 难、事务变复杂、运维复杂）。先做好索引、缓存、读写分离、冷热分离，实在扛不住再分库分表。

18 NoSQL 与数据库选型

CAP 理论

分布式系统无法同时满足三者，只能三选二：C 一致性（读到的都是最新）、A 可用性（总能有响应）、P 分区容错（网络分区仍工作）。实际中 P 必须保证，于是只能在 C 和 A 之间取舍。

主流 NoSQL 及适用场景

数据库类型强项典型场景
Redis键值 / 内存极快、丰富数据结构、支持过期缓存、计数器、分布式锁、排行榜
MongoDB文档Schema 灵活、JSON 友好内容管理、日志、快速迭代业务
Elasticsearch搜索全文检索、倒排索引搜索引擎、日志分析（ELK）
HBase列族海量数据、稀疏存储大数据实时读写

Redis 数据结构速览

类型场景举例
String缓存、计数器、分布式锁
Hash存对象（用户信息）
List消息队列、最新消息列表
Set去重、共同好友、标签
ZSet排行榜、延迟队列

选型口诀

🧠 选型口诀
事务关系型 → MySQL/PG；高并发缓存 → Redis；灵活文档 → MongoDB；全文搜索 → ES；海量分析 → 列存（ClickHouse）/Hadoop 系。大多数系统是「MySQL 主存 + Redis 缓存 + ES 搜索」的组合，而非二选一。

19 学习路线与实战建议

学习路线

  1. 打基础：理解数据库概念、表结构、SQL 四大分类，把增删改查练熟。
  2. 会查询：掌握 JOIN、子查询、聚合分组、常用函数，能写出任意业务查询。
  3. 懂原理：理解索引（B+ 树）、事务（ACID、隔离级别）、锁与 MVCC。
  4. 会设计：用 ER 图建模，掌握三大范式与反范式取舍。
  5. 能优化：会用 EXPLAIN、慢查询日志，掌握常见优化手段。
  6. 懂架构：了解主从复制、读写分离、分库分表、高可用。
  7. 会选型：熟悉 Redis、MongoDB、ES 等 NoSQL，能根据业务选型。
