01 认识微信小程序与生态

小程序是什么

微信小程序是一种运行在微信内的「轻应用」：无需下载安装、扫码即用、用完即走。技术上它既不是纯 H5，也不是原生 App，而是「逻辑层（JS 引擎）+ 渲染层（WebView）」双线程架构，通过微信提供的能力桥接，能调用 摄像头、定位、支付、蓝牙等原生能力。

对比项 小程序 H5（公众号网页） 原生 App
安装成本 无需安装，微信内即用 无需安装，浏览器打开 需下载安装包
体验与能力 接近原生，可调系统能力 受浏览器限制较多 体验最佳，能力最全
开发成本 低（前端技术栈） 低（纯 Web） 高（iOS/Android 双端）
获客路径 扫码/搜索/分享，用完即走 依赖浏览器与链接传播 应用商店下载，转化成本高
审核发布 微信审核（一般较快） 无需审核（域名需备案） 应用商店审核严格

双线程模型：为什么页面不卡

小程序把 JS 逻辑和界面渲染拆到两个线程：

  • 逻辑层（App Service）：运行 JS，处理数据与业务，不能直接操作 DOM。
  • 渲染层（WebView）：负责 WXML/WXSS 的渲染与交互响应。
  • 两层靠 setData 通信：逻辑层把数据序列化后传给渲染层，驱动界面更新。
💡 一句话理解
双线程是为了安全与稳定：渲染层像「前台服务员」，逻辑层像「后台厨房」——前台不能碰后台数据，点单（事件）和上菜（setData）都要走传话通道。这也解释了为什么 setData 传大数据会卡：传话内容越多，上菜越慢。

小程序的生态全景

维度 入口 / 能力 说明
用户入口 扫码、搜索、分享卡片、公众号菜单、下拉任务栏 「就近展示」——附近的小程序、二维码扫码是线下核心入口
商业能力 微信支付、商家券、视频号带货、小程序直播 交易闭环都在微信内完成
流量分发 搜一搜、发现-小程序、广告投放、分享裂变 好友/群分享是天然裂变渠道
开放能力 登录、订阅消息、获取手机号、定位、蓝牙、NFC 基础库按需开放，部分需企业认证
云能力 云开发（云函数/数据库/存储/托管） 免自建服务器，适合快速起步
⚠️ 避坑提示
小程序有代码包体积限制：单个主包/分包不超过 2MB，所有分包总计不超过 20MB（平台新规已逐步放宽，以官方最新公告为准）。图片、字体、大库都别堆在代码包里，要放 CDN 或云存储。
🧠 速记口诀
「扫码即用用完走，双线程里 setData 传；轻应用要轻包装，2M 包体是红线」——记住定位与约束，开发思路就对了。

02 环境搭建与项目结构

注册账号与安装工具

开发前需要完成三步准备：

Step 1 · 注册

进入「微信公众平台」（mp.weixin.qq.com）注册小程序账号，获取 AppID（个人也能注册，但支付、获取手机号等能力需企业主体）。

Step 2 · 安装开发者工具

下载「微信开发者工具」（稳定版），支持 Windows/macOS，内置模拟器 + 调试器 + 代码编辑器。

Step 3 · 创建项目

用 AppID 创建项目（没有 AppID 可选「测试号」）。模板可选 JavaScript / TypeScript / 云开发，学习期建议从「JS 基础模板」开始。

主体类型 个人 企业 / 组织
注册门槛 身份证即可 需营业执照、对公账户等
微信支付 ✗ 不支持 ✓ 支持（需商户号）
获取手机号 / 订阅消息长期类 受限 ✓ 支持
类目覆盖 偏内容/工具类 几乎全类目（电商、餐饮等）

app.json：小程序的「总控台」

{
  "pages": ["pages/index/index", "pages/list/list"],
  "window": {
    "navigationBarTitleText": "我的小程序",
    "navigationBarBackgroundColor": "#07c160",

  },
  "tabBar": {
    "color": "#999",
    "selectedColor": "#07c160",

      { "pagePath": "pages/index/index", "text": "首页" },
      { "pagePath": "pages/list/list", "text": "列表" }

配置项 作用 备注

WXML 三大核心语法

WXML 是「类 HTML」模板，核心就三件事：绑数据、列列表、判条件。

<!-- 1. 数据绑定：{{ }} 里写表达式 -->
<view>{{message}}</view>
<view>{{a + b}} · {{isVip ? '会员' : '普通'}}</view>

<!-- 2. 列表渲染：wx:for + wx:key -->
<view wx:for="{{list}}" wx:key="id">
  {{index}} - {{item.name}}
</view>

<!-- 3. 条件渲染：wx:if 系列 -->
<view wx:if="{{score >= 60}}">及格</view>
<view wx:elif="{{score >= 30}}">加油</view>
<view wx:else>不及格</view>

<!-- 属性绑定 & 事件 -->
<image src="{{imgUrl}}" mode="aspectFill" />
<button bindtap="handleTap" data-id="{{item.id}}">按钮</button>
语法 说明 注意点
{{ }} Mustache 表达式 可做简单运算、三元、字符串拼接，不能写语句
wx:for 遍历数组渲染 默认变量 item/index，可用 wx:for-item 改名
wx:key 列表 diff 优化键 用唯一 id 或 *this，别用 index（列表会变时易错位）
wx:if 条件渲染（真移除/真创建） 切换代价高，适合低频分支
hidden 条件渲染（仅隐藏） 节点常驻，适合高频切换
⚠️ 避坑提示
wx:if 与 hidden 别混用场景：列表项/表单这类「要保留状态的组件」用 hidden；而首屏登录态等「切走就不该存在」的用 wx:if。另外 wx:for 与 wx:if 写在同一节点时，wx:for 优先级更高（先循环再判断），性能差且易踩坑，建议拆开写。
🧠 速记口诀
「双花括号绑数据，wx:for 循环加 key；条件用 if 藏用 hidden，for 和 if 莫同框」——模板三件套，背熟就够用。

04 WXSS 样式与 rpx 适配

WXSS = CSS + rpx + 样式隔离

WXSS 基本就是 CSS，多了响应式单位 rpx，同时样式默认「页面隔离」：页面样式不会串到别的页面，自定义组件默认也不受页面样式影响（组件样式隔离）。

  • 750rpx = 屏幕宽度：任何机型上，750rpx 都恰好是一屏宽，无需媒体查询即可自适应。
  • 设计稿按 750 宽 出图时，px 数值可直接写 rpx，1:1 换算。
  • 全局样式写 app.wxss；页面样式写页面自己的 .wxss。
单位 换算关系 适用场景
rpx 750rpx = 屏宽（随机型缩放） 布局、字号、间距首选
px 固定物理逻辑像素 1px 边框、固定小元素
vh / vw 视口高度/宽度的 1% 全屏容器、弹层定位
% 相对父容器 常规百分比布局

Flex 布局：小程序的「主流布局」

/* 经典：一行三个等宽卡片 */
.row {
  display: flex;
  justify-content: space-between;
}
.row .item {
  width: 230rpx;   /* (750 - 2*30rpx间距 - 2*10rpx缝隙) / 3 */
  height: 230rpx;
}

/* 垂直居中（移动端 90% 居中需求） */
.center {
  display: flex;
  align-items: center;
  justify-content: center;
}

/* 按钮文字不换行 + 溢出省略 */
.ellipsis {
  overflow: hidden;
  white-space: nowrap;
  text-overflow: ellipsis;
}

尺寸换算速查（以 iPhone 6/7/8 为基准）

设计稿宽度 换算口诀 示例（设计稿 16px）
750px 1px = 1rpx 写 16rpx
375px（iPhone 逻辑宽度） 1px = 2rpx 写 32rpx
其他宽度 W rpx = px × 750 ÷ W —
💡 一句话理解
记住一个基准：设计稿 750 宽 → 原样照抄 px 为 rpx。UI 给 375 宽的稿子就把数字乘 2。这是小程序开发最常用的「心算」。
⚠️ 避坑提示
部分 Web 写法在小程序里不可用：* 通配符选择器、body/html 标签选择器在页面中无效；本地字体/背景图不支持引用远程绝对路径外链 CSS（要用 @import 导入本地 wxss 或放到 CDN）。样式也别依赖 !important 硬怼，组件样式隔离时它救不了你。
🧠 速记口诀
「750 稿子 1:1 写 rpx，flex 横行打天下；页面样式互不扰，通配 body 全失效」——WXSS 的差异点就这么几条，先记住再写样式。

05 逻辑层与页面生命周期

Page()：页面的「大脑」

每个页面由 Page({...}) 描述，包含 data、生命周期、事件与自定义方法。

// pages/detail/detail.js
Page({
  // 1. 页面数据：模板里直接可用 {{id}}
  data: { id: '', list: [], loading: true },

  // 2. 生命周期
  onLoad(options) {
    // 页面创建时执行一次，options 是 URL 参数
    this.setData({ id: options.id })
    this.fetchDetail(options.id)
  },
  onShow() { /* 每次进入页面 */ },
  onReady() { /* 首次渲染完成 */ },
  onHide() { /* 页面隐藏（切后台/跳页） */ },
  onUnload() { /* 页面销毁 */ },
  onPullDownRefresh() { /* 下拉刷新 */ },
  onReachBottom() { /* 触底加载更多 */ },

  // 3. 自定义方法（供 bindtap 等调用）
  fetchDetail(id) {
    // 模拟请求
    setTimeout(() => {
      this.setData({ list: [{ id, title: '商品' + id }], loading: false })
    }, 300)
  }
})

生命周期时序

阶段 回调 典型用途
创建 onLoad(options) 读 URL 参数、初始化数据
onShow() 每次展示都触发：刷新状态、埋点
运行 onReady() 首次渲染完成，可交互（拿节点信息）
onHide() 切后台/跳转他页：暂停定时器、音乐
销毁 onUnload() 清理监听、释放资源

setData：唯一的「改界面通道」

// 直接改 this.data 不会更新界面！必须走 setData
this.setData({
  'user.name': '小明',   // 支持路径式更新深层字段
  'cart[0].count': 2
})

// 更新后立即读取的是旧值（异步渲染），如需拿最新值用回调
this.setData({ count: 3 }, () => {
  console.log('渲染完成，最新值', this.data.count)
})
⚠️ 避坑提示
别把整个大对象一把 setData（如整页 JSON）——数据要序列化跨线程传输，数据越大越卡。最佳实践：只更新变化的最小字段，列表类用「路径 + 下标」精准更新。

事件绑定：bind 与 catch

写法 行为 场景
bindtap 事件冒泡（可继续触发父级） 常规点击
catchtap 阻止冒泡（stopPropagation） 卡片内按钮不想触发卡片点击
mut-bind 互斥绑定 特殊场景（较新基础库）
capture-bind / capture-catch 捕获阶段监听 / 拦截 需要先于子级处理的场景
💡 一句话理解
dataset 是给事件「捎话」的：<view data-id="5"> 被点击后，事件对象里 e.currentTarget.dataset.id === '5'。列表页给每项传 id 全靠它，别再用全局变量存「当前点击的是谁」。
🧠 速记口诀
「加载读参 onLoad，展示刷新 onShow；改界面只认 setData，最小字段最省心；冒泡用 bind，拦住用 catch」——页面逻辑三板斧：生命周期 + setData + 事件。

页面跳转 API 对比

API 行为 栈行为
wx.navigateTo 跳新页面（可返回） 入栈，最多 10 层
wx.redirectTo 关闭当前页跳新页 替换栈顶
wx.switchTab 跳 tabBar 页面 关闭所有非 tab 页

⚠️ 避坑提示

🧠 速记口诀
「反馈三兄弟 toast、loading、modal；跳页五虎将 push 用 navigate，回退 navigateBack，tab 用 switchTab，清栈 reLaunch」——交互与导航，先背这组 API 就够入门。

07 网络请求与数据缓存

wx.request：请求服务器数据

小程序发请求用 wx.request，注意必须先配置合法域名（开发工具可勾选「不校验域名」临时调试，真机/上线必须 HTTPS 且已在后台配置）。

wx.request({
  url: 'https://api.example.com/v1/goods',
  method: 'GET',
  data: { page: 1, size: 10 },
  header: { Authorization: 'Bearer ' + token },
  success(res) {
    if (res.statusCode === 200) {
      console.log(res.data)   // 业务数据
    }
  },
  fail(err) {
    wx.showToast({ title: '网络异常', icon: 'none' })
  }
})

封装 Promise 版 request（项目标配）

// utils/request.js
const BASE_URL = 'https://api.example.com/v1'

function request(path, method = 'GET', data = {}) {
  return new Promise((resolve, reject) => {
    wx.request({
      url: BASE_URL + path,
      method,
      data,
      header: { Authorization: wx.getStorageSync('token') || '' },
      success(res) {
        if (res.statusCode === 200 && res.data.code === 0) {
          resolve(res.data.data)
        } else if (res.statusCode === 401) {
          // token 失效：跳登录
          wx.removeStorageSync('token')
          wx.navigateTo({ url: '/pages/login/login' })
          reject(res)
        } else {
          wx.showToast({ title: res.data.msg || '请求失败', icon: 'none' })
          reject(res)
        }
      },
      fail: reject
    })
  })
}

  get: (p, d) => request(p, 'GET', d),
  post: (p, d) => request(p, 'POST', d)

  success(res) {

      method: 'POST',

12 分包加载与性能优化

为什么需要分包

主包 2MB 的天花板下，业务多了必然超限。分包把代码按「访问路径」拆开：用户进哪个功能，才下载哪个包，首包更小、启动更快。

// app.json：分包配置
{
  "pages": ["pages/index/index", "pages/cart/cart"],
  "subpackages": [
    {
      "root": "packageGoods",
      "name": "商品模块",
      "pages": [
        "pages/detail/detail",
        "pages/search/search"
      ]
    },
    {
      "root": "packageOrder",
      "pages": ["pages/order/list/list"],
      "independent": true    // 独立分包：不依赖主包，可单独加载
    }
  ],
  "preloadRule": {
    "pages/index/index": {
      "network": "all",
      "packages": ["packageGoods"]   // 首页空闲时预下载商品包
    }
  }
}
概念 说明
普通分包 依赖主包（可访问主包资源），随主包一起下发但不随启动加载
独立分包 不依赖主包，可独立运行；适合分享落地页（如活动页、邀请页）
分包预下载 配置 preloadRule，在空闲/特定网络下提前下载分包
分包异步化 主包可 require 分包 JS / 引用分包组件（需基础库 2.20.1+）
⚠️ 避坑提示
① tabBar 页面必须放主包，不能放分包； ② 分包之间不能互相 require（独立分包尤其严格）； ③ 主包也要瘦身：把公共大库（如图表库）按需引入，图片一律外链； ④ 上线前看「详情-代码质量-包体积」报告，超限直接上传失败。

性能优化 Checklist

维度 手段 收益
启动 分包 + 预下载 + 首屏只渲染必要组件 首屏时间明显下降
setData 最小字段、路径更新、合并多次、节流高频更新 减少跨线程通信量
图片 WebP/压缩、CDN、懒加载 lazy-load、占位图 省流量、防白屏
列表 分页加载、虚拟列表（recycle-view）、图片懒加载 长列表不卡
渲染 避免大 wx:for 嵌套、避免在 onShow 里重复拉全量数据 减少渲染压力
网络 接口并发、缓存幂等数据（Storage）、预请求 弱网体验更好
💡 一句话理解
性能优化的本质是「少干活」：少传数据（setData 最小化）、少下文件（分包+图片瘦身）、少渲染（虚拟列表）、少请求（缓存）。别一上来就上框架，先按这四「少」自查。
🧠 速记口诀
「主包两兆是红线，分包拆开预下载；setData 要最小化，图片瘦身列表虚」——性能优化记住「分包 + 四少」。

behaviors：组件的「mixins」

多个组件有相同的 data、方法、生命周期时，抽成 behavior 复用，类似 Vue 的 mixin。

// behaviors/loading.js —— 通用「加载中」逻辑
module.exports = Behavior({
  data: { loading: false, hasMore: true },
  methods: {
    startLoading() { this.setData({ loading: true }) },
    finishLoading() { this.setData({ loading: false }) }
  }

// components/goods-list/index.js —— 直接复用
const loadingBehavior = require('../../behaviors/loading')

Component({
  behaviors: [loadingBehavior],
  data: { list: [] },

    load() {
      this.startLoading()   // 来自 behavior
      // ...拉数据
      this.finishLoading()
    }
  }
})
💡 一句话理解
behaviors 的合并规则要记：data 浅合并，方法直接覆盖（组件自身优先于 behavior，后引入的 behavior 优先于先引入的）；同名字段/方法，优先级 组件 > 后 behavior > 先 behavior。

relations：组件间的「亲属关系」

父组件与子孙组件需要直接通信（如 tab 容器管理多个 tab-pane）时用 relations。

// components/tabs/index.js —— 父组件
Component({
  relations: {
    '../tab-pane/index': {
      type: 'child',              // 关联子组件
      linked(target) {
        // 子组件挂载时触发：登记起来
        this._panes = this._panes || []
        this._panes.push(target)
      },
      unlinked(target) {
        this._panes = (this._panes || []).filter(p => p !== target)
      }
    }
  },
  methods: {
    switchTo(index) {
      // 通知所有子 pane 切换
      this._panes.forEach((pane, i) => pane.setActive(i === index))
    }
  }
})

接口鉴权与防刷

// 后端鉴权最小实践（Node 伪代码）
1. 登录：code + appid + secret → 微信 code2session → openid
2. 签发 token：jwt.sign({ openid }, SECRET, { expiresIn: '7d' })
3. 校验：每个接口解析 Authorization，验签 + 查过期
4. 防刷：同 openid 限频（如 1 秒 1 次写操作）
5. 敏感接口：二次校验（签名 = md5(参数 + salt + timestamp)）

// 前端配合
header: { Authorization: `Bearer ${token}`, 'X-Ts': Date.now() }
风险 攻击方式 防御手段
越权（IDOR） 改订单号/用户 ID 访问他人数据 后端一律以 token 中的 openid 为准，不信前端传的 userId
重放 抓包重复提交订单/领券 幂等键、时间戳 + 签名、服务端去重
刷接口 脚本高频调用 限频、验证码、风控
敏感信息泄露 接口返回多余字段（手机号、openid） 最小化返回、字段脱敏
密钥泄露 appsecret 写进前端被打包逆向 密钥只存后端/云函数环境变量

隐私合规：2023 年后的用户信息规则

  • 头像昵称：不能再静默 wx.getUserProfile 弹窗拿头像昵称。改为：头像用 button open-type="chooseAvatar"，昵称用 input type="nickname"，让用户主动填写/选择。

  • 手机号：必须企业主体 + 用户主动点击 button open-type="getPhoneNumber"，且手机号组件有调用频率限制。

① 未声明用途就收集隐私信息 → 审核驳回 + 能力封禁； ② 强制用户授权（不授权不让用）→ 违规，须提供「拒绝仍可用」的降级路径； ③ 采集位置/通讯录等敏感信息必须弹窗说明用途，且只在对应功能时请求； ④ 不得诱导用户开启「始终允许位置」。
🧠 速记口诀
「域名 HTTPS 先备案，密钥只在后端藏；越权全凭 token 判，头像昵称靠主动填；隐私声明先写好，审核合规不踩雷」——安全合规五条线，背完再上线。

微信支付：一次完整的支付链路

Step 1 · 后端统一下单

前端把「订单号 + 金额」发给后端；后端调微信支付 统一下单 接口，拿到 prepay_id。

Step 2 · 后端签名

后端用 prepay_id 生成调起支付所需参数（timeStamp、nonceStr、package、signType、paySign）——签名必须在后端做。

Step 3 · 前端调起支付

前端拿到参数后调 wx.requestPayment，微信弹出支付面板。

Step 4 · 回调验签

微信异步通知后端支付结果，后端验签 + 改订单状态，再给前端回执。 

// 前端调起支付（参数全部由后端返回）
wx.requestPayment({
  timeStamp: res.timeStamp,
  nonceStr: res.nonceStr,
  package: res.package,      // 'prepay_id=xxx'
  signType: 'RSA',
  paySign: res.paySign,
  success() { wx.showToast({ title: '支付成功' }) },
  fail() { /* 用户取消/失败，别自动重扣 */ }
})

// 支付结果以【后端回调】为准，不要信任前端的 success
🚫 红线提醒
① 支付金额/订单状态必须后端校验，前端传金额是重大漏洞； ② 必须处理「支付成功但回调没到」：用主动查单兜底； ③ 沙箱/测试别用真实金额；商户密钥泄露要立即重置。

request:fail url not in domain list 域名未配置 / 非 HTTPS 后台加合法域名；真机禁止勾选「不校验」
page not found / 找不到页面 页面未注册或路径错 检查 app.json pages 与文件名大小写
Component is not found usingComponents 路径错 用绝对路径 /components/xx/index 最稳
setData 报错 / 页面卡顿 数据过大或死循环更新 最小化 setData、检查观察者死循环
上传提示包体积超限 主包 > 2MB 图片外链、大页面分包、删除无用代码
真机白屏 / 模拟器正常 基础库差异、域名、缓存旧版 看 vConsole 日志；清缓存；升基础库
授权弹窗不出现 隐私协议未配置 / 已拒绝过 后台配隐私指引；用 open-type 引导重新授权
getUserProfile 返回匿名 平台规则调整 改用 chooseAvatar + nickname 输入
审核被拒 类目不符 / 隐私 / 诱导 按拒审原因逐条整改，附测试说明
⚠️ 避坑提示
开发前先读一遍《微信小程序平台运营规范》与《用户隐私保护指引要求》——很多「上线前才发现的坑」（类目资质、隐私弹窗、诱导分享、虚拟支付限制）其实规范里都写了。另外 iOS 上虚拟支付（买会员、充值）受限，涉及虚拟商品要提前设计合规方案。

推荐学习路线

第 1 周 · 入门

注册账号、跑通 Hello World；吃透四件套 + WXML/WXSS + setData + 生命周期。目标：能做一个静态展示页 + 列表详情跳转。

第 2 周 · 进阶

wx.request 封装、登录流程、自定义组件、表单与轮播。目标：完成一个 真实接口驱动的信息流小程序。

第 3 周 · 高级

分包与性能优化、云开发全栈（云函数 + 云数据库）、订阅消息。目标：做一个带后端的完整小工具并发布体验版。

第 4 周 · 精通

支付链路、隐私合规自查、TypeScript 改造、miniprogram-ci 自动化。目标：独立上线并持续迭代一款正式小程序。

🧠 速记口诀
「先跑通四件套，再封装请求做登录；分包优化提体验，云开发能全栈；合规红线心中记，独立上线是终点」——按这条路线走完，你就能从「会写页面」到「能交付产品」。
