01 Git 是什么与核心概念

版本控制解决什么问题

Git 是一个分布式版本控制系统（DVCS），用来记录文件每次改动的「快照」。没有版本控制时，你只能这样备份：

  • 文件名带日期：report_final_v2_最终版_改.docx（三天后又冒出一个「真最终版」）
  • Ctrl+C 复制文件夹：改了哪个、为什么改、想回退到哪个版本，全靠记忆
  • 多人协作靠网盘互传：你改完我改，谁覆盖谁说不清

Git 把这一切变成一条可回溯、可分支、可协作的时间线：每一次提交（Commit）都是一份完整快照，随时可以回到任意历史节点。

集中式 vs 分布式

对比项集中式（SVN）分布式（Git）
仓库存放只有服务器一份中央仓库每个开发者本地都有完整仓库
离线工作无法提交、无法看历史完全离线可用，提交/回滚/分支都行
服务器挂了整个团队瘫痪任何人本地仓库都能恢复
分支成本贵且慢，大家不敢乱开极便宜，鼓励多分支并行
协作模型集中提交Pull + Push + Pull Request 多种

Git 三个核心区域

理解 Git 最重要的模型：文件在三个区域之间流转。

区域比喻怎么进入
工作区（Working Directory）你的「办公桌」——正在编辑的文件git init / clone 后默认就在
暂存区（Index / Staging）「待提交清单」——挑好要提交的文件git add
本地仓库（Repository）「档案柜」——已存档的历史快照git commit
📌 一句话理解
工作区 → git add → 暂存区 → git commit → 仓库。add 是「挑货」，commit 是「入库」。挑货可以反复挑、挑错了随时撤，入库后就形成历史。
🧠 速记口诀
「办公桌挑货，清单暂存区，档案柜入库；add 进清单，commit 存档案」——文件流动三兄弟：工作区 → 暂存区 → 仓库。

02 安装与初始配置

安装 Git

系统方式验证
Windows官网下载安装包，或用 winget：winget install Git.Gitgit --version
macOSbrew install git（或 Xcode Command Line Tools）
Linuxsudo apt install git（Debian/Ubuntu）

第一次使用必配三件套

git config --global user.name "你的名字"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
  • user.name / user.email：提交时记录「谁干的」，会写进每条提交历史，不配就无法提交
  • init.defaultBranch main：新版 Git 默认分支名改为 main（老版本默认 master）

推荐增强配置

配置命令作用
颜色输出git config --global color.ui auto状态/分支/差异带颜色，一眼看清
差异算法git config --global diff.algorithm histogram更智能的差异对比
换行符（Windows）git config --global core.autocrlf true自动转换 CRLF/LF，避免「整文件变红」
默认编辑器git config --global core.editor "code --wait"写提交信息用 VSCode
常用别名git config --global alias.st statusgit st 即 git status
⚠️ 避坑提示
① 配置分三级：--system（整机）/ --global（当前用户）/ --local（当前仓库），优先级 local > global > system；② 查看当前所有配置用 git config --list；③ 公司项目邮箱要用公司邮箱，否则提交会记到个人账号下。
🧠 速记口诀
「装完先配名与邮，不配提交就报错；global 管本机，local 管本仓库」——三件套：name、email、defaultBranch。

03 创建仓库与第一次提交

两种创建方式

场景命令说明
本地已有项目git init在项目根目录初始化，生成隐藏的 .git 文件夹
从远程拉取git clone 仓库地址完整复制远程仓库（含全部历史）到本地

第一次提交五步走

  1. git init：初始化仓库
  2. git status：查看当前状态（红 = 未跟踪/未暂存）
  3. git add .：把当前目录所有文件加入暂存区（绿 = 已暂存）
  4. git commit -m "feat: 初始化项目"：提交，附上说明
  5. git log --oneline：查看提交历史
git init
git status
git add .
git commit -m "feat: 初始化项目"
git log --oneline
📌 一句话理解
git init 只在项目里生成一个 .git 文件夹，它只是「档案柜」的地址，不是备份——真正产生历史的是第一次 git commit。
⚠️ 避坑提示
① 不要在别人的仓库里再 git init（会生成嵌套仓库，push 会混乱）；② git add . 会把所有文件都加进去，正式项目先写好 .gitignore（第 10 章讲）再 add；③ commit 信息用 动词开头 + 简短描述，如 feat: 新增登录页。
🧠 速记口诀
「init 开档案，status 看状态，add 挑货，commit 入库，log 翻账本」——第一次提交五连，从此告别 Ctrl+C 备份。

04 暂存区与提交详解

git add 的多种姿势

命令作用
git add 文件名添加指定文件
git add .添加当前目录所有改动（含新增、修改、删除）
git add -u只暂存「已跟踪文件」的修改/删除（不含新增）
git add -p分块暂存（交互式挑每一段，精修提交必备）
git add -A= add . + 处理删除（推荐在仓库根目录用）

git status 的三种状态

  • 未跟踪（Untracked）：新文件，Git 还没管过 → 显示红色 ??
  • 已修改未暂存（Modified）：改过但没 add → 显示红色 M
  • 已暂存（Staged）：add 过，等 commit → 显示绿色

提交的讲究

命令作用
git commit -m "说明"提交并写一行说明
git commit -am "说明"add + commit 一步到位（只对已跟踪文件）
git commit --amend -m "新说明"修改上一条提交的说明（或补内容）
git commit --amend --no-edit把暂存区改动并入上一条提交，不换说明
⚠️ 避坑提示
① git commit --amend 会改写历史，如果这条提交已经 push 到远程，不要 amend（除非你清楚后果）；② 提交信息写清楚「做了什么 + 为什么」，比「改了点东西」强一百倍；③ git commit -am 不会包含未跟踪的新文件，新文件必须显式 add。
🧠 速记口诀
「add 分块用 -p，提交说明写清楚；amend 改上条，push 之后别乱碰」——小步提交、原子提交，是职业习惯的分水岭。

05 查看历史与文件差异

git log 家族

命令作用
git log完整提交历史（作者/时间/说明）
git log --oneline一行一条，最常用
git log --oneline --graph带分支图，看清分叉合并脉络
git log --oneline -5只看最近 5 条
git log --author="名字"只看某人的提交
git log -p 文件名看某文件每次提交的具体改动
git log --oneline --grep="关键词"按提交说明搜索

git diff 家族

命令作用
git diff工作区 vs 暂存区（改了什么还没 add）
git diff --staged暂存区 vs 仓库（add 了什么还没 commit）
git diff HEAD工作区全部改动 vs 最近一次提交
git diff 分支A 分支B两个分支的差异
git diff 提交A 提交B两个提交的差异

其他查看命令

  • git show 提交号：看某次提交的完整改动
  • git show HEAD：看最近一次提交改了什么
  • git blame 文件名：逐行标注「这行是谁、哪次提交写的」（找背锅侠必备）
  • git reflog：救命的操作日志，记录你所有 HEAD 移动，误删分支也能找回来
🚨 红线提醒
git reflog 是 Git 的「黑匣子」：即使你 git reset --hard 删了提交、git branch -D 删了分支，只要 reflog 里还在，就能用提交号找回。遇到误操作先别慌，git reflog 看一遍再说。
🧠 速记口诀
「log 看历史、diff 看差异、show 看细节、blame 找背锅、reflog 是黑匣子」——查历史五件套，定位问题快三倍。

06 分支基础

分支是什么

分支就是指向某个提交的可移动指针。它让「并行开发互不干扰」成为可能：你开一个分支改新功能，主分支继续发版，改完再合并回去。创建分支的成本几乎为零，所以 Git 鼓励多开分支。

分支核心命令

命令作用
git branch列出本地分支（* 号标记当前分支）
git branch 分支名创建分支（不切换）
git checkout 分支名切换分支（老命令）
git switch 分支名切换分支（新版推荐，语义更清晰）
git switch -c 分支名创建并切换（= checkout -b）
git branch -d 分支名删除已合并的分支（安全）
git branch -D 分支名强制删除未合并分支（谨慎）
git branch -a列出所有分支（含远程）
📌 一句话理解
git switch -c dev = 「新建一条叫 dev 的时间线并跳过去」。分支切换只改变你「看哪条时间线」，代码本身不会丢。
⚠️ 避坑提示
① 切换分支前先 commit 或 stash，否则工作区未提交的改动会「跟着你走」到新分支；② 分支名规范：功能 feat/xxx、修复 fix/xxx、文档 docs/xxx；③ 不要在主分支上直接写代码——主分支永远保持可发布状态。
🧠 速记口诀
「branch 看列表，switch 来切换，-c 建了又切，-d 安全删、-D 强删」——分支四式：看、切、建、删。

07 远程仓库与 GitHub

远程仓库（Remote）

远程仓库是托管在服务器上的 Git 仓库（GitHub、GitLab、Gitee 等）。本地仓库和远程仓库通过 remote 关联，push（推）和 pull（拉）同步代码。

命令作用
git remote -v查看远程仓库地址
git remote add origin 地址关联远程仓库（origin 是约定俗成的名字）
git remote rename old new重命名远程
git remote remove 名字移除远程关联（不影响本地代码）

推送与拉取

命令作用
git push origin main把本地 main 推送到远程
git push -u origin main首次推送并建立跟踪关系（之后直接 git push）
git pull= fetch + merge，拉取远程并合并到当前分支
git fetch只拉取远程更新到本地，不自动合并
git pull --rebase拉取时用变基代替合并（历史更干净，见第 13 章）
git push origin --delete 分支名删除远程分支

SSH 免密配置（重要）

  1. 生成密钥：ssh-keygen -t ed25519 -C "你的邮箱"（一路回车）
  2. 复制公钥：cat ~/.ssh/id_ed25519.pub
  3. 粘贴到 GitHub → Settings → SSH and GPG keys → New SSH key
  4. 克隆时用 SSH 地址（git@github.com:...），从此免密推送
⚠️ 避坑提示
① push 被拒绝说明远程有本地没有的提交：先 git pull --rebase 再 push；② HTTPS 地址每次要输密码/token，改用 SSH 免密；③ GitHub 2021 年起不再支持密码 push，用 token 或 SSH；④ 不要把密钥文件（id_rsa / id_ed25519 无 .pub 后缀）提交进仓库。
🧠 速记口诀
「remote 关联，push 推送，pull 拉取，fetch 只收不并；SSH 配一次，免密用到老」——远程协作四字经：关联、推送、拉取、同步。

08 合并与冲突解决

git merge 的两种形态

形态发生条件特点
快进合并（Fast-forward）当前分支没新提交，目标分支只是向前走历史是一条直线，无合并提交
三方合并（Merge commit）两个分支都有各自的新提交产生一个合并提交，历史出现分叉

合并操作

# 切回主分支，把功能分支合进来
git switch main
git merge feat/login

# 不想产生合并提交（保持直线历史）
git merge --ff-only feat/login

# 强制生成合并提交
git merge --no-ff feat/login

冲突（Conflict）是什么

当两个分支改了同一文件的同一行，Git 不知道听谁的，就会冲突。冲突文件里会出现标记： 

<<<<<<< HEAD
这里是当前分支的内容
=======
这里是合并进来的分支内容
>>>>>>> feat/login

解决冲突五步

  1. git status 找到冲突文件（显示 both modified）
  2. 打开文件，删掉 <<<<<<< / ======= / >>>>>>> 标记，保留正确内容
  3. git add 冲突文件（标记「已解决」）
  4. git commit（完成合并）
  5. 想放弃这次合并：git merge --abort
⚠️ 避坑提示
① 冲突不可怕，可怕的是乱删代码——先看两个版本分别是什么逻辑再决定；② 解决冲突时不要顺手删别人的代码，不确定就问；③ 小改动用 git merge --abort 重来，大改动逐文件慢慢解；④ 解决完冲突一定要 git add + git commit，否则 Git 一直认为冲突未解决。
🧠 速记口诀
「合并两形态：快进直线、三方分叉；冲突看标记，删线留内容，add 再 commit」——遇到冲突别慌，先读代码再动手。

09 标签与版本发布

Tag 是什么

Tag（标签）是给某个提交打上的「永久记号」，通常用来标记发布版本：v1.0.0、v2.3.1。它和分支的区别：分支会移动，标签钉死不动。

标签操作

命令作用
git tag列出所有标签
git tag v1.0.0给当前提交打轻量标签
git tag -a v1.0.0 -m "发布说明"打附注标签（带打签人和说明，推荐）
git tag v1.0.0 提交号给指定提交打标签
git push origin v1.0.0推送指定标签到远程
git push origin --tags推送全部标签
git tag -d v1.0.0删除本地标签
git push origin --delete tag v1.0.0删除远程标签
git checkout v1.0.0切到标签对应代码（分离头指针）

语义化版本（SemVer）

版本号含义例子
主版本号不兼容的重大变更1.0.0 → 2.0.0
次版本号新增功能（向后兼容）1.0.0 → 1.1.0
修订号修复 Bug（向后兼容）1.1.0 → 1.1.1
⚠️ 避坑提示
① 标签打错了尽早删，因为标签在远程一旦被多人引用，改动代价很大；② 发布前先确认代码能跑、测试通过，「先 tag 后发布」，让每个版本都能回溯；③ checkout 到标签后处于分离头指针（detached HEAD）状态，此时提交会「悬空」——要基于标签改代码，先 git switch -c 新分支名。
🧠 速记口诀
「主版本破兼容，次版本加功能，修订号修 Bug；打签用 -a，发布先打签」——SemVer 三段式：X.Y.Z。

10 忽略文件与配置管理

.gitignore 是什么

.gitignore 告诉 Git哪些文件不要跟踪。项目里的依赖、编译产物、本地配置、密钥等都不该进仓库。

必须忽略的典型文件

# 依赖与构建产物
node_modules/
dist/
build/
target/
*.class

# 环境与密钥
.env
*.pem
config.local.js

# 系统文件
.DS_Store
Thumbs.db
*.log

# 编辑器配置（团队统一才保留）
.idea/
.vscode/

.gitignore 语法速查

语法含义示例
文件名忽略该文件secret.json
目录/忽略整个目录node_modules/
*通配符*.log
!文件名取反（重新跟踪）!important.log
目录/子文件忽略特定子路径docs/build/
**任意层级**/temp/

全局忽略与配置分层

  • 全局忽略：git config --global core.excludesfile ~/.gitignore_global（放系统文件 .DS_Store 等）
  • 配置查看：git config --list / git config --global --list / git config --local --list
  • 删除缓存里的忽略文件：已经被跟踪的文件，gitignore 不会自动生效：git rm -r --cached 目录 再提交
⚠️ 避坑提示
① gitignore 只对「未跟踪」文件生效——已经提交过的文件，即使写了 ignore 也照样跟踪，要用 git rm --cached 移出；② 密钥文件一旦提交过远程，改 gitignore 没用，必须换密钥（历史里还留着）；③ 别把整个 .vscode 都忽略，团队需要共享格式化配置时可选择性保留。
🧠 速记口诀
「依赖密钥构建物，三样必进 ignore；* 通配 ! 取反，已跟踪要 rm --cached」——先写 ignore 再 add，安全第一条。

11 撤销与回滚

四种撤销工具怎么选

场景命令效果
工作区改乱了（未 add）git restore 文件名丢弃工作区修改，回到暂存区/仓库版本
误 add 了（想移出暂存区）git restore --staged 文件名取消暂存，改动保留在工作区
撤销提交但保留改动git reset --soft HEAD~1回到上一个提交，改动留在暂存区
撤销提交且保留到工作区git reset --mixed HEAD~1（默认模式）改动回到工作区
彻底回滚（危险）git reset --hard HEAD~1提交和改动一起消失（可用 reflog 救）
已 push，撤销某次提交git revert 提交号生成一个「反向提交」，不改历史

restore / reset / revert 对比

  • git restore：针对「文件」，把工作区/暂存区恢复到某个状态，不动历史
  • git reset：移动 HEAD 指针，改写历史（本地未 push 时用）
  • git revert：在历史末尾追加反向提交，历史不变（已 push 时用）
🚨 红线提醒
已 push 的提交绝不 reset，要用 revert。否则你和队友的历史就分叉了，下次 pull 会冲突到怀疑人生。记住：本地历史随便改，公共历史只能 revert。
🧠 速记口诀
「未 add 用 restore，误 add 用 --staged；本地 reset 随便改，已 push 只能 revert」——撤销四兄弟：restore、reset 三档、revert。

12 暂存 Stash 与清理

git stash 是什么

手头改到一半，突然要切分支改别的——又不想提交半成品。用 git stash 把当前改动暂时收进「口袋」，工作区恢复干净；忙完再 stash pop 掏出来继续。

stash 命令一览

命令作用
git stash暂存当前改动（默认不含未跟踪文件）
git stash -u连同未跟踪文件一起暂存
git stash -m "说明"带说明暂存，方便区分
git stash list查看暂存列表
git stash pop取出最近一次暂存并删除该记录
git stash apply取出暂存但保留记录（可多次应用）
git stash drop丢弃最近一次暂存
git stash clear清空所有暂存（谨慎）
git stash branch 分支名基于暂存新建分支并应用（解决 pop 冲突）

git clean 清理未跟踪文件

命令作用
git clean -n预览会删除哪些文件（先看再删）
git clean -f删除未跟踪文件
git clean -fd连同未跟踪目录一起删
git clean -fdx连同被忽略文件一起删（危险）
⚠️ 避坑提示
① stash 是有存放期限的——放太久忘了，pop 时容易冲突；用完尽快取；② git clean 是不可恢复的删除（不进回收站），一定先 -n 预览；③ stash pop 冲突时，用 git stash branch 新分支 最稳，冲突可以慢慢解。
🧠 速记口诀
「stash 收口袋，pop 掏出来，list 看清单；clean 删垃圾，先 -n 预览再 -f 删」——半成品先收好，垃圾文件先看再删。

13 变基 Rebase 与提交整理

merge vs rebase

对比项git mergegit rebase
历史形态保留分叉，产生合并提交把分支「重放」到最新，历史是一条直线
提交记录真实记录「何时分叉合并」重写提交时间/顺序
适用公共分支、长期分支本地个人分支、整理历史
风险低已 push 的提交禁止 rebase

rebase 基本操作

# 在功能分支上，把 base 变到 main 的最新
git switch feat/login
git rebase main

# 拉取时直接变基（推荐日常用法）
git pull --rebase

交互式变基：整理提交（git rebase -i）

这是 Git 最强大的整理工具，可以改写最近 N 条提交：

# 整理最近 3 条提交
git rebase -i HEAD~3
命令作用
pick保留该提交（默认）
reword保留提交但修改说明（r）
edit保留提交但停下来修改内容（e）
squash合并到上一个提交（s）
fixup合并到上一个提交且丢弃说明（f）
drop删除该提交（d）
🚨 红线提醒
只对「未 push」的本地提交 rebase。已经 push 到远程、且其他人拉取过的提交，一旦 rebase，历史 SHA 全变，队友 pull 会直接炸开。团队协作规范：公共分支只 merge，个人分支随意 rebase。
🧠 速记口诀
「merge 留真相，rebase 修直线；-i 整理历史：pick 留、squash 并、drop 删」——个人分支用 rebase 保持干净，公共分支用 merge 尊重事实。

14 Git 内部原理与对象模型

Git 的四种对象

Git 的核心是一个内容寻址文件系统：所有数据都以对象存储，对象名是内容的 SHA-1 哈希。

对象存什么比喻
Blob文件内容（不含文件名）货物本身
Tree目录结构：文件名 → blob/tree 的映射货物清单 + 货架编号
Commit一次提交：作者、时间、说明、指向的 Tree、父提交入库单据
Tag（附注标签）指向某个 commit 的签名信息贴在货架上的标签

一次提交的「链条」

每个 commit 都指向父提交，形成一条链。分支就是指向链尾 commit 的指针，HEAD 指向当前分支。所以「切分支」只是换了个指针，快得飞起。 

# 查看对象类型
git cat-file -t 提交号
# 查看对象内容
git cat-file -p 提交号

# 查看 .git 目录结构
ls .git
# objects/（对象库）、refs/（分支和标签指针）、HEAD（当前指针）

.git 目录速览

路径作用
HEAD当前指向哪个分支/提交
config本仓库配置（local 级）
refs/heads/本地分支指针
refs/tags/标签指针
objects/对象库（blob/tree/commit）
index暂存区（staging area）
logs/reflog 操作日志
📌 一句话理解
内容相同 = 哈希相同，Git 靠这个去重：同一个文件不管存在多少分支、多少版本，仓库里只存一份 blob。这也是 Git 仓库「虽小却全」的原因。
🧠 速记口诀
「blob 存内容、tree 存目录、commit 存快照、tag 钉版本；分支是指针，HEAD 指当前」——理解了对象模型，Git 再无黑魔法。

15 钩子 Hook 与自动化

Git Hooks 是什么

钩子是在 Git 特定事件发生时自动执行的脚本，存放在 .git/hooks/ 目录（带 .sample 后缀的是示例，去掉后缀才生效）。最常用的钩子：

钩子触发时机典型用途
pre-commitcommit 前跑代码检查（eslint）、格式化、查密钥
commit-msgcommit 前校验提交信息格式（如必须带类型前缀）
pre-pushpush 前跑测试、阻止直接推 main
post-commitcommit 后通知、备份
post-merge合并后自动装依赖（npm install）

一个最简单的 pre-commit

#!/bin/sh
# .git/hooks/pre-commit
# 检查是否提交了密钥文件
if git diff --cached --name-only | grep -E "\.(env|pem|key)$"; then
  echo "❌ 检测到敏感文件，禁止提交！"
  exit 1
fi

注意：.git/hooks/ 里的钩子不随仓库共享。团队共享钩子用 Husky（Node 生态）或 core.hooksPath 指向仓库内目录。

husky + lint-staged 实践

# package.json 里配置
"husky": {
  "hooks": {
    "pre-commit": "lint-staged",
    "commit-msg": "commitlint -E HUSKY_GIT_PARAMS"
  }
},
"lint-staged": {
  "*.{js,ts,vue}": ["eslint --fix", "git add"]
}
⚠️ 避坑提示
① 钩子脚本要有执行权限（chmod +x），Windows 上注意脚本解释器；② --no-verify 可跳过钩子（git commit --no-verify），但这是「紧急通道」，别当常态；③ 钩子只防君子不防小人——真正的质量门禁要靠 CI。
🧠 速记口诀
「pre-commit 查代码、commit-msg 查格式、pre-push 查测试；钩子不共享，husky 来帮忙」——把规范交给机器，别靠自觉。

16 团队协作工作流

三种主流工作流

工作流分支模型适用场景
GitHub Flow只有 main + 功能分支；功能分支 → PR → 合并持续部署的互联网项目（最流行）
GitFlowmain + develop + feature + release + hotfix 五类分支有明确版本发布周期的项目
主干开发（Trunk-Based）所有人直接在 main 上小步提交高度自动化的 CI/CD 团队

GitHub Flow 标准流程

  1. 从 main 拉功能分支：git switch -c feat/xxx
  2. 小步提交：git commit -m "feat: ..."
  3. 推送到远程：git push -u origin feat/xxx
  4. 发起 Pull Request（PR），队友 Review 代码
  5. CI 通过 + Review 通过 → 合并到 main
  6. 合并后删除功能分支，触发自动部署

PR（Pull Request）注意事项

  • PR 要小：一个 PR 只做一个功能，几百行以内的 diff 才好 review
  • PR 标题/描述写清楚：做了什么、为什么、怎么测
  • 合并前先同步 main：git pull --rebase origin main，减少冲突
  • Review 是双向的：评论要具体、礼貌，被 review 要虚心改
⚠️ 避坑提示
① 千万别直接往 main 推代码（除非你一个人用）；② 一个 PR 拖太久容易和 main 脱节产生大冲突——小步快跑，频繁同步；③ 合并策略团队统一：squash merge（历史干净）还是 merge commit（保留过程），说好就别换。
🧠 速记口诀
「功能分支 + 小步提交 + PR 评审 + CI 把关 + 自动部署」——GitHub Flow 五连，互联网团队标配。

18 避坑指南与学习路线

高频事故与补救

事故场景症状补救方案
commit 写错说明上一条提交信息是乱码git commit --amend -m "正确说明"
误删分支分支没了git reflog 找提交号 → git branch 分支名 提交号
reset --hard 删了提交代码没了git reflog → git reset --hard 提交号
push 被拒绝远程有更新git pull --rebase 再 push
切分支带走了改动改动跑到别的分支先 commit/stash，再切回原分支处理
误提交密钥文件密钥进了历史立即撤销密钥 + 清理历史（filter-repo）
pull 冲突merge conflict看冲突标记，手动解决后 add + commit
amend/rebase 后 push 失败历史不一致本地未共享可强推；共享了禁止强推

新手十大避坑要点

  1. 每天上班先 git pull --rebase，别让本地落后太多
  2. 小步提交：一次提交只做一件事，说明写「做了什么 + 为什么」
  3. 不要提交密钥/大文件/依赖目录，先写 .gitignore
  4. 公共分支绝不 reset / 强推，统一用 revert
  5. 切分支前先看 status，确认工作区干净
  6. 重要节点打 tag，发布版本可回溯
  7. rebase 只用于未 push 的提交
  8. 遇到问题先 reflog，Git 有黑匣子，别慌着删
  9. git commit --no-verify 是应急通道，别当常态
  10. PR 要小、描述要清楚，Review 要具体

推荐学习路线

第 1 周 · 基础

安装配置、init/add/commit、status/log、分支的增删切。目标：能用 Git 管理个人项目。

第 2 周 · 协作

clone/push/pull、远程仓库、SSH、冲突解决、GitHub PR 流程。目标：能参与团队协作。

第 3 周 · 进阶

reset/revert/restore 三兄弟、stash、cherry-pick、tag 发布、.gitignore 规范。

第 4 周 · 精通

rebase -i 整理历史、Git 对象模型、hooks、GitFlow/GitHub Flow、bisect 调试。

⚠️ 避坑提示
学 Git 最大的误区是「背命令」——命令是背不完的。正确姿势：先理解三个区域 + 对象模型，再记「场景 → 命令」的映射，最后靠 git help 和 git status 的提示边用边查。
🧠 速记口诀
「理解模型 > 背命令；场景映射记得牢；遇事不决 reflog，公共历史只 revert」——Git 学成，走遍开发不慌。
