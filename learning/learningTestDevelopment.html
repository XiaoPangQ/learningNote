01 软件测试基础与质量观

1.1 什么是软件测试

软件测试是通过人工或自动化手段，验证软件是否满足需求、发现缺陷并评估质量的过程。它不是"随便点点"，而是有目标、有计划、可度量的工程活动。

简单理解：测试就像"质检员"——生产线上每件产品出厂前都要过检。软件也一样，上线前必须经过多道"质检关卡"，避免带病上线。

1.2 为什么要做测试

  • 发现缺陷：尽早发现 bug，修复成本最低
  • 验证需求：确认软件确实实现了预期的功能和性能
  • 建立信心：为发布决策提供依据，让团队敢上线
  • 降低成本：缺陷越晚发现，修复成本指数上升
发现阶段 相对修复成本 说明
需求/设计阶段 1x 改文档即可，最便宜
编码阶段 6.5x 改代码 + 重新编译
测试阶段 15x 定位 + 修复 + 回归
生产环境 60–100x 用户投诉、数据修复、舆情风险
为什么越早越好？缺陷成本随阶段指数增长，所以行业强调"测试左移"——把测试活动提前到需求、设计阶段。

1.3 测试七大原则

  • 测试显示缺陷的存在：测试只能证明有 bug，不能证明没 bug
  • 穷尽测试不可能：输入组合无穷，必须用抽样策略
  • 尽早测试：测试活动越早介入，效果越好成本越低
  • 缺陷集群性：少量模块集中了大部分缺陷（80/20 法则）
  • 杀虫剂悖论：重复执行同样的用例，缺陷发现能力会下降
  • 测试依赖于上下文：电商和银行 App 的测试重点完全不同
  • 无缺陷谬误：没 bug 不等于好用，还要满足用户期望
🧠 口诀：「显穷早集杀上无」——显示缺陷、穷尽不可能、尽早测试、缺陷集群、杀虫剂悖论、上下文依赖、无缺陷谬误。

1.4 软件质量模型（ISO/IEC 25010）

质量特性 含义 测试关注点
功能性 功能是否正确完整 功能测试、接口测试
可靠性 持续稳定运行不崩溃 稳定性测试、异常恢复
易用性 用户容易理解和使用 UI/UX 测试、可用性测试
效率 响应快、资源占用低 性能测试、专项测试
可维护性 代码易修改、易扩展 代码评审、单元测试
可移植性 跨环境运行的能力 兼容性测试

1.5 错误、缺陷与故障的关系

测试中常说的 bug 其实包含三个层次：错误（Error）是程序员写错代码；缺陷（Defect）是代码中的错误导致的功能问题；故障（Failure）是缺陷被触发后表现出的失败现象。

传播链：人为错误 Error → 引入缺陷 Defect → 运行触发 → 故障 Failure。测试的价值就是在"故障"到达用户之前，拦截住"缺陷"。

1.6 核心测试术语速查

术语 含义
验证（Verification） 做的东西对不对（是否符合规格）
确认（Validation） 做的东西是不是用户要的（是否满足需求）
冒烟测试（Smoke） 主干功能快速过一遍，判断能否继续测
回归测试（Regression） 改动后验证旧功能没被破坏
健全性测试（Sanity） 针对本次改动的重点快速验证
探索性测试（Exploratory） 边学边测，凭经验和直觉找漏洞

02 测试流程与文档

2.1 标准测试流程

  1. 需求分析：理解需求，明确测试范围与重点
  2. 测试计划：制定策略、排期、资源与风险
  3. 用例设计：设计并评审测试用例
  4. 用例执行：按优先级执行，记录结果
  5. 缺陷跟踪：提交 bug、跟踪修复、回归验证
  6. 测试报告：汇总质量数据，给出上线结论
  7. 上线验证：生产环境冒烟回归
🧠 口诀：「需计用执缺报验」——需求、计划、用例、执行、缺陷、报告、验收。走完一轮就是一次完整测试迭代。

2.2 测试计划包含什么

要素 要回答的问题
测试范围 测什么？不测什么（明确排除项）？
测试策略 用什么方法、工具、层级覆盖？
资源安排 谁负责？需要什么环境与数据？
进度计划 各阶段什么时候开始、结束？
风险与对策 哪些风险可能影响交付？如何应对？
准入准出 什么条件下开始测、什么条件算测完？
避坑：测试计划不是写给别人看的文档，而是团队执行的"作战地图"。范围、准入准出条件写不清楚，后期一定会扯皮。

2.3 测试用例八大要素

  • 用例编号：如 TC-LOGIN-001，便于追溯管理
  • 用例标题：一句话说明验证什么
  • 前置条件：执行前的环境与数据准备
  • 测试步骤：具体操作步骤
  • 测试数据：输入的数据（常与步骤合并）
  • 预期结果：符合需求的期望输出（最关键）
  • 优先级：P0/P1/P2，决定执行顺序
  • 用例类型：功能/接口/性能/安全等
为什么预期结果最关键？没有预期结果，执行者无法判断对错，用例就退化成"随手点点"，无法复用、无法自动化。

2.4 缺陷生命周期

一个 bug 从被发现到关闭，通常经过：新建 → 指派 → 修复 → 验证 → 关闭，中间可能经历重新打开、拒绝、延期等状态。

状态 说明
New 新建 测试人员提交缺陷
Assigned 指派 分配给对应开发人员
Open / In Progress 开发开始处理
Fixed 已修复 开发修改完成，等待验证
Reopen 重新打开 验证不通过，打回重改
Closed 关闭 验证通过，缺陷关闭
Rejected / Won't Fix 无效缺陷或暂不处理
🧠 口诀：「新指派修验关」——新建、指派、修复、验证、关闭，五步闭环。

2.5 缺陷报告怎么写

一条高质量缺陷应包含：标题（一句话说清问题）、复现步骤、实际结果、预期结果、环境信息（版本/系统/浏览器）、严重程度与优先级、截图或日志。

严重程度 Severity 优先级 Priority
致命：崩溃、数据丢失、核心流程不可用 P0：立即修复，阻断发布
严重：主功能错误、无可用替代方案 P1：本版本内必须修复
一般：功能异常但有绕过方案 P2：本版本尽量修复
轻微：文案、样式、体验问题 P3：可下版本处理
常见误区：严重程度和优先级不是一回事——"致命但不常见"和"轻微但影响面大"很常见。例如登录按钮文案写错（轻微）会造成全网投诉（P1）。

2.6 测试报告

测试报告回答三个问题：测了什么、结果如何、能不能上线。核心内容：测试概述、用例执行统计（总数/通过/失败/阻塞）、缺陷统计与分析、遗留风险、上线结论。

报告的灵魂是结论，不是流水账：领导只关心一件事——"能上线吗？风险是什么？"用数据支撑结论，别堆过程。

03 测试用例设计方法

3.1 等价类划分

把输入数据按"是否等价"分组：有效等价类（符合需求的数据）与无效等价类（不符合需求的数据）。每组取一个代表值测试即可，避免穷举。

需求（年龄输入） 有效等价类 无效等价类
18–60 岁可注册 18、30、60 17、61、-1、0、abc、空
🧠 口诀：「有效一例，无效分型」——有效等价类取一个代表即可；无效等价类每种错误类型都要单独测（整数越界、负数、非数字、为空是四种情况）。

3.2 边界值分析

缺陷最容易发生在边界附近（大于、小于、等于、临界）。边界值分析是等价类的补充：取上点（边界值本身）、内点（边界内最近点）、离点（边界外最近点）测试。

区间 [18, 60] 取值
上点（边界本身） 18、60
内点（边界内侧最近） 19、59
离点（边界外侧最近） 17、61
🧠 口诀：「上内离」——上点、内点、离点，边界值全测齐。

3.3 判定表与因果图

判定表适合"多个条件组合决定多个动作"的场景：列出条件桩（所有输入条件）和动作桩（所有输出动作），穷举条件组合覆盖。因果图是判定表的前置工具，用于梳理条件与结果的因果关系。

条件 组合1 组合2 组合3 组合4
已登录 是 是 否 否
购物车非空 是 否 是 否
可下单 ✅ ❌ 提示加购 ❌ 跳登录 ❌ 双提示

3.4 场景法

从用户角度用基本流（主流程）+ 备选流（分支、异常）描述业务场景，每个场景就是一条用例。最适合业务流程类测试（下单、支付、退款）。

  • 基本流：登录 → 选商品 → 下单 → 支付 → 完成
  • 备选流1：登录时密码错误（重试）
  • 备选流2：库存不足（提示并返回）
  • 备选流3：支付超时（订单状态处理）

3.5 正交实验法

条件多、组合爆炸时，用正交表选取代表性的组合，用最少的用例覆盖两两组合。适合配置兼容性测试（浏览器 × 系统 × 分辨率）。

为什么用正交？3 个条件各 4 个取值全组合要 4×4×4=64 条用例；用正交表 L16 只需 16 条，就能覆盖所有"两两组合"，性价比极高。

3.6 错误推测法

凭经验猜"哪里最容易出错"：除零、空值、超长、重复提交、并发点击、断网、时间边界（23:59:59）、金额为 0/负数、权限边界……直接针对性设计用例。

方法 适用场景 特点
等价类 输入框、数据范围 最基础，必用
边界值 有边界的数据 缺陷高发区
判定表 条件组合逻辑 覆盖全、用例多
场景法 业务流程 贴近用户
正交实验 配置组合爆炸 少量用例覆盖广
错误推测 经验补充 依赖个人经验
综合策略：先用场景法搭业务流程骨架，再用等价类 + 边界值填数据细节，用判定表补组合逻辑，最后用错误推测查漏。

04 测试环境与工具链

4.1 测试环境的组成

一个可用的测试环境 = 硬件 + 软件 + 网络 + 数据 + 配置 五要素齐备。

  • 硬件：服务器、真机、模拟器
  • 软件：被测系统、中间件（DB/Redis/MQ）、依赖服务
  • 网络：内网/外网、代理、弱网模拟
  • 数据：测试库数据、造数脚本、备份恢复
  • 配置：环境变量、域名映射、开关配置

4.2 环境分类与隔离

环境 用途 特点
开发环境 Dev 开发自测 可随意折腾
测试环境 Test 功能/接口测试 需稳定，数据可控
预发布环境 Staging 上线前全流程演练 与生产一致，数据脱敏
生产环境 Prod 线上运行 只读验证，严禁乱动
避坑：多环境必须物理或逻辑隔离。测试数据写入生产库、测试环境与预发共用一套 Redis 导致缓存串数据，是测试事故的高发原因。

4.3 Git 基础命令

测试人员也要会 Git：拉代码、切分支、提交缺陷相关验证代码、管理测试脚本。 

# 常用 Git 命令
git clone https://xxx/repo.git   # 拉取代码
git checkout -b test/dev-001     # 新建并切换分支
git add .                        # 暂存
git commit -m "add test script"  # 提交
git push origin test/dev-001     # 推送
git pull                         # 拉取最新
git log --oneline -5             # 查看最近提交
git stash                        # 暂存未提交的修改
git merge main                   # 合并主分支

4.4 缺陷管理工具

工具 特点 适用场景
禅道 国产、开源、需求/用例/bug 一体 国内中小团队
Jira 生态丰富，可深度定制工作流 大中型团队、敏捷
TAPD / PingCode 腾讯系敏捷协作，研发一体化 腾讯生态、敏捷团队
GitHub Issues 轻量、与代码仓库打通 开源项目

4.5 测试常用工具全景

  • 接口测试：Postman、Apifox、JMeter、requests
  • UI 自动化：Selenium、Playwright、Appium
  • 抓包调试：Chrome DevTools、Fiddler、Charles、mitmproxy
  • 性能测试：JMeter、LoadRunner、Grafana + Prometheus
  • 安全测试：Burp Suite、AppScan、AWVS
  • 单元测试：pytest、JUnit、Go test、Jest
为什么工具越用越少？一个优秀的测试工程师不是"工具越多越好"，而是每类问题有一套熟练的主工具，能快速上手新工具。

05 第一个测试项目实战

5.1 项目背景与测试范围

以电商网站的登录 + 下单两个模块为例，走一遍完整测试流程：需求分析 → 测试计划 → 用例设计 → 执行 → 缺陷跟踪 → 测试报告。

需求要点：① 手机号 + 密码登录，密码错误 5 次锁定 30 分钟；② 下单需购物车有商品、库存充足、余额充足；③ 支付成功后库存扣减、订单状态为"待发货"。

5.2 需求分析与测试点提取

需求 测试点 用例方法
手机号 + 密码登录 格式校验、密码正确/错误、空值 等价类 + 边界值
5 次错误锁定 30 分钟 第 4/5/6 次、锁定倒计时、解锁 边界值 + 场景法
下单校验库存 库存充足/不足/为 0、并发扣减 场景法 + 并发
支付成功扣库存 扣减正确性、超卖、重复支付 场景法 + 错误推测

5.3 测试用例示例（登录模块）

编号 标题 步骤 预期 优先级
TC-LOGIN-001 正确账号密码登录 输入正确手机号+密码，点登录 登录成功，跳转首页 P0
TC-LOGIN-002 密码错误提示 输入错误密码登录 提示"密码错误" P0
TC-LOGIN-003 手机号格式校验 输入 11 位非手机号数字 提示格式错误 P1
TC-LOGIN-004 连续 5 次错误锁定 连续输错 5 次 提示账号锁定 30 分钟 P0
TC-LOGIN-005 锁定期间登录 锁定后立即尝试正确密码 仍提示锁定，不可登录 P1
TC-LOGIN-006 30 分钟后自动解锁 等待 30 分钟后登录 可正常登录 P1

5.4 执行与缺陷提交

按 P0 → P1 → P2 顺序执行。发现缺陷后按标准模板提交：

【标题】连续输错 5 次后，提示文案显示"锁定 30 分钟"，实际 10 分钟即可登录
【环境】Chrome 130 / Windows 11 / 版本 2.3.1-test
【步骤】
1. 打开登录页
2. 连续输入错误密码 5 次
3. 等待 10 分钟后再试
【实际结果】可以正常登录（锁定时间不足 30 分钟）
【预期结果】锁定满 30 分钟才可登录
【严重程度】严重
【优先级】P1
【附件】screen-recording.mp4

5.5 回归与测试报告

开发修复后，重新执行原用例 + 关联用例（回归）。最后汇总：本次共设计用例 68 条，执行 68 条，通过 62 条，失败 6 条，缺陷 8 个（已关闭 7 个，遗留 1 个低优）。

避坑：修复一个 bug 常引入新 bug。回归测试必须跑关联模块（如改了登录，订单模块的登录态相关用例也要回归），不能只验证"这个 bug 好了没"。

06 功能测试与兼容性测试

6.1 功能测试要点

  • 正向流程：主流程必须通，数据流转正确
  • 反向流程：错误输入、非法操作有正确提示
  • 异常流程：断网、超时、崩溃后状态可恢复
  • 数据一致性：界面展示、数据库记录、接口返回三方一致
  • 状态机验证：订单各状态流转合法，非法跳转被拦截
🧠 口诀：「正反异常一致性」——正向、反向、异常三条路径 + 数据一致性，功能测试就不会漏大方向。

6.2 UI 与易用性测试

UI 测试关注样式还原（设计稿对比）、文案准确、交互反馈；易用性测试关注用户能否快速学会、高效使用、少犯错。

易用性维度 检查点
可学习性 新手能否不培训直接上手？
效率 常用操作几步完成？有快捷键吗？
可记忆性 隔一段时间回来还记得怎么用吗？
容错性 误操作有确认/撤销/恢复吗？
满意度 整体体验是否愉悦？

6.3 兼容性测试

验证软件在不同浏览器、操作系统、设备、分辨率下的表现。核心是建立兼容性矩阵，按用户占比排优先级。

维度 组合示例
浏览器 Chrome / Edge / Safari / Firefox / 微信内置浏览器
操作系统 Windows / macOS / iOS / Android / HarmonyOS
屏幕尺寸 375px / 414px / 768px / 1024px / 1440px
网络环境 Wi-Fi / 4G / 5G / 弱网（高延迟低带宽）
为什么不能全组合测试？组合爆炸。用正交实验法挑代表组合，或用云测平台（BrowserStack、Testin、阿里云移动测试）并行跑真机矩阵，效率翻倍。

6.4 兼容性问题常见类型

  • CSS 渲染差异：flex/grid 兼容性、字体渲染、圆角阴影
  • JS 兼容性：ES6+ 语法、API 缺失（老内核浏览器）
  • 安全策略差异：Cookie 限制、第三方 Cookie、HTTPS 混用
  • 字体与编码：中文乱码、emoji 渲染
  • 分辨率适配：布局错乱、元素溢出、安全区适配
避坑：只测 Chrome 就上线是兼容性事故的高发原因。微信内置浏览器（X5 内核）和 iOS Safari 是国内 Web 项目绕不开的两个"隐藏环境"。

07 接口测试

7.1 为什么接口测试这么重要

  • 更早介入：前后端联调前就能测，提前暴露问题
  • 成本更低：不依赖 UI，执行快、易自动化
  • 覆盖更深：能测 UI 测不到的场景（异常参数、并发、鉴权）
  • 定位更准：问题直接定位到接口层，不扯皮"前端还是后端"
类比：UI 测试像"看门面"，接口测试像"查内部管道"——管道堵了门面再漂亮也没用。

7.2 HTTP 基础回顾

方法 用途 幂等
GET 查询资源 是
POST 创建资源/提交操作 否
PUT 整体更新 是
PATCH 部分更新 否
DELETE 删除资源 是
状态码 含义
2xx 成功（200 OK、201 创建、204 无内容）
3xx 重定向（301 永久、302 临时、304 缓存）
4xx 客户端错误（400 参数错、401 未认证、403 无权限、404 不存在）
5xx 服务端错误（500 内部、502 网关、503 不可用、504 超时）

7.3 接口用例怎么设计

  • 正常场景：合法参数，验证返回正确
  • 参数异常：必填缺失、类型错误、超长、格式错误
  • 边界值：分页 pageSize=0/1/最大值、金额 0/负数/小数位
  • 鉴权异常：无 token、token 过期、伪造 token、越权访问
  • 业务异常：库存不足、余额不足、重复提交、状态不合法
  • 幂等与并发：重复请求不重复扣款、并发下单不超卖
一个接口最少 6 类用例：正常 1 条 + 参数异常若干 + 边界若干 + 鉴权 3 条 + 业务异常若干 + 并发/幂等 2 条。

7.4 Postman 实战

核心用法：Collection 管理用例、Environment 管理环境变量、Tests 写断言、Runner 批量执行。

7.6 接口断言体系

好的接口断言分层校验：HTTP 状态码 → 业务码 → 核心数据 → Schema/类型。只用 status=200 断言等于没测。 

# requests + pytest 接口测试示例
import requests
import pytest

BASE = 'https://api.example.com'

def test_login_success():
    r = requests.post(f'{BASE}/login',
                      json={'phone': '13800138000', 'pwd': 'abc123'})
    assert r.status_code == 200          # ① 状态码
    body = r.json()
    assert body['code'] == 0             # ② 业务码
    assert body['data']['token']         # ③ 关键字段存在
    assert isinstance(body['data']['token'], str)  # ④ 类型校验

@pytest.mark.parametrize('payload', [
    {'phone': '', 'pwd': 'abc123'},      # 手机号为空
    {'phone': '123', 'pwd': 'abc123'},   # 手机号格式错
    {'phone': '13800138000', 'pwd': ''}, # 密码为空
])
def test_login_invalid(payload):
    r = requests.post(f'{BASE}/login', json=payload)
    assert r.status_code == 400 or r.json()['code'] != 0

08 自动化测试（Selenium）

8.1 什么该自动化、什么不该

适合自动化 不适合自动化
回归频繁的稳定功能 一次性探索性测试
大量数据的参数化验证 UI 频繁改动的冒烟前期
跨系统集成流程 视觉/音效等主观体验
CI 中的冒烟与回归 短期需求的一次性验证
避坑：自动化不是"越多越好"。UI 自动化维护成本高（元素一改全挂），稳定业务才值得自动化；接口自动化性价比通常更高。

8.2 Selenium 原理

Selenium WebDriver 基于 WebDriver 协议：测试脚本（Python/Java）通过 HTTP 把命令发给浏览器驱动（chromedriver/geckodriver），驱动再调用浏览器原生接口执行操作。

一句话：脚本 → WebDriver 协议 → 浏览器驱动 → 真实浏览器。所以脚本语言可以任选，行为一致。

8.3 元素定位八法

定位方式 示例 优先级
id By.ID, 'username' 首选，唯一稳定
name By.NAME, 'username' 次选
class By.CLASS_NAME, 'btn-primary' 注意同 class 多个元素
tag By.TAG_NAME, 'input' 极不推荐，太泛
link_text By.LINK_TEXT, '登录' 仅精确文本链接
partial_link By.PARTIAL_LINK_TEXT, '登' 部分文本链接
css_selector By.CSS_SELECTOR, '#login input[type=password]' 推荐，快且灵活
xpath By.XPATH, "//input[@id='username']" 兜底，最慢

8.4 三种等待

等待 写法 特点
强制等待 time.sleep(2) 固定死等，不稳定，少用
隐式等待 driver.implicitly_wait(10) 全局兜底，每次查找轮询，太"钝"
显式等待 WebDriverWait + expected_conditions 针对元素等条件，精确高效
🧠 口诀：「能显式不隐式，sleep 是最后手段」。显式等待最稳定：等元素可点、可见、出现指定文本，条件满足立即继续。

8.5 PO 模式（Page Object）

把每个页面封装成类，元素定位与操作都收进页面类里，测试用例只负责"业务流程编排"。页面改了只改一处，用例不碎一地。 

# PO 模式：页面对象 + 用例分离
from selenium.webdriver.common.by import By
from selenium.webdriver.support.ui import WebDriverWait
from selenium.webdriver.support import expected_conditions as EC

class LoginPage:
    """登录页面对象：元素与操作都封装在这里"""
    url = 'https://example.com/login'

    def __init__(self, driver):
        self.driver = driver

    def open(self):
        self.driver.get(self.url)

    def login(self, phone, pwd):
        # 显式等待元素可操作
        phone_input = WebDriverWait(self.driver, 10).until(
            EC.presence_of_element_located((By.ID, 'phone')))
        phone_input.send_keys(phone)
        self.driver.find_element(By.ID, 'pwd').send_keys(pwd)
        self.driver.find_element(By.CSS_SELECTOR, '.btn-login').click()

    def get_error_text(self):
        return self.driver.find_element(By.CLASS_NAME, 'err-msg').text


# ---------- 测试用例：只关心业务 ----------
def test_login_ok(driver):
    page = LoginPage(driver)
    page.open()
    page.login('13800138000', 'abc123')
    assert '登录成功' in page.get_error_text() or 'home' in driver.current_url

8.6 数据驱动与关键字驱动

  • 数据驱动：测试步骤固定，数据从外部（Excel/JSON/CSV）读取，一份脚本跑多组数据
  • 关键字驱动：把"打开页面/输入/点击/断言"封装成关键字，用表格编排用例，非技术人员也能维护
演进路径：线性脚本 → 模块化 → 数据驱动 → 关键字驱动 → 测试平台化。团队成熟度不同，别一步跨到最复杂。

09 单元测试与代码质量

9.1 单元测试是什么

单元测试是对最小代码单元（函数/方法/类）的自动化验证，在开发阶段由开发者（或测试开发）编写，追求快速、隔离、可重复。

  • 最快反馈：秒级运行，改完即测
  • 精准定位：失败直接指向具体函数
  • 重构保险：敢改代码不怕改坏
  • 活的文档：用例即用法示例

9.2 pytest 核心用法

# 安装：pip install pytest
import pytest


# 断言用原生 assert，失败信息友好
def add(a, b):
    return a + b


def test_add():
    assert add(1, 2) == 3
    assert add(-1, 1) == 0

    (1, 2, 3),
    (0, 0, 0),

def test_add_param(a, b, expected):

# fixture：共享前置/后置
@pytest.fixture

Stub 桩 替身：固定返回预设结果 只"给数据"，不验证调用
Mock 模拟 替身 + 记录调用行为 可断言"被调用了几次、传了什么参数"

9.4 代码覆盖率

覆盖率度量被测试代码的执行比例，常见四种：行覆盖、函数覆盖、分支覆盖、语句覆盖。工具：pytest-cov、JaCoCo（Java）、Istanbul（JS）。 

# 运行并统计覆盖率
pytest --cov=myapp --cov-report=html --cov-fail-under=80
避坑：覆盖率 100% ≠ 质量好——没断言的用例也能拉高覆盖率。关注"关键分支是否被断言覆盖"，而不是数字游戏。

9.5 TDD / BDD / ATDD

方法论 核心思想 流程
TDD 测试驱动开发 先写测试，再写实现 红（失败）→ 绿（通过）→ 重构
BDD 行为驱动 用自然语言描述行为 Given…When…Then…（如 Cucumber）
ATDD 验收测试驱动 先定验收标准再开发 需求讨论 → 验收用例 → 实现
🧠 口诀：TDD 治"怎么写"，BDD 治"写什么"，ATDD 治"什么时候算完"。

9.6 代码质量工具

  • SonarQube：静态扫描，检查坏味道、重复代码、圈复杂度、安全漏洞
  • 圈复杂度：衡量代码分支复杂度，越高越难测，建议控制在 10 以内
  • Code Review：人工审查，配合静态扫描互补
  • 规范检查：ESLint（JS）、flake8/ruff（Python）、Checkstyle（Java）

10 数据库测试与 SQL

10.1 为什么测试要会 SQL

  • 准备数据：造数、修改订单状态、模拟历史数据
  • 验证结果：断言界面操作是否真的写对了库
  • 清理数据：测试后恢复现场，避免数据污染
  • 定位问题：区分"前端没展示"还是"库没写入"
核心心法：界面是表象，数据库是真相。测试时"界面 + 接口 + 数据库"三方对照，才能确认数据一致性。

10.2 SQL 必备语法

-- 查询
SELECT id, name, amount FROM orders WHERE user_id = 7;

-- 分组统计：每个用户的订单数与总额
SELECT user_id, COUNT(*) AS cnt, SUM(amount) AS total
FROM orders
WHERE status = 'PAID'
GROUP BY user_id
HAVING cnt > 1          -- HAVING 过滤分组结果
ORDER BY total DESC
LIMIT 10;

-- 多表连接
SELECT o.id, u.name FROM orders o
JOIN users u ON o.user_id = u.id;

-- 更新/删除（测试中慎用，记得 where 精确）
UPDATE orders SET status = 'PAID' WHERE id = 123;
DELETE FROM orders WHERE id = 456;

10.3 事务与 ACID

特性 含义
原子性 Atomicity 要么全成功，要么全回滚
一致性 Consistency 事务前后数据都符合约束
隔离性 Isolation 并发事务互不干扰
持久性 Durability 提交后数据永久保存
🧠 口诀：「原一持隔」——原子性、一致性、持久性、隔离性。
隔离级别 脏读 不可重复读 幻读
读未提交 可能 可能 可能
读已提交 避免 可能 可能
可重复读（MySQL 默认） 避免 避免 基本避免
串行化 避免 避免 避免

10.4 索引与失效场景

索引为什么快：B+ 树把全表扫描变成对数级查找。但索引不是万能的，这些场景会导致索引失效：

  • 对索引列做函数运算：WHERE YEAR(create_time)=2024
  • 隐式类型转换：phone 是 varchar，WHERE phone=138…（数字）
  • 模糊匹配前置通配符：LIKE '%abc'
  • 联合索引不满足最左前缀
  • OR 连接非索引列
  • 数据量太小，优化器放弃索引走全表
测试关注：查询接口慢的时候，先看执行计划（EXPLAIN），确认是否走了索引、扫描了多少行——这往往是"接口慢"的真相。

10.5 测试中的 SQL 实践

# 测试脚本中的数据库操作（pymysql 示例）
import pymysql

conn = pymysql.connect(host='127.0.0.1', user='test',
                       password='test', database='shop')


def prepare_order(user_id, amount):
    """造数：直接插入一条待支付订单"""
    with conn.cursor() as cur:
        cur.execute(
            'INSERT INTO orders (user_id, amount, status) VALUES (%s,%s,%s)',
            (user_id, amount, 'PENDING'))
    conn.commit()
    return cur.lastrowid


def assert_order_paid(order_id):
    """断言：支付后订单状态应为 PAID"""
    with conn.cursor() as cur:
        cur.execute('SELECT status FROM orders WHERE id=%s', (order_id,))
        row = cur.fetchone()
    assert row[0] == 'PAID', f'订单 {order_id} 状态异常: {row}'
红线：严禁在生产库执行 DELETE/UPDATE 造数或清理！测试数据操作一律限定在测试库，且 SQL 必须带精确 WHERE。

10.6 高频 SQL 面试/笔试场景

-- ① 分组 TopN：每个部门工资前三
SELECT * FROM (
  SELECT e.*, ROW_NUMBER() OVER (
    PARTITION BY dept_id ORDER BY salary DESC) rn
  FROM emp e) t
WHERE t.rn <= 3;

-- ② 去重保留最小 id
DELETE FROM users WHERE id NOT IN (
  SELECT MIN(id) FROM users GROUP BY phone);

-- ③ 连续登录（lag 窗口函数）
SELECT DISTINCT user_id FROM (
  SELECT user_id, login_date,
         LAG(login_date, 2) OVER (
           PARTITION BY user_id ORDER BY login_date) d2
  FROM user_login) t
WHERE DATEDIFF(login_date, d2) = 2;

11 性能测试

11.1 性能测试类型

类型 目的 示例
负载测试 验证正常负载下表现 1000 并发跑 30 分钟
压力测试 找到系统崩溃的临界点 逐渐加压到 5000 并发
并发测试 验证并发正确性（超卖/死锁） 100 线程同时下单

11.2 核心指标

指标 含义 健康参考
TPS 每秒完成的事务数 越高越好，看业务目标
QPS 每秒查询/请求数 与 TPS 常混用，关注口径
RT / ART 响应时间 / 平均响应时间 接口一般 <200ms 优，<1s 可接受
P95 / P99 95%/99% 请求在多少时间内完成 P99 才反映长尾体验
错误率 失败请求占比 一般要求 <0.1%
资源利用率 CPU/内存/IO/网络 CPU 70–80% 需警惕，100% 打满
🧠 口诀：「量、时、错、源」——吞吐量、响应时间、错误率、资源利用率，性能报告四件套。

11.3 JMeter 实战流程

  1. 线程组：设置并发数、Ramp-Up、循环次数
  2. HTTP 请求 Sampler：配置协议、域名、路径、参数
  3. 断言：响应断言（状态码、关键字）
  4. 监听器：聚合报告、响应时间图、TPS 图
  5. 运行：GUI 小规模调试，命令行大规模压测
# JMeter 命令行压测（GUI 只用于调试）
jmeter -n -t test.jmx -l result.jtl \
       -e -o report_html \
       -Jusers=1000 -Jduration=600

# 生成的结果：result.jtl（原始数据）+ report_html（HTML 报告）

11.4 性能瓶颈定位思路

从现象倒推原因，逐层排查：

现象 排查方向
CPU 打满 死循环、GC 频繁、正则/加密计算、日志过多
内存上涨 内存泄漏、大对象、缓存无上限
RT 高但机器空闲 慢 SQL、锁等待、远程调用超时、网络
TPS 上不去 连接池打满、队列堆积、单点串行
错误率升高 超时、限流触发、线程池拒绝

11.5 常见调优手段

  • 数据库：加索引、分库分表、慢 SQL 优化、读写分离
  • 缓存：热点数据上 Redis，降低 DB 压力
  • 异步化：非核心逻辑进 MQ，削峰填谷
  • 应用层：连接池调优、JVM 参数、限流熔断
  • 架构层：水平扩容、负载均衡、CDN 静态化
避坑：压测必须隔离环境 + 真实数据规模。拿 1000 条数据的库压测没意义——生产 1 亿条数据，索引失效直接打崩。

13 安全测试基础

13.1 OWASP Top 10 概览

风险 一句话理解
失效的访问控制 越权访问他人数据/功能
加密失败 敏感数据明文存储/传输
注入 SQL/命令/代码注入
不安全设计 架构层面缺少安全约束
安全配置错误 默认口令、错误页泄露信息、CORS 放开
易受攻击组件 依赖库有已知漏洞未升级
认证与识别失败 弱口令、撞库、会话固定
软件与数据完整性失败 反序列化漏洞、更新链被篡改
日志与监控不足 攻击发生无日志可查
服务端请求伪造 SSRF 诱导服务器访问内网

13.2 SQL 注入原理与防御

原理：用户输入被拼进 SQL 语句执行，导致查询逻辑被篡改。例如用户名输入 ' OR '1'='1 绕过登录。 

# 危险写法：字符串拼接
sql = "SELECT * FROM users WHERE name='" + name + "'"
# 输入  ' OR '1'='1   → 变成
# SELECT * FROM users WHERE name='' OR '1'='1'   # 恒真，绕过登录！

# 正确写法：参数化查询
cur.execute('SELECT * FROM users WHERE name=%s', (name,))
🧠 口诀：「参数化打底、白名单加固、最小权限兜底」——参数化能堵住绝大多数注入；特殊场景（排序字段、表名）用白名单校验；数据库账号按需授权。

13.3 XSS 跨站脚本

类型 触发方式 危害
反射型 URL 参数带脚本，未过滤直接渲染 诱导点击窃取 Cookie
存储型 评论/昵称存脚本，所有人访问都执行 蠕虫传播、批量窃取
DOM 型 前端 JS 操作 DOM 时注入 绕过服务端过滤
防御：输出编码（<script> 转义为 &lt;script&gt;）、CSP 策略、HttpOnly Cookie。

13.4 CSRF 与越权

  • CSRF 跨站请求伪造：用户已登录，攻击者诱导浏览器自动发请求（改密码/转账）。防御：CSRF Token、同源校验、SameSite Cookie。
  • 越权：水平越权（改 URL 中的 id 看别人的订单）、垂直越权（普通用户调管理员接口）。防御：服务端每次请求校验身份与资源归属。
🧠 口诀：「水平换 id，垂直换角色」——测试越权就这两招：把 id 换成别人的，把角色从普通用户换成管理员再调接口。

13.5 安全测试流程与工具

  1. 信息收集：域名、端口、指纹、技术栈
  2. 漏洞扫描：AWVS/AppScan/Nessus 自动化扫描
  3. 人工验证：Burp Suite 改包验证（绕过前端校验、篡改参数）
  4. 专项测试：注入、越权、文件上传、反序列化、逻辑漏洞
  5. 报告与复测：出具风险等级报告，修复后回归
红线：安全测试只允许在授权范围内进行！未授权的扫描/攻击是违法行为。测试账号数据用脱敏数据，严禁触碰生产真实用户数据。

14 持续集成与测试平台

14.1 CI/CD 三兄弟

概念 做什么 测试的价值
持续集成 CI 代码提交即自动构建 + 自动测试 测试是 CI 的"守门员"
持续交付 CD 构建产物随时可部署到任何环境 测试通过即可发布
持续部署 自动部署到生产 全自动流水线 + 生产监控兜底

14.2 流水线中的测试分层

# GitLab CI 示例：测试分层流水线
stages:
  - test
  - build
  - deploy

# ① 单元测试（最快，最先跑）
unit-test:
  stage: test
  script:
    - pip install -r requirements.txt
    - pytest tests/unit --cov=app --cov-fail-under=80

# ② 接口测试（依赖被测服务）
api-test:
  stage: test
  script:
    - docker compose up -d app
    - pytest tests/api -m api

# ③ E2E 冒烟（最慢，放最后）
e2e-smoke:
  stage: test
  script:
    - pytest tests/e2e -m smoke
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
为什么按这个顺序？单测秒级、接口分级、E2E 最慢——把最便宜的先跑，快速失败、快速反馈。

14.3 质量门禁

质量门禁是流水线上的"硬关卡"，不满足就阻断发布：

  • 单元测试通过率 = 100%
  • 覆盖率 ≥ 80%（新代码）
  • 静态扫描无 P0/P1 级问题
  • 接口测试全部通过
  • 冒烟测试通过
门禁的意义：把"质量靠人盯"变成"质量靠流程守"。门禁一旦设立，就是团队红线，不可随意绕过。

14.4 测试左移与右移

方向 做什么 典型活动
左移 测试往开发前期移动 需求评审、静态扫描、单测、代码评审
右移 测试延伸到生产阶段 灰度验证、生产监控、A/B 测试、混沌演练
🧠 口诀：「左移降成本，右移保体验」——左移尽早发现缺陷，右移确保线上真实环境质量。

14.5 测试平台化

成熟团队会把能力沉淀为平台：用例管理平台（用例在线维护）、自动化执行平台（定时/触发执行 + 报告）、测试环境管理（环境申请与释放）、数据工厂（造数平台）、质量大盘（度量可视化）。

避坑：平台化是"锦上添花"不是"雪中送炭"。流程混乱、用例都没沉淀时先搞平台，只会造出一堆没人用的"系统"。

15 测试架构与分层策略

15.1 测试金字塔

测试金字塔是最经典的分层策略：底层单元测试数量最多、速度最快、成本最低；中层接口测试；顶层 E2E 测试数量最少、最慢、最脆弱。

层级 数量 速度 成本 定位
E2E 端到端 少（10% 左右） 最慢（分钟级） 最高 核心主流程兜底
接口测试 中（30%） 快（秒级） 中 业务逻辑主战场
单元测试 多（60%+） 最快（毫秒级） 最低 代码逻辑兜底
为什么这样分？E2E 慢且脆，跑一次全量要几十分钟还老"误报"；单元测试秒级跑完千条。把验证重心压到中下层，反馈又快又稳。

15.2 分层测试策略设计

  • 冒烟层：每次构建跑，主流程快速过（登录、下单、支付）
  • 回归层：每晚/每次合并跑，全量用例
  • 专项层：性能/安全/兼容，按迭代节奏跑
  • 线上层：生产监控、巡检、拨测

15.3 测试右移实践

实践 说明
灰度发布 新版本先给 5% 用户，监控无恙再全量
线上巡检 定时脚本拨测核心链路（可用性、响应时间）
A/B 实验 同一功能两版本对比，用数据决策
全链路压测 生产环境模拟大促流量，验证容量
故障演练 主动注入故障（杀进程、断数据库），验证降级预案

15.4 全链路测试与混沌工程

  • 全链路测试：贯穿 App → 网关 → 微服务 → DB/缓存/MQ 的完整链路，配合链路追踪（SkyWalking/Zipkin）定位问题
  • 混沌工程：在生产（或镜像环境）主动注入故障，验证系统韧性——"提前打破，才能不怕坏"
一句话：测试金字塔管"上线前"，测试右移管"上线后"，全链路与混沌把两段连成闭环。

16 测试数据管理

16.1 测试数据的类型

类型 说明 示例
基础数据 系统运行必需 用户、商品、配置项
业务数据 支撑业务场景 订单、支付流水、优惠券
边界数据 验证边界逻辑 金额 0.01、最大长度、临界库存
异常数据 触发异常分支 空值、非法格式、失效状态
海量数据 性能与分页验证 百万级订单、千万级用户

16.2 造数方式对比

方式 优点 缺点
手工录入 简单 慢、易错、不可重复
SQL 造数 快、可控 需懂库结构，易污染
接口造数 走真实业务逻辑 依赖接口完整
造数工具/脚本 可复用、可批量 需要开发维护
数据工厂平台 按需自助、统一管理 建设成本高

16.3 数据脱敏规则

字段 脱敏示例
姓名 张三 → 张*
手机号 138****8000
身份证 110101********1234
银行卡 6222 **** **** 1234
邮箱 a***@example.com
地址 广东省深圳市***
合规红线：生产数据复制到测试环境必须脱敏！《个人信息保护法》下，泄露真实用户信息（即使只是测试环境）也是重大违规。

16.4 数据隔离与清理

  • 按环境隔离：每套环境独立数据库，互不串数据
  • 按人/分支隔离：多人并行测试时按租户/前缀区分数据
  • 定时清理：用例后置清理（fixture teardown）、每日定时清库
  • 数据版本快照：关键场景可整体恢复（数据库备份还原）
避坑：清理数据时注意外键与关联表顺序，先删子表再删主表；批量清理务必加 LIMIT 分批，避免长事务锁死。

16.5 测试数据平台化

成熟方案：数据工厂——按业务场景一键造数（如"生成一个已支付待发货的订单"），数据脱敏服务，数据生命周期管理（自动过期、自动清理）。

17 测试度量与效能

17.1 核心度量指标

指标 公式/含义 看什么
用例执行率 已执行 / 计划执行 是否按计划完成
用例通过率 通过 / 执行总数 质量达标情况
需求覆盖率 已测需求 / 总需求 是否有漏测风险
缺陷密度 缺陷数 / 千行代码（KLOC） 模块质量横向对比
缺陷逃逸率 线上缺陷 /（测试缺陷 + 线上缺陷） 测试有效性核心指标
自动化率 自动化用例 / 总用例 回归效率潜力
🧠 口诀：「覆盖看漏测，逃逸看质量」——需求覆盖率防漏测，缺陷逃逸率衡量测试真的拦住多少问题。

17.2 缺陷分析

  • 按模块分布：哪块代码缺陷多，资源就往哪倾斜
  • 按阶段分布：缺陷多在哪个阶段引入（需求/设计/编码）→ 改进对应环节
  • 按类型分布：逻辑错误、边界、并发、性能、UI……找出共性
  • 80/20 法则：20% 的模块贡献 80% 的缺陷

17.3 根因分析工具

工具 用法
5 Why 分析法 连续追问 5 个"为什么"挖到根因
鱼骨图 从人机料法环（人员/机器/材料/方法/环境）找原因
帕累托图 缺陷按数量排序，聚焦"少数关键"
复盘会 事故后复盘：根因 → 改进 → 跟踪闭环
5 Why 示例：线上订单丢失 → 为什么？支付回调没处理 → 为什么？回调逻辑有 bug → 为什么？没测过该场景 → 为什么？用例缺失 → 为什么？需求评审没识别该场景。根因在需求环节，而非"修个 bug"。

17.4 测试效能提升

  • 提自动化率：把高频回归自动化，释放人力做探索性测试
  • 并行执行：分布式跑用例（pytest-xdist、Selenium Grid）
  • 用例瘦身：定期删除重复、无效、长期 P3 用例
  • 精准测试：按代码变更影响范围选择回归用例，不全量跑
  • 反馈闭环：测试问题当天同步开发，别攒到最后
避坑：自动化率不是越高越好。为了"率"而自动化的脆弱 UI 用例，维护成本会反噬团队。先算 ROI，再决定自动化什么。

17.5 质量报告体系

分层报告：每日（执行进度 + 阻塞）、迭代（缺陷分析 + 质量结论）、季度（质量趋势 + 改进成果）。报告用趋势图说话，让质量"看得见、可改进"。

18 前沿趋势与 AI 测试

18.1 AI 辅助测试

环节 AI 能做什么
用例生成 根据需求/接口文档自动生成测试用例与断言
元素定位 智能识别页面元素，减少维护成本
缺陷分析 自动聚类相似缺陷、识别高频根因
失败分析 自动化用例失败时智能定位"用例问题还是产品 bug"
视觉回归 图像对比找 UI 差异（pixelmatch 等）

18.2 智能用例生成示例（LLM）

# 用 LLM 生成边界用例（示意）
prompt = """
需求：注册接口，手机号 11 位、密码 6-20 位含字母数字。
请生成等价类 + 边界值测试用例，输出 JSON 数组，字段：
title, phone, pwd, expect_code
"""

# 可能的输出（示意）：
# [
#   {"title": "合法手机号+合法密码", "phone": "13800138000", "pwd": "abc123", "expect_code": 0},
#   {"title": "手机号 10 位",         "phone": "1380013800", "pwd": "abc123", "expect_code": 400},
#   {"title": "密码 5 位",            "phone": "13800138000", "pwd": "abc12", "expect_code": 400},
#   {"title": "密码 20 位",           "phone": "13800138000", "pwd": "abc12345678901234567", "expect_code": 0},
# ]
AI 测试的核心：AI 是"提效助手"不是"替代者"。它擅长生成、聚类、初筛，最终判断质量结论的仍需要人来把关。

18.3 精准测试

基于代码变更分析（Diff + 调用链）自动圈定受影响范围，只回归相关用例，把回归时间从"全量几小时"降到"精准几分钟"。

为什么是趋势？微服务 + 快速迭代下，全量回归跑不动了。精准测试让"改一行代码"的验证成本趋近于零，是 CI 提速的关键技术。

18.4 大模型/智能应用测试

  • LLM 功能评测：正确性、相关性、幻觉率、有害内容
  • RAG 评测：检索命中率、引用一致性、上下文长度边界
  • Agent 评测：任务完成率、工具调用正确性、多轮稳定性
  • 测试基建：评测集（Golden Set）、LLM-as-Judge、在线评测流水线

18.5 测试开发成长路线

阶段 核心能力 代表产出
入门（0–1 年） 手工功能测试、用例设计、缺陷管理 高质量用例、缺陷报告
中级（1–3 年） 接口测试、自动化、SQL、性能基础 接口/UI 自动化脚本、压测报告

18.6 学习路线与资源

  1. 第 1–2 周：测试基础、用例设计方法（本笔记 1–3 章）
  2. 第 3–4 周：接口测试（Postman + requests + 实际项目）
  3. 第 5–6 周：自动化测试（Selenium + PO 模式 + pytest）
  4. 第 7–8 周：SQL 与数据库测试、性能测试（JMeter）
  5. 第 9–10 周：移动端专项、安全测试基础、CI/CD 集成
  6. 持续：AI 测试、平台建设、质量治理、跟进行业实践
最重要的建议：动手实践。把一套真实系统（或开源项目）从用例设计到自动化、到压测完整做一遍。测试是"手艺活"，纸上得来终觉浅。
