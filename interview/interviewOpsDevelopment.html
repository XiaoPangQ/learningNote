01运维基础与职业认知

Q
运维工程师的职责是什么？运维的价值在哪里？🔥 高频

核心职责：

  • 保障稳定性：保障线上服务 7×24 可用（可用性 ≥ 99.9%）
  • 交付效率：搭建 CI/CD 流水线，让发布又快又稳
  • 成本控制：容量规划、资源利用率优化
  • 安全保障：漏洞修复、权限管控、数据备份
  • 效率提升：把重复劳动工具化、自动化、平台化

运维的价值：不是「修机器的」，而是用技术手段让业务跑得稳、跑得快、花得少；每一次故障的避免都是隐形的收益。

「稳、快、省、安、效」五字诀——稳定是底线，效率是追求，自动化是出路
Q
SRE 和传统运维有什么区别？🔥 高频

SRE（Site Reliability Engineering，站点可靠性工程）由 Google 提出，核心是用软件工程方法解决运维问题。

维度传统运维SRE
工作方式人工操作、救火式代码/工具自动化
目标不出故障SLO + 错误预算（允许合理故障率）
琐事重复劳动常态琐事（toil）占比 < 50%，超了就做自动化
应急靠经验预案、演练、无责复盘
传统运维「人盯机器」，SRE「代码管机器」；SLO 定目标，错误预算给弹性，toil 超半就自动化
Q
谈谈你对 DevOps 的理解？🔥 高频

定义：Development + Operations，打破开发与运维的墙，通过文化 + 流程 + 工具实现「快速交付 + 稳定运行」。

核心环节：计划 → 编码 → 构建 → 测试 → 发布 → 部署 → 运营 → 监控 → 反馈（闭环迭代）。

关键实践：

  • CI/CD：持续集成/持续交付（Jenkins、GitLab CI）
  • 基础设施即代码：IaC（Ansible、Terraform）
  • 容器化与微服务：Docker + K8s
  • 可观测性：监控 + 日志 + 链路追踪
「一个字：快；两个字：闭环；三个字：自动化」；Dev 做得快，Ops 管得稳，中间靠流水线

  • 手工操作 → 声明式自动化（IaC、GitOps）
  • 被动救火 → 可观测性 + 故障预测
  • 命令行运维 → 平台工程 / 自助化门户

「机器变服务，手工变声明，救火变预防」；不想被淘汰就学 K8s + 写代码

02Linux 基础与核心命令

Q
CPU 负载（load average）和 CPU 使用率有什么区别？🔥 高频

CPU 使用率：单位时间内 CPU 忙着干活的时间占比（用户态 us + 系统态 sy + 等 IO 的 wa 等）。

负载（load average）：一段时间内正在运行 + 等待运行（可运行态）+ 不可中断睡眠（D 状态，通常是等 IO）的任务数，三个数值分别是 1 / 5 / 15 分钟平均。

关键结论：

  • 负载和 CPU 核数比：load / 核数 > 1 表示过载（4 核机器 load > 4 就危险）
  • 负载高但使用率低 → 多半是 IO 瓶颈（D 状态进程堆积），不是 CPU 不够
  • 使用率高 + us 大 → 计算密集；sy 大 → 系统调用/上下文切换多；wa 大 → 等 IO
「使用率看忙不忙，负载看排队长不长」；负载除以核数，超 1 就排队，wa 高别加核——先查磁盘
Q
top 命令里主要看哪些指标？🔥 高频

头部全局指标：

  • load average：1/5/15 分钟负载（对照核数）
  • %Cpu(s)：us 用户态 / sy 内核态 / id 空闲 / wa 等 IO / st 被虚拟化偷走
  • MiB Mem / Swap：free 剩余、buff/cache 缓存、available 真正可用

进程区关键列：PID、USER、%CPU、%MEM、RES（常驻内存）、S（状态 R/S/D/Z）、TIME+。

常用交互键：P 按 CPU 排序、M 按内存排序、1 展开各核、c 显示完整命令、k 杀进程。

「先看负载再看 wa，us 计算重、wa 磁盘慢、sy 切换多」；进程排序 P 和 M，一眼找元凶
Q
ps 命令怎么用？进程有哪些状态？

常用：ps aux（BSD 风格全量）与 ps -ef（标准风格）；查某服务：ps aux | grep nginx。

进程状态（S 列）：

  • R：运行/就绪
  • S：可中断睡眠（等事件，多数进程常态）
  • D：不可中断睡眠（等 IO，kill -9 都杀不掉，负载高的常客）
  • Z：僵尸（子进程退出但父进程没回收）
  • T：停止
「R 跑 S 睡 D 硬等，Z 是僵尸 T 是停」；D 杀不死只能修 IO，Z 要打父进程
Q
kill -9 和 kill -15 有什么区别？
  • kill -15（SIGTERM，默认）：礼貌终止，进程可以捕获信号、清理资源（释放锁、刷盘）后再退出——首选。
  • kill -9（SIGKILL）：强制击杀，内核直接回收，进程无机会清理，可能丢数据、留脏文件——最后手段。
  • kill -1（SIGHUP）：挂断信号，常被用于重载配置（如 nginx -s reload 的效果）。
  • kill -HUP pid / kill -USR2：平滑重启类。

顺序建议：先 kill -15，等几秒没退出再 kill -9。

「15 商量着走，9 直接枪毙」；先礼后兵，能 -15 别 -9
Q
free 命令输出怎么解读？buffer 和 cache 有什么区别？🔥 高频 
$ free -h
              total   used   free   shared  buff/cache   available
              7.6Gi   2.1Gi  500Mi  100Mi   5.0Gi        5.2Gi
  • buff（缓冲）：写方向缓存，暂存要写入磁盘的数据
  • cache（缓存）：读方向缓存，缓存从磁盘读出的数据
  • available 才是关键：free 小 ≠ 内存不足，因为 buff/cache 在内存紧张时会自动释放
  • 判断标准：available 持续很低 + swap used 增长 → 真缺内存
「buffer 管写，cache 管读；不看 free 看 available」；Linux 白拿闲内存当缓存，不是泄漏
Q
进程被 OOM Kill 了，如何排查？🔥 高频

什么是 OOM：物理内存 + swap 都耗尽时，内核的 OOM Killer 按 oom_score（内存占用越大分越高）选进程杀掉自救。

排查步骤：

  1. 确认 OOM：dmesg -T | grep -i "killed process" 或 grep -i oom /var/log/messages
  2. 看内存趋势：Prometheus/Grafana 内存曲线、sar -r 历史数据
  3. 定位进程：top / ps aux --sort=-%mem | head 找内存大户
  4. 分清类型：内存泄漏（只涨不降）还是 配置不足（流量高峰打满）
  5. 处理：加内存/加交换分区应急 → 泄漏则 dump 分析或升级修复 → 关键服务设 oom_score_adj 保护
「dmesg 找证据，曲线分泄漏；只涨不降是泄漏，高峰打满是容量」

Q
软链接和硬链接的区别？🔥 高频
维度硬链接 ln软链接 ln -s
本质指向同一 inode独立文件，存路径
跨分区不能可以
链接目录不能可以
源文件删除不影响（链接数-1）悬空失效（红闪）
文件大小与源相同为路径字符串长度
ln  file.txt  file.hard      # 硬链接：inode 相同
ln -s /data/app/log  /var/log/app   # 软链接：常用，路径可迁移
ls -li   # -i 可查看 inode 号验证
「硬连 inode 共生死，软连路径像快捷方式」；运维场景多用软链（版本切换、日志迁移）
Q
find 常用姿势？文本三剑客怎么分工？🔥 高频 
find /var/log -name "*.log" -mtime +7 -size +100M   # 7 天前且大于 100M
find / -type f -perm /4000 2>/dev/null              # 找 SUID 文件（安全审计）
find ./ -name "*.tmp" -exec rm -f {} \;              # 找到即删
find ./ -name "*.log" | xargs grep -l "ERROR"        # 配合 xargs 搜内容

三剑客分工：grep 负责找（过滤行）、sed 负责改（编辑替换）、awk 负责算（按列处理）。

「grep 找、sed 改、awk 算」；find 按条件选文件，xargs 把文件名变参数
Q
awk 和 sed 有哪些高频用法？ 
# awk：取列、过滤、统计
awk -F: '{print $1, $NF}' /etc/passwd     # 按冒号分隔，打印首尾列
awk '$3>1000{print $1}' file              # 第三列大于 1000 的行
awk '{sum+=$1} END{print sum/NR}' file     # 求平均值

# sed：替换、删除、追加
sed -i 's/8080/9090/g' app.conf           # 全局替换并写回文件
sed -n '10,20p' file                       # 只看 10-20 行
sed '/^#/d;/^$/d' file                     # 删注释行和空行
awk「按列切」$1 第一列 NF 最后列；sed「按行改」s 替换 d 删除 -i 写回；改配置前先备份 cp conf conf.bak
Q
tar 打包压缩的常用命令？ 
tar czf app_$(date +%F).tar.gz app/          # 打包+gzip 压缩
tar xzf app_2026-08-27.tar.gz               # 解压
tar tf app.tar.gz                           # 不解压先看内容
tar czf etc.tar.gz -C / etc                 # -C 指定基目录，避免绝对路径
  • z=gzip（通用）、j=bzip2（更小更慢）、J=xz（最小最慢）
  • c=create 打包、x=extract 解压、t=list 查看、f=file 指定文件名（必须放最后）
「c 打 x 解 t 看，f 名字放最后，z 压 gzip」；备份命名带日期 $(date +%F)
Q
vmstat、iostat、sar 分别用来看什么？
  • vmstat：全局概览——r（运行队列，应 ≤ 核数）、si/so（swap 换入换出，非 0 即内存紧张）、bi/bo（块设备读写）、wa 高说明等 IO
  • iostat -x 1：磁盘细节——%util（接近 100% 即打满）、await（IO 平均等待毫秒数，机械盘 > 20 就偏慢）
  • sar -r / -n DEV / -q：历史回溯——内存、网卡流量、负载的按时间曲线，排查「昨晚几点开始出的问题」
「vmstat 看全局，iostat 看磁盘，sar 看历史」；si/so 非 0 内存紧，%util 打满盘不行，await 高要换 SSD

03文件系统与磁盘管理

Q
什么是 inode？磁盘有空间却提示 No space left 怎么回事？🔥 高频

inode：文件的「户口本」，存储元数据（权限、属主、时间戳、大小、数据块指针），不存文件名（文件名存在目录项里）。

两种磁盘满：

  • 块用完：大文件占满 df -h 可见 100%
  • inode 用完：海量小文件（邮件队列、session、缓存碎片），df -h 有空间但 df -i 100%，同样报 No space left
df -h                        # 看容量
df -i                        # 看 inode 使用率
for i in /*; do echo $i $(find $i -xdev | wc -l); done   # 定位小文件目录
「块装数据，inode 存户口」；df -h 满查大文件，df -i 满查海量小文件
Q
df 和 du 结果不一致是什么原因？磁盘满了怎么安全清理？🔥 高频

不一致原因：文件被 rm 删除但仍被进程持有句柄（常见于被删的日志），空间不会释放；df 看块位图，du 遍历目录，所以 df > du。

lsof | grep deleted           # 找被删但未释放的文件
# 方案一：重启或重载持有进程；方案二（不重启清日志）：
> /var/log/big.log             # 清空文件内容而非删除文件
truncate -s 0 /var/log/big.log

安全清理顺序：日志轮转压缩 → journalctl --vacuum-size=500M → yum clean all / apt clean → docker 镜像清理 → 最后才考虑删业务数据（先确认再动手）。

「df 大 du 小，句柄没放掉」；删文件 ≠ 释放空间，清日志用重定向别用 rm
Q
LVM 扩容的步骤？

LVM 三层结构：物理卷 PV → 卷组 VG → 逻辑卷 LV（在 LV 上建文件系统）。

pvcreate /dev/sdb                     # 1. 新盘建 PV
vgextend vg_data /dev/sdb             # 2. 加入 VG
lvextend -l +100%FREE /dev/vg_data/lv # 3. 扩 LV
resize2fs /dev/vg_data/lv             # 4. 在线扩文件系统（xfs 用 xfs_growfs）
df -h                                  # 5. 验证
「pv 建、vg 并、lv 扩、fs 长」四步走；ext4 用 resize2fs，xfs 用 xfs_growfs，缩容 risky 别乱试
Q
RAID 0、1、5、10 的区别与选型？🔥 高频
级别原理最少盘容量利用率容错
RAID 0条带化，分散写2100%无，坏一盘全完
RAID 1镜像，一份写两份250%坏一盘没事
RAID 5条带 + 分布式校验3(n-1)/n坏一盘可重建
RAID 10先镜像再条带450%性能与安全兼顾

选型：数据库等高 IO 高可靠 → RAID 10；文件存储性价比 → RAID 5/6；纯缓存临时数据 → RAID 0；系统盘 → RAID 1。

「0 快不容错，1 镜像贵一半，5 校验省盘，10 镜像加快」；数据库选 10，图便宜选 5
Q
mount 挂载与 /etc/fstab 怎么写？

Q
Linux 权限怎么计算？755、644 分别是什么意思？🔥 高频

权限位三组：属主 u、属组 g、其他人 o；每组三位 r=4、w=2、x=1，相加得出数字。

  • 755 = rwxr-xr-x：属主全权，其他人可进可执行（目录常用）
  • 644 = rw-r--r--：属主可读写，其他只读（普通文件常用）
  • 700/600：仅属主可用（私钥 ~/.ssh 必须 600，否则 ssh 拒用）
  • 目录的 x 代表能否进入，r 只是能 ls 看名字
chmod 755 deploy.sh        # 数字法
chmod u+x,g-w file          # 符号法
chown -R app:app /data/app  # 递归改属主属组
chmod 600 ~/.ssh/id_rsa     # 私钥权限，SSH 硬性要求
「读4写2执行1，主组其他排三组」；目录没 x 进不去，私钥不是 600 连不上

sudo 和 su 的区别？怎么给用户授权？

  • sudo：临时提权执行单条命令，用自己的密码，可限制命令范围、有审计日志

# 授权格式：用户  主机=(身份)  命令

「su 换人要 root 密码，sudo 借权用自己的密码」；授权用 visudo，命令写全路径

SUID、SGID、Sticky 分别是什么？

  • SGID（2xxx，g 位的 s）：目录下新文件继承目录属组，团队共享目录常用
  • Sticky（1xxx，o 位的 t）：在目录里只能删自己的文件，/tmp 的 1777 就是它

SSH 免密登录的原理和配置步骤？🔥 高频

TCP 三次握手和四次挥手的过程与原因？🔥 高频

三次握手（建连）：客户端 SYN → 服务端 SYN+ACK → 客户端 ACK。

  • 为什么三次：双方都要确认收发能力；两次会让失效的历史 SYN 突然到达造成错误连接
  • 握手失败看：服务端 SYN_RECV 堆积 = SYN 洪水攻击，可开 tcp_syncookies

四次挥手（断连）：主动方 FIN → 对方 ACK →（对方发完数据）FIN → 主动方 ACK，之后进入 TIME_WAIT 等 2MSL。

  • 为什么四次：TCP 全双工，两个方向要分别关；被动方可能还有数据没发完，ACK 和 FIN 分开发
  • TIME_WAIT 多：主动关闭方产生，量大可开 tcp_tw_reuse；服务器出现大量 CLOSE_WAIT = 程序没调用 close，代码 bug
「三握确认双收发，四挥全双工分头关」；CLOSE_WAIT 多是代码没关，TIME_WAIT 多是主动关太多

给个 IP 和掩码，怎么算网络地址和可用主机数？

  1. 掩码 26 = 255.255.255.192，借了 2 位主机位
  2. 块大小 = 256 - 192 = 64，子网按 64 切：0、64、128、192
  3. 130 落在 128–191 段 → 网络地址 192.168.10.128，广播 .191
  4. 可用主机 = 64 - 2（去网络地址和广播）= 62

私网地址三段：A 类 10.0.0.0/8、B 类 172.16.0.0/12、C 类 192.168.0.0/16。

NAT 的原理是什么？

NAT（网络地址转换）：出口路由器把内网私有 IP:端口 映射为公网 IP:端口，回程按映射表还原——一个公网 IP 背后可以藏整个内网。

  • SNAT：改源地址（内网上网：出方向）
  • DNAT：改目标地址（公网访问内网服务/端口映射：进方向）
  • 价值：缓解 IPv4 短缺 + 隐藏内网结构（附带安全）
「出网改源 SNAT，进网改目 DNAT」；一张映射表，进出两不改就丢

Nginx 为什么快（高性能原理）？🔥 高频
  • epoll 事件驱动：一个 worker 用 epoll 同时监听几万连接，就绪回调；对比 select 每次全量轮询（1024 上限）
  • master-worker 多进程：master 管配置与 fork，worker 干活互相独立，一个崩了不影响其他
  • 异步非阻塞 IO：worker 不傻等磁盘/后端，事件就绪再处理，不因慢客户端拖死
  • 内存池 + 连接池，避免频繁 malloc 和握手
  • 锁竞争少：worker 进程各管各的连接（accept_mutex / SO_REUSEPORT）
「epoll 多路复用 + 多进程 + 异步非阻塞」三板斧；能扛 C10K 到 C100K 全靠不阻塞

  }

「= 精确最优先，^~ 前缀免正则，~ 正则按顺序，普通前缀比长短」；改配置三连：-t 测试、reload、tail 错误日志

Q
线上出现 502 / 504，怎么排查？🔥 高频

本质：都是「Nginx 这个中间人联系不上后端」——502 是联系不上（连接被拒/进程挂了），504 是联系上了但等超时。

502 排查：

  1. 后端进程在不在：ss -tlnp | grep 8080、systemctl status
  2. 后端崩没崩：看应用日志、OOM 记录（被杀也会 502）
  3. php-fpm 场景：进程数打满（pm.max_children）、socket 文件权限

504 排查：

  1. 后端慢查询/死锁：看慢日志、show processlist
  2. 调超时：proxy_read_timeout 60s（默认 60s）
  3. 上游阻塞：连接池耗尽、依赖的下游（第三方接口）慢
「502 进程挂，504 进程慢」；先看后端活不活，再查慢在哪一环

Nginx 和 PHP-FPM 是怎么配合工作的？
  1. Nginx 收到 .php 请求，按 location 交给 FastCGI 协议转发给 php-fpm
  2. php-fpm 的 worker 进程执行 PHP 脚本（连接数据库、渲染页面）
  3. 结果经 FastCGI 返回 Nginx，Nginx 包成 HTTP 响应给用户
  4. 两种对接方式：TCP（127.0.0.1:9000）或 unix socket（同机更快）

常见调优：pm = dynamic，pm.max_children 按内存算 = 可用内存 / 单进程内存；502 常见原因就是 max_children 打满或进程崩。

「Nginx 收发快递，php-fpm 车间干活，FastCGI 是传菜口」；同机用 socket，跨机用 9000

Keepalived + VIP 是怎么实现高可用的？

原理：两台 Nginx 配 VRRP 协议，Keepalived 抢一个虚拟 IP（VIP）；主挂了，备秒级接管 VIP，客户端无感。

  • master 优先级 100，backup 90；心跳失败 → backup 抢 VIP 并发 ARP 通告
  • 脑裂：双方都认为自己是主（网络抖动）→ 两台都持有 VIP，可加仲裁/检测脚本降低概率
  • 常与 LVS 组合：Keepalived 管 HA，LVS 管 LB（lvs+keepalived 经典架构）
「VIP 一漂，服务不断」；主备心跳抢 IP，防脑裂要双线检测

Q
MySQL 主从复制的原理？主从延迟怎么处理？🔥 高频

复制流程（三线程）：

  1. 主库提交事务写入 binlog，Dump 线程推送给从库
  2. 从库 IO 线程拉取 binlog 写入本地中继日志 relay log
  3. 从库 SQL 线程重放 relay log，数据达成一致

主从延迟原因与对策：从库单线程重放慢、大事务、从库机器差 → 半同步复制、并行复制（MTS）、拆大事务、读写分离时「写后读走主库」。

「主写 binlog，IO 拉中继，SQL 来重放」；延迟三大招：并行复制、拆事务、关键读走主
Q
MySQL 慢了怎么排查和优化？🔥 高频

排查链路：开慢查询日志 → explain 分析 → 看索引/type/rows → 优化。

SET GLOBAL slow_query_log=ON;
SET GLOBAL long_query_time=1;     # 超过 1 秒记日志
mysqldumpslow -s t -t 10 slow.log # 按耗时取 Top10
EXPLAIN SELECT ...                 # 重点看 type/key/rows/Extra

优化要点：慢 SQL 加合适索引（type 到 ref/range 以上）；Extra 出现 Using filesort / Using temporary 说明排序临时表要治；避免 select *、深度分页用游标；单表过大考虑分库分表归档；参数层调 buffer_pool（物理内存 50–70%）。

「慢日志抓现行，explain 定病因，索引治排序，分页防深翻」

哪些情况索引会失效？🔥 高频
  • 对索引列做函数或运算：WHERE YEAR(create_time)=2026 → 改范围查询
  • 最左前缀被跳过：联合索引 (a,b,c) 只查 b、c
  • 隐式类型转换：字符串列用数字查 phone=13800000000
  • 前导模糊：LIKE '%xx' 失效（'xx%' 可用）
  • OR 两侧有非索引列
  • != / NOT IN / IS NULL 视数据分布可能放弃索引
「函数运算、左缀断裂、类型隐转、前置百分号」四大坑；联合索引像查字典，从第一个字母翻起

MySQL 死锁怎么排查和处理？
  1. 看错误日志：SHOW ENGINE INNODB STATUS 的 LATEST DETECTED DEADLOCK 段，能看到两个事务持锁与等待的 SQL
  2. 实时观察：SELECT * FROM information_schema.INNODB_TRX;（ trx_state=LOCK WAIT 的）
  3. 处理：死锁会被自动检测，回滚代价小的事务，应用侧重试即可
  4. 根治：事务小而快、多表按相同顺序加锁、索引齐全（锁行而非锁全表扫描）、必要时降低隔离级别 RC
「死锁自动解，重试保平安」；治本三招：事务短、顺序同、索引全

Pod 的生命周期和重启策略？🔥 高频

Pod 起不来（Pending / CrashLoopBackOff）怎么排查？🔥 高频

kubectl describe pod web-xxx      # 事件区（Events）是第一线索
kubectl logs web-xxx --previous   # 上一次崩溃的日志（关键！）
kubectl exec -it web-xxx -- sh    # 进去看看

对症下药：

  • Pending：资源不够（节点满）→ describe 看 FailedScheduling；或 PVC 没绑定、亲和性不满足
  • ImagePullBackOff：镜像名/标签错、仓库没权限 → 配 imagePullSecrets
  • CrashLoopBackOff：logs --previous 看崩溃原因——配置错、依赖连不上、探针太严
  • Evicted：节点内存压力驱逐 → 调 requests/limits 或加节点
「describe 看 Events，previous 看死因」；Pending 没地放，Crash 看日志，Pull 查镜像
Q
requests 和 limits 有什么区别？
  • requests：调度依据，承诺值——调度器保证节点至少有这么多资源
  • limits：上限，天花板——CPU 超了被节流（throttle），内存超了被 OOMKill
  • QoS 等级：requests=limits → Guaranteed（最稳）；都不设 → BestEffort（最先被驱逐）；中间 → Burstable
  • 经验：内存 requests=limits 防 OOM 波动；CPU 可 limits 略高于 requests 提利用率
「requests 是订票，limits 是天花板」；CPU 超限被限流，内存超限直接杀

Q
Prometheus 的架构和工作原理？🔥 高频
  • Pull 拉模型：Prometheus 周期性主动抓取目标的 /metrics 接口（ exporter 暴露指标），而非被推送——简单可靠、易排查
  • 组件：Prometheus Server（抓取+TSDB 存储）→ Alertmanager（分组、抑制、路由告警）→ Grafana（可视化）；服务发现对接 K8s/consul
  • Exporter：node_exporter（机器）、mysqld_exporter（数据库）、blackbox_exporter（拨测）
  • PromQL：rate(http_requests_total[5m]) 常用于算速率
  • 局限：存 15 天左右即定位短期监控；超长期下推 Thanos / VictoriaMetrics
「PULL 拉指标，metrics 出口，Alertmanager 告警，Grafana 看图」；短存本地长存 Thanos
Q
监控要看哪些指标？（USE / RED / 黄金四信号）🔥 高频
  • USE 法则（看资源）：每个资源看 Utilization 使用率、Saturation 饱和度（排队）、Errors 错误——CPU、内存、磁盘、网络挨个过
  • RED 法则（看服务）：每个服务看 Rate 请求量、Errors 错误率、Duration 耗时分布
  • Google 黄金四信号：延迟、流量、错误、饱和度
  • 经验：CPU/内存/磁盘/网络四件套 + 服务 QPS/RT/错误率 + 业务指标（下单量）三层都要有
「资源 USE，服务 RED」；机器看余量，服务看快慢，业务看涨跌

  • 分组与抑制：同机房故障聚合成一条；上游挂了抑制下游衍生告警
  • 每条告警必带：现象、影响的业务、runbook 链接（告警要可执行）
「分级、持续、聚合、抑制」八字；告警带 runbook，收到就知道点哪

ELK 的原理和链路？日志太多怎么优化？🔥 高频

链路：应用日志 → Filebeat（轻量采集）→ Kafka（削峰缓冲）→ Logstash（解析/grok 切字段）→ Elasticsearch（存储索引）→ Kibana（查询看板）。

  • 日志规范：JSON 格式 + trace_id 贯穿全链路，检索效率天差地别
「Filebeat 收、Kafka 缓、Logstash 切、ES 存、Kibana 查」；日志 JSON 化，检索带 trace_id

「先锁时间，再串 trace，最后对变更」；出问题先问：最近改了什么？

  • 聚合：同一根因的告警分组为一条（Alertmanager group_by）
  • 抑制：网络设备挂了就抑制其上所有主机的失联告警

「分聚合、抑静默、周复盘」；没人看的告警是噪音，不是保障

什么是 SLA、SLO、SLI 和错误预算？
  • SLI：指标（如成功率、P99 延迟）——量出来的
  • SLO：内部目标（如成功率 ≥ 99.9%）——自己定的
  • SLA：对客户的协议（含赔款条款）——写合同的
  • 错误预算 = 1 − SLO（99.9% 即每月允许约 43 分钟故障）；预算花完就冻结发布只做稳定性——用数据平衡快与稳

12故障排查与场景题

Q
服务器响应变慢，说下你的排查思路？🔥 高频

总纲：USE 法则，CPU → 内存 → 磁盘 IO → 网络，逐项排除：

  1. 先看全局：top / uptime——load 对比核数、%wa、swap si/so
  2. CPU 高：top 找进程 → pidstat -p PID 1 看是 us 还是 sy；Java 用 top -Hp + jstack 抓线程栈
  3. 内存紧：available 低、swap 换入换出 → 找内存大户，判断泄漏还是容量
  4. 磁盘慢：iostat -x 1 看 %util / await；iotop 找元凶进程（常见：日志刷爆、备份任务撞高峰）
  5. 网络：sar -n DEV 看带宽打满没；ss -s 看连接数；curl 计时 -w "%{time_total}" 分解耗时在哪段
  6. 应用层：慢日志、线程池满、锁等待、下游依赖慢
  7. 别忘了问：什么时候开始？之前改了什么？（变更即嫌疑）
「先 top 后分层：CPU 内存盘网挨个过；wa 高查盘，si/so 高查内存，最后查变更」
Q
用户反馈网站打不开，怎么办？🔥 高频
  1. 先确认范围：监控大盘还在吗？是个别用户还是全部？影响面决定级别
  2. 入口链路查：域名解析（dig）→ 入口 LB / CDN → 防火墙安全组
  3. 应用层：curl -v http://localhost 本机通不通 → Nginx 502/504？后端进程活着吗
  4. 资源层：负载是否打满、连接数是否爆、是否被打（CC/ syn flood）
  5. 数据层：数据库连接池满、锁等待、Redis 挂了导致依赖雪崩
  6. 止损优先：先重启/扩容/回滚恢复业务，再慢慢找根因（保留现场：日志、dump）
  7. 同步上报：现象、影响、进展、预计恢复时间
「先定面、再顺链、先止血、后验尸」；恢复优先于定位，保留现场再复盘
Q
磁盘使用率告警 90%+，怎么处理？🔥 高频

应急（先腾空间）：

df -h                                              # 确认哪个分区
du -xh --max-depth=2 /  2>/dev/null | sort -rh | head   # 找大目录
journalctl --vacuum-size=500M                      # 收 journald 日志
find /var/log -name "*.gz" -mtime +30 -delete      # 删旧压缩日志

定位（为什么涨）：日志没轮转（上 logrotate）？大文件被删未释放（lsof | grep deleted → 重载进程）？Docker 镜像堆积（docker system prune）？数据库 binlog/临时表？

根治：logrotate + 监控提前告警（80% 黄线）+ 容量规划 + 挂新盘/LVM 扩容。

「df 定分区，du 找大户，删前先备份」；应急清日志，根治上轮转
Q
发现服务器疑似被入侵（异常流量/陌生进程），怎么办？🔥 高频
  1. 隔离优先：先断网/摘流量（防火墙封 IP、安全组全断），别急着重启——内存痕迹会没
  2. 保留证据：ps、ss、crontab -l、~/.ssh/authorized_keys、history、/var/log/secure 打包留存
  3. 排查入口：last / lastb 看登录记录；新异常用户（/etc/passwd）；可疑计划任务（/var/spool/cron）；可疑 SUID 文件；开放端口对未知 IP
  4. 确认影响：对外扫描是否变成肉鸡；数据是否被拖
  5. 恢复：重装系统最稳；改所有密码与密钥；补漏洞（弱口令、未授权 Redis、过期组件）
  6. 复盘加固：密钥登录、最小端口、fail2ban、HIDS 入侵检测
「一断二存三查四改五重装」；别手贱重启，证据在内存里
Q
数据库服务器 CPU 飙到 100%，怎么排查？
  1. top 确认是 mysqld 在吃 CPU（而不是别的进程）
  2. show processlist; 看当前正在跑什么——大量耗时 SQL 一目了然
  3. 慢查询日志 + explain 定位烂 SQL（缺索引/全表扫描）
  4. 常见根因：缺索引的慢查询、大事务、深分页、缓存失效打穿 DB、锁等待自旋
  5. 应急：kill 掉肇事 SQL → 限流应用 → 补索引；根治看第 08 章慢查询方案
「processlist 抓现行，慢日志定惯犯」；缓存挂了会打穿，索引缺了会扫全表
Q
讲一次你处理线上故障的完整经历（STAR）？故障复盘怎么做？🔥 高频

答题框架（STAR）：背景（业务与规模）→ 告警现象 → 你的排查路径（每一步用什么工具排除什么）→ 止血动作 → 根因 → 长效改进。重点讲思路不是结局。

复盘原则（无责复盘 blameless）：

  • 聚焦流程与系统漏洞，不追责个人（人才会说真话）
  • 产出三问：为什么没拦住（事前）？为什么发现慢（监控）？为什么恢复慢（预案）？
  • 行动项落到人落到期，下次同类故障必须更早发现/自愈
「止血、定位、根因、改进」四段；复盘三连问：拦住没？发现快吗？恢复快吗？
Q
凌晨 3 点收到 P0 告警，你如何行动？
  1. 快速判断影响面：看大盘与告警内容，P0 确认则立即响应并拉起应急群
  2. 同步值班链：上报主管、拉相关同学（DBA/开发）
  3. 按 runbook 止血：预案优先——重启/切主/扩容/回滚，不慌乱试错
  4. 边处置边播报：每 15 分钟同步进展（现象、动作、结果）
  5. 恢复后：确认监控正常、留档现场、次日复盘
「确认、上报、按预案止血、持续播报」；半夜靠的是 runbook，不是临场发挥
Q
容灾和备份策略怎么设计？
  • 备份 3-2-1 原则：3 份数据、2 种介质、1 份异地
  • 层次：冷备（磁带/归档）→ 热备（主从实时）→ 同城双活（两机房同时服务）→ 异地多活（两地三中心，单元化路由）
  • RTO / RPO：RTO 恢复耗时、RPO 丢多少数据——先和业务定指标再选方案
  • 演练：每季度真实切换演练；没演练过的容灾是纸面容灾
「3-2-1 备三份，冷热双活往上加」；RTO 多久能活、RPO 丢多少数据，演练见真章

手写：带日期归档、自动清理过期备份的脚本？🔥 高频 
#!/bin/bash
set -euo pipefail
SRC="/data/app"
DEST="/backup"
KEEP_DAYS=7
DATE=$(date +%F)
BACKUP_FAIL=0

tar czf "$DEST/app_${DATE}.tar.gz" -C "$(dirname $SRC)" "$(basename $SRC)" \
  || BACKUP_FAIL=1

# 校验 + 清理过期备份
if [ "$BACKUP_FAIL" -eq 0 ]; then
  echo "$(date '+%F %T') 备份成功: app_${DATE}.tar.gz ($(du -h ${DEST}/app_${DATE}.tar.gz | awk '{print $1}'))" >> $DEST/backup.log
  find $DEST -name "app_*.tar.gz" -mtime +${KEEP_DAYS} -delete
else
  echo "$(date '+%F %T') 备份失败！" >> $DEST/backup.log
  exit 1
fi
# 远端同步（可选）：rsync -az $DEST/app_${DATE}.tar.gz backup@remote:/backup/

要点：变量集中顶部好维护；set -euo pipefail 兜错；备份结果写日志；find -mtime 清理；异地用 rsync。

手写：检测服务存活，挂了自动拉起并告警？🔥 高频 
#!/bin/bash
set -uo pipefail
SERVICE="nginx"
WEBHOOK="https://oapi.dingtalk.com/robot/send?access_token=xxx"
MAX_RETRY=3

check_and_restart() {
  systemctl is-active --quiet "$SERVICE" && return 0
  echo "$(date '+%F %T') $SERVICE 已停止，尝试重启..."
  for i in $(seq 1 $MAX_RETRY); do
    systemctl restart "$SERVICE"
    sleep 3
    systemctl is-active --quiet "$SERVICE" && {
      curl -s -X POST "$WEBHOOK" -H 'Content-Type: application/json' \
        -d "{\"msgtype\":\"text\",\"text\":{\"content\":\"$SERVICE 曾宕机，已自动拉起(第${i}次)\"}}"
      return 0
    }
  done
  curl -s -X POST "$WEBHOOK" -H 'Content-Type: application/json' \
    -d "{\"msgtype\":\"text\",\"text\":{\"content\":\"紧急：$SERVICE 重启${MAX_RETRY}次仍失败，需人工介入!\"}}"
  return 1
}

check_and_restart
# 更优雅：配 systemd Restart=on-failure 或 K8s livenessProbe，脚本只做兜底

要点：先判断再动手（幂等）；重试 + 告警两级；提醒面试官「生产上首选 systemd/K8s 自愈，脚本兜底」是加分项。
