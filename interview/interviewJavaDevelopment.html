01语言基础与数据类型

Q1JDK、JRE、JVM 有什么区别？Java 如何实现跨平台？🔥 高频

三者是包含关系：JDK ⊃ JRE ⊃ JVM。

  • JVM（Java 虚拟机）：执行字节码的「虚拟电脑」，负责类加载、字节码解释/JIT 编译、内存管理与 GC
  • JRE（运行环境）：JVM + 核心类库（java.lang、java.util 等），只能运行程序
  • JDK（开发工具包）：JRE + 开发工具（javac、javap、jdb、jstack 等），能编译 + 运行

跨平台原理：Java 源码编译成与平台无关的字节码（.class），各平台安装对应版本的 JVM 来执行——「一次编译，到处运行」。跨平台的是 Java 程序，而 JVM 本身不跨平台（各平台有各平台的 JVM 实现）。

「JDK 造车，JRE 开车，JVM 是发动机」；程序跨平台靠字节码，JVM 各平台各一份

Q3什么是自动装箱拆箱？Integer 缓存是什么？🔥 高频
  • 自动装箱：基本类型 → 包装类，编译期调用 Integer.valueOf()
  • 自动拆箱：包装类 → 基本类型，编译期调用 intValue() 等方法
  • Integer 缓存：IntegerCache 缓存 -128 ~ 127 的对象，此范围内 valueOf 返回同一对象，== 为 true；超出范围则 new 新对象，== 为 false
Integer a = 127, b = 127;
System.out.println(a == b);       // true  —— 走缓存，同一对象
Integer c = 128, d = 128;
System.out.println(c == d);       // false —— new 出了两个对象
System.out.println(c.equals(d));  // true  —— 包装类比较永远用 equals
高频陷阱：包装类比较一律用 equals；自动拆箱遇到 null 会抛 NullPointerException（如 Integer 为 null 参与运算）。
「装箱 valueOf，拆箱 xxxValue；缓存负 128 到 127，出了缓存 == 假」
Q4== 和 equals 的区别？🔥 高频
  • ==：基本类型比较值；引用类型比较地址（是否同一对象）
  • equals：Object 默认就是 ==；String、Integer 等已重写为比较内容
  • 自定义类想比内容，必须自己重写 equals（同时重写 hashCode）

经典题：String s1 = "abc" 与 String s2 = new String("abc")——s1 == s2 为 false（一个在常量池、一个在堆），s1.equals(s2) 为 true。

「== 比地址，equals 比内容（前提是重写）」；包装类和 String 比较永远用 equals
Q5String 为什么设计成不可变？有什么好处？🔥 高频

String 内部用 private final char[]（JDK9 后 byte[]） 存储，类本身 final 不可继承、没有提供修改数组的方法——所以一旦创建内容不可变。

  • 字符串常量池：不可变才能安全地共享缓存同一份字面量，节省内存
  • 线程安全：不可变对象天然线程安全，可自由跨线程共享
  • hashCode 缓存：String 的 hash 计算一次后缓存，适合做 HashMap 的 key（这也是 HashMap key 推荐 String 的原因）
  • 安全性：路径、类名、URL 参数不可被中途篡改
「常量池、线程安、hash 缓存、防篡改」四大好处，靠 final 类 + final 私有数组实现

Q7什么是字符串常量池？intern() 方法做什么？
  • 常量池：JVM 专门存放字符串字面量的区域（JDK7 后从方法区移到堆），相同字面量只存一份
  • String s = "abc"：先查池，有就直接引用；没有则入池再引用
  • new String("abc")：一定在堆里新建对象（最多产生 2 个对象：堆对象 + 池中字面量）
  • intern()：主动把字符串放入/查找常量池——池中有则返回池中引用，没有则入池（JDK7 起存的是堆对象引用）并返回
「字面量进池共享，new 一定新建堆对象」；intern 是手动入池的开关
Q8final、finally、finalize 分别是什么？
  • final（关键字）：修饰类不可继承、方法不可重写、变量不可重新赋值（引用类型指地址不可变，对象内容仍可变）
  • finally（异常块）：try/catch 后的代码块一定执行（除非 JVM 退出 System.exit / 线程被杀 / 断电），用于释放资源
  • finalize（方法）：对象被 GC 回收前由 GC 线程调用，JDK9 已废弃——执行时机不确定、性能差，替代方案是 try-with-resources 或 Cleaner
「final 不许改、finally 一定跑、finalize 已淘汰」
Q9static 关键字有哪些用法？
  • 静态变量：类级别一份，所有对象共享，存在方法区/堆的静态区，类加载时初始化
  • 静态方法：属于类，不能访问实例成员、不能用 this，可直接类名调用（main 方法就是静态方法）
  • 静态代码块：类加载时执行一次，用于初始化静态资源（优先于构造器）
  • 静态内部类：不依赖外部实例，不持有外部类引用（可避免内存泄漏，单例/Builder 常用）
  • 静态导入（import static）：直接使用静态成员，少写类名
「变量共享、方法无 this、代码块加载跑、内部类不抱引用」
Q10Java 是值传递还是引用传递？🔥 高频

Java 只有值传递。

  • 传基本类型：拷贝值本身，方法内修改不影响外部
  • 传引用类型：拷贝的是「地址的值」——方法内通过该地址修改对象内容会影响外部，但让参数指向新对象不影响外部
void change(StringBuilder sb) {
    sb.append("x");        // 影响外部：改的是同一对象
    sb = new StringBuilder("new");  // 不影响外部：只改了副本的指向
}
「Java 只有值传递」；改内容看得见，换指向看不见

02面向对象

Q11面向对象三大特性是什么？各自解决什么问题？🔥 高频
  • 封装：属性私有 + 公共方法访问，隐藏实现细节、控制读写权限（private + getter/setter）
  • 继承：子类复用父类代码、表达 is-a 关系；Java 单继承（多实现接口），子类拥有父类非私有成员
  • 多态：同一名方法在不同对象上有不同表现——编译看左边（静态类型），运行看右边（实际对象），是「可扩展性」的基石

多态三个前提：继承/实现 + 重写 + 父类引用指向子类对象（Animal a = new Dog()）。

「封装藏细节、继承复代码、多态换实现」；多态三前提：父引子、有重写、有继承

  • @Override 注解：让编译器帮检查是否真的重写成功
  • 被 static / final / private 修饰的方法不能被重写（private 对子类不可见）
「重载同类不同参、编译期定；重写父子同签名、运行期定」

「抽象类是半成品模板（单继承），接口是能力合同（多实现）」
Q14类的加载与初始化顺序是什么？🔥 高频

一个对象的完整初始化顺序：

  1. 父类静态变量 + 父类静态代码块（类加载，只执行一次，按书写顺序）
  2. 子类静态变量 + 子类静态代码块
  3. 父类实例变量 + 父类实例代码块
  4. 父类构造器
  5. 子类实例变量 + 子类实例代码块
  6. 子类构造器
  • 静态内容只随类加载执行一次；实例内容每 new 一次执行一次
  • 子类构造器默认第一行 super()——所以父类先初始化
「先静态后实例、先父类后子类、静态只一次」——口诀背熟，笔试常考
Q15多态的实现原理是什么？
  • 调用方法时，JVM 通过对象头中的类指针找到方法表（vtable），再根据实际类型定位到重写后的方法——即动态绑定（运行期才确定调用目标）
  • invokespecial 调构造器/private/super 方法（静态绑定）；invokevirtual 调普通实例方法（虚方法，支持多态）；invokestatic 调静态方法（静态绑定，所以 static 方法「多态无效」）
  • 字段没有多态：字段访问按编译期静态类型决定
「方法看运行类型（动态绑定），字段看声明类型（没有多态），static/final/private 不参与」
Q16内部类有哪几种？各有什么特点？
  • 成员内部类：依附外部实例，持有外部类引用，可访问外部全部成员；可能引发内存泄漏
  • 静态内部类：不依赖外部实例、不持有外部引用——推荐用它做 Holder/Builder/单例（如 HashMap.Node）
  • 局部内部类：定义在方法内，作用域仅限该方法
  • 匿名内部类：没有名字、声明即实例化，常用于回调/事件监听；访问局部变量必须是 final 或事实 final（变量拷贝一份，改了外部就不同步了）
「成员抱引用、静态不抱、局部方法内、匿名即用即走」；防泄漏优先静态内部类
Q17构造器有哪些规则？可以被重写吗？
  • 构造器与类同名、无返回值（连 void 都没有），随 new 一起调用
  • 可以重载（不同参数列表形成多个构造器），可用 this(...) 互调（必须放第一行）
  • 不能被继承，因此不能被重写；但子类构造器默认调用 super(...)（父类无默认构造器时子类必须显式调用）
  • 构造器不能是 abstract / static / final / synchronized
  • 陷阱：构造器里调用可被重写的方法是危险行为——子类重写后可能读到「还没初始化完」的字段
「同名无返回、可重载不可重写、子类先 super」
Q18深拷贝和浅拷贝的区别？怎么实现深拷贝？🔥 高频
  • 浅拷贝：复制对象本身，引用类型字段只复制地址——新旧对象共享内部子对象（改一个另一个也变）
  • 深拷贝：连同引用指向的对象一起递归复制，新旧对象完全独立

实现方式：

  1. 实现 Cloneable + 重写 clone()（默认浅拷贝，深拷贝需字段也递归 clone——代码繁琐）
  2. 序列化/反序列化（推荐）：对象图整体转字节再转回来，如 JSON 序列化（Jackson/Gson）或 Java 原生序列化
  3. 手动 new + 逐字段复制（小对象最简单直观）
「浅拷共享子对象，深拷整树全独立」；深拷贝首选序列化大法
Q19Object 类有哪些常用方法？
  • equals(Object) / hashCode()：内容判断与哈希值，成对重写
  • toString()：默认「类名@十六进制哈希」，日志打印必重写
  • getClass()：获取运行时类对象（final 方法）
  • clone()：protected 本地方法，需实现 Cloneable 才可调
  • wait() / notify() / notifyAll()：线程协作（final，必须在 synchronized 块内调用）
  • finalize()：已废弃，回收前回调
「equals+hashCode 成对、toString 打印、wait/notify 配锁用」
Q20super 和 this 关键字的用法？
  • this：当前对象引用——this.字段 区分同名局部变量、this(...) 调本类其他构造器、this 作为参数传递自己
  • super：父类「引用」——super.字段/方法 访问被隐藏/重写的父类成员、super(...) 调父类构造器
  • this() 和 super() 都必须在构造器第一行，且不能共存
  • 构造器里没写任何 this/super，编译器默认插入 super()（无参父类构造）
「this 看自己、super 找爸爸；两个调用抢第一行，只能留一个」

03常用 API 与工具类

Q21equals 和 hashCode 之间有什么契约？为什么重写 equals 必须重写 hashCode？🔥 高频

JDK 规定的两大契约：

  1. equals 相等 → hashCode 必须相等
  2. hashCode 相等，equals 不一定相等（哈希冲突是允许的）

为什么必须成对重写：HashMap/HashSet 先用 hashCode 定位桶，再用 equals 判等。若只重写 equals 不重写 hashCode——两个「内容相等」的对象 hash 不同，落在不同桶里，contains 永远返回 false，集合去重直接失效。

「equals 等，hash 必等；只重写一个，集合判等翻车」
Q22如何正确重写 equals()？有哪些坑？

标准五步：①自反 ②对称 ③传递 ④一致 ⑤与 null 比较为 false。

@Override
public boolean equals(Object o) {
    if (this == o) return true;                 // 1. 快速判断同一对象
    if (o == null || getClass() != o.getClass()) // 2. 判空 + 类型判断
        return false;
    Person p = (Person) o;
    return age == p.age && Objects.equals(name, p.name); // 3. 逐字段比较
}

@Override
public int hashCode() {

Q30ArrayList 的扩容机制是怎样的？
  • 无参构造：初始为空数组，首次 add 时扩到 10（默认容量）
  • 装满再 add：扩容 1.5 倍——newCapacity = oldCapacity + (oldCapacity >> 1)
  • 扩容 = 新建数组 + Arrays.copyOf 整体拷贝（O(n)，所以预估大小、初始化时指定容量可避免多次扩容）
  • 最大容量：Integer.MAX_VALUE - 8（数组头部保留）；超出抛 OutOfMemoryError
  • 注意：ArrayList 线程不安全，并发场景用 CopyOnWriteArrayList 或 Collections.synchronizedList
「首次给 10，往后 1.5 倍，拷贝旧数据」；能预估就传初始容量
Q31HashMap 的底层结构是怎样的？（JDK 1.8）🔥 高频

JDK1.8 的 HashMap = 数组 + 链表 + 红黑树。

  • 数组（Node[] table）：主体，默认容量 16，负载因子 0.75
  • 链表：hash 冲突的节点用链地址法挂在同一桶上（1.8 尾插）
  • 红黑树：链表长度 ≥ 8 且数组长度 ≥ 64 时树化（查询 O(log n)）；节点减到 6 时退回链表
  • 容量超过 容量 × 0.75 触发扩容（翻倍，2 的幂）

树化阈值 8 的由来：泊松分布下链长到 8 的概率约千万分之六——正常 hash 下几乎不可能，树化只是哈希攻击兜底。

「数组挂链表，链长 8 变树，树缩 6 退链，超 75% 扩容翻倍」
Q32描述 HashMap 的 put 完整流程？🔥 高频
  1. 计算 key 的 hash：h = key.hashCode() ^ (h >>> 16)（高 16 位参与异或，扰动函数减少冲突）
  2. index = (n-1) & hash 定位桶，桶为空——直接新建节点放入
  3. 桶不空则逐一比对：key 的 hash 相同且 (== 或 equals 相等) → 覆盖旧 value
  4. 如果是 TreeNode → 按红黑树方式插入
  5. 否则沿链表尾插；插完链长 ≥8 且数组 ≥64 → 树化
  6. 元素总数 > 容量 × 0.75 → resize 扩容（容量翻倍，节点按 hash 与旧容量与运算结果留在原地或搬到新位置）
  • key 为 null 特殊处理：固定放下标 0 的桶（只允许一个 null key）
「hash 扰动定位桶，空则放、同则盖、链则尾插、长则树化、满则扩容」
Q33HashMap 容量为什么必须是 2 的幂？
  • 定位桶时用 (n - 1) & hash 代替取模 hash % n——当 n 是 2 的幂时两者等价，位运算更快
  • n-1 的二进制是全 1（如 16-1=1111），与运算后 hash 的每一位都能参与，分布均匀、减少冲突；若 n-1 有 0 位，某些桶永远取不到
  • 扩容翻倍保持 2 的幂；构造时传 17 也会被 tableSizeFor 向上修正为 32
「2 的幂：与运算代替取模，快 + 桶全用得上」
Q34链表转红黑树为什么阈值是 8？退化为什么是 6？
  • 8 的由来：理想 hash 下链长服从泊松分布，长度到 8 的概率约 0.00000006——几乎只有 hash 算法劣化/哈希攻击才会出现，树化是兜底而非常态
  • 红黑树节点大小是链表节点的 2 倍，为罕见场景常态买单不值
  • 退化阈值 6 而非 8：留出缓冲带，避免节点数在 7/8 之间反复增删导致树 ↔ 链表反复转换的抖动开销
「8 是小概率兜底，6 是防抖缓冲」
Q35HashMap 在 JDK 1.7 和 1.8 有什么区别？🔥 高频
维度JDK 1.7JDK 1.8
结构数组 + 链表数组 + 链表 + 红黑树
插入方式头插法尾插法
扩容先判断再插入先插入再判断
扩容迁移重新计算 index，倒序搬移hash & oldCap 判断「原位 or 原位+旧容量」，顺序保持
  • 头插的核心问题：1.7 并发扩容时，两个线程头插搬移节点会形成环形链表，后续 get 死循环 CPU 100%——1.8 改尾插修复（但 HashMap 依旧线程不安全，并发请用 ConcurrentHashMap）
  • 1.8 节点由 Entry 改名 Node（树节点 TreeNode）

Q36ConcurrentHashMap 如何保证线程安全？（1.7 vs 1.8）🔥 高频
  • JDK 1.7：分段锁 Segment（继承 ReentrantLock），默认 16 段——不同段并发写互不阻塞，并发度 = 段数
  • JDK 1.8：抛弃分段锁，改为 CAS + synchronized 锁单个桶头节点：
    • 桶为空：CAS 无锁插入，失败自旋重试
    • 桶非空：synchronized 锁住头节点，只影响这一个桶，锁粒度更细
  • 其他保障：size() 用 baseCount + CounterCell 分散计数（类似 LongAdder）；不允许 null key/value（并发下无法区分「不存在」和「值为 null」，歧义）

为什么 key/value 不能为 null：HashMap 单线程 get 返回 null 能用 containsKey 区分；并发下 containsKey 和 get 是两次调用，中间可能被改——干脆禁止。

「1.7 分段 16 间房，1.8 CAS + 锁桶头」；并发 map 禁 null 是为消灭歧义
Q37HashSet 的实现原理？如何保证不重复？
  • HashSet 内部就是一个 HashMap，元素作 key，所有 value 指向同一个静态 PRESENT = new Object() 占位对象
  • 去重逻辑完全复用 HashMap：先比 hashCode 定位桶，再 == / equals 判等——重复则覆盖（表现为 add 返回 false）
  • 推论：自定义对象去重必须正确重写 hashCode + equals，否则「内容相同」的两个对象都会被存进去
  • LinkedHashSet = HashMap + 双向链表，维护插入顺序；TreeSet 底层 TreeMap，按比较器排序去重
「HashSet 是披着 Set 皮的 HashMap，value 全是 PRESENT」；去重效果取决于 hashCode + equals
Q38TreeMap 的排序原理？与 HashMap 怎么选？
  • 底层红黑树（自平衡二叉搜索树），增删查均 O(log n)
  • 排序依据：key 实现 Comparable（自然排序）或构造时传 Comparator（定制排序，优先级更高）
  • 额外能力：firstKey / lastKey / floorKey / ceilingKey / headMap / tailMap——范围查询、最值、有序遍历
  • 选择：要排序/范围查询 → TreeMap；只做 KV 存取 → HashMap（O(1) 更快）；要插入顺序 → LinkedHashMap
「TreeMap 红黑树，log n 还能范围查；无序求快 HashMap」
Q39LinkedHashMap 的原理？怎么用它实现 LRU？
  • 结构 = HashMap + 双向链表维护顺序：默认按插入顺序，构造参数 accessOrder=true 则按访问顺序（get 也会把节点移到链尾）
  • LRU 三步：①accessOrder = true ②重写 removeEldestEntry() 返回 size() > capacity ③访问/插入自动把热数据挪到尾部，超容量的头部（最久未用）被自动移除
class LRUCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;
    LRUCache(int capacity) {
        super(16, 0.75f, true);   // accessOrder = true
        this.capacity = capacity;
    }
    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity; // 超容即淘汰最老
    }
}
「LinkedHashMap 加链表，accessOrder 开启访问序，重写淘汰回调即 LRU」
Q40什么是 fail-fast？怎么安全地遍历时删除元素？🔥 高频
  • fail-fast：迭代器创建时记录 modCount，每次 next 检查 modCount != expectedModCount 就抛 ConcurrentModificationException——快速暴露「集合被结构性修改」的错误用法
  • 遍历时直接 list.remove(obj) 绕过了迭代器 → 计数不一致 → 报错（有时是「偶尔不报」，更隐蔽）

正确姿势：

  1. 迭代器自己的 remove：it.remove()（会同步 expectedModCount）
  2. JDK8+ 集合方法：list.removeIf(x -> ...)（内部就是迭代器删除）
  3. 倒序 for 循环按下标删（只针对 List，避免删除后索引位移漏删）
  4. 并发场景用 CopyOnWriteArrayList（写时复制，迭代的是快照，绝不报错）
「modCount 对不上就炸；删除要么用迭代器，要么 removeIf，要么 COW」
Q41集合选型的整体思路？（业务场景怎么选容器）
  • 要不要键值对：要 → Map；不要 → List / Set / Queue
  • Map 细分：默认 HashMap；要排序/范围 → TreeMap；要插入/访问序 → LinkedHashMap；并发 → ConcurrentHashMap
  • List 细分：默认 ArrayList；当队列/栈或头尾频繁增删 → LinkedList（或 ArrayDeque，性能更好）；并发读多写少 → CopyOnWriteArrayList
  • Set 细分：去重默认 HashSet；有序 TreeSet / LinkedHashSet；并发 → CopyOnWriteArraySet / ConcurrentHashMap.newKeySet()
  • 队列：单端 ArrayDeque（推荐替代 Stack）；阻塞队列 BlockingQueue（生产者消费者）；优先级 PriorityQueue（底层小顶堆）
「先问键值再问序，并发一律 Concurrent/COW，队列首选 ArrayDeque」

05异常处理

Q42Java 异常体系是怎样的？🔥 高频
  • 顶层：Throwable，两大分支：Error 与 Exception
  • Error：严重错误，程序救不了——OutOfMemoryError、StackOverflowError、NoClassDefFoundError
  • Exception：
    • 受检异常（Checked）：编译器强制处理——IOException、SQLException
    • 非受检（RuntimeException 及子类）：编译器不管——NullPointerException、IndexOutOfBoundsException、ClassCastException、ArithmeticException

常见运行时异常对应场景：NPE（调 null 的成员）、数组/字符串越界、类型强转不匹配、除以 0（整数运算）、NumberFormatException（Integer.parseInt("abc")）。

「Throwable 分两支：Error 救不了，Exception 分受检和运行时」
Q43受检异常和非受检异常的区别？各自适合什么场景？🔥 高频
  • 受检异常：编译期强制 try/catch 或 throws；表示可预期、可恢复的外部问题（文件不存在、网络中断）——调用方必须面对
  • 非受检异常：编译器不强制；表示程序 bug（空指针、越界）——应该修代码而不是 catch
  • 业务中常把受检包成非受检：throw new RuntimeException(e) 让框架统一兜底
别用异常做流程控制：异常构造要抓栈快照（fillInStackTrace），代价远高于 if 判断；也不要 catch (Exception e) 后什么都不干（吞异常最致命）。
「受检是外部意外必须接，非受检是代码 bug 要修根」
Q44try-with-resources 是什么？为什么推荐？
  • 资源类实现 AutoCloseable（或 Closeable），放 try 的括号里，无论正常结束还是抛异常，编译器自动按声明逆序 close
  • 对比传统 try-finally 手写 close：代码更短、不会漏关、不会出现「close 抛异常把业务异常吞掉」（被抑制的异常可通过 getSuppressed 拿到）
try (FileInputStream in = new FileInputStream("a.txt");
     FileOutputStream out = new FileOutputStream("b.txt")) {
    in.transferTo(out);   // 结束自动 close，先开后关
}
「实现 AutoCloseable，放进括号自动关，先开后关」
Q45finally 里写 return 会发生什么？finally 一定执行吗？🔥 高频
  • finally 里 return：会覆盖 try/catch 的返回值，并且若 finally 抛异常会吞掉原异常——严禁这样写（编译器给 warning）
  • finally 里修改基本类型返回值：无效——return 时返回值已拷贝进局部变量表
  • finally 修改引用对象的内容：生效（地址早拷贝了，改的是同一对象）
  • 不执行 finally 的三种情况：①System.exit() ②JVM 崩溃/断电 ③finally 所在线程被杀死；注意 try 里死循环也会导致永远到不了 finally
「finally 的 return 会顶掉一切，千万别写；exit/崩溃/杀线程才跳过 finally」
Q46如何自定义异常？有什么最佳实践？
public class BizException extends RuntimeException {
    private final int code;                       // 业务错误码
    public BizException(int code, String message) {
        super(message);                           // 消息传给父类

  • 业务异常一般继承 RuntimeException（不强制调用方处理），带 错误码 + 消息便于前端/日志定位
  • 最佳实践：①异常要有上下文信息（哪个订单、什么参数）②不要吞异常，至少记日志 ③不要用异常控制流程 ④统一由全局异常处理器（@ControllerAdvice）兜底转响应

Q47throw 和 throws 的区别？
  • throw：语句，方法体内真正抛出一个异常对象，后面代码不执行
  • throws：声明，写在方法签名上，告诉调用者可能抛哪些异常，本身不抛

06泛型与反射

Q48什么是泛型的类型擦除？带来了什么问题？🔥 高频
  • 泛型只存在于编译期：编译后 List<String> 与 List<Integer> 都是裸的 List，类型参数被擦成上界（默认 Object，声明 <T extends Number> 则擦成 Number）
  • 目的：兼容 JDK5 之前的老代码（迁移兼容性），「伪泛型」
  • 带来的限制：
    • 不能 new T()、不能 new T[]（运行期不知道 T 是谁）
    • 不能 instanceof List<String>；泛型类不能是异常类
    • 静态成员不能用类型参数
    • List<String>.class 不存在，只有一个 List.class
  • 需要运行期泛型信息的场景：通过继承捕获泛型（子类持有具体类型的 Class）或方法签名的 getGenericSuperclass()——主流框架（Jackson、MyBatis）都这么干
「泛型进编译器，出 class 全擦掉，运行期只剩上界」；要拿类型靠继承或签名
Q49? extends 和 ? super 有什么区别？什么是 PECS？🔥 高频
  • ? extends T（上界通配符）：泛型是 T 或 T 的子类——只读不写（读出来的一定是 T；但放任何东西进去都不安全）
  • ? super T（下界通配符）：泛型是 T 或 T 的父类——可写只能写 T（读出来只能当 Object）
  • PECS 原则：Producer Extends, Consumer Super——生产者（读数据）用 extends，消费者（写数据）用 super
  • 经典例子：Collections.copy(List<? super T> dest, List<? extends T> src)——从 src 读、往 dest 写
「extends 读只读，super 写只写；生产用 extends，消费用 super」
Q50什么是反射？有哪些应用场景？🔥 高频

Q51反射有什么缺点？如何优化？

Q57NIO 的三大核心组件是什么？🔥 高频

  • Channel（通道）：双向传输管道（可读可写），替代单向流；FileChannel / SocketChannel / ServerSocketChannel

Q58什么是零拷贝？Java 里怎么实现？🔥 高频

传统读文件发送网络要 4 次拷贝 + 4 次上下文切换：磁盘→内核缓冲（DMA）→用户空间（CPU）→socket 缓冲（CPU）→网卡（DMA）。

  • 零拷贝：数据全程不进用户空间（用户态不参与 CPU 拷贝），减少拷贝次数与上下文切换
  • 实现 1：FileChannel.transferTo() —— 底层 Linux sendfile 系统调用，内核缓冲直送 socket
  • 实现 2：mmap 内存映射（MappedByteBuffer）——文件映射进用户地址空间，省一次拷贝，适合修改
  • 应用：Kafka 高吞吐（sendfile 顺序读发给消费者）、RocketMQ（mmap）、Tomcat 大文件传输、Nginx
「sendfile 直送网卡，mmap 映射省一跳；Kafka 快就快在这」
Q59IO 操作有哪些最佳实践？
  • 流必须关闭：try-with-resources 自动关闭（多个资源按声明逆序关，先开后关）
  • 一定加缓冲：BufferedInputStream / BufferedReader 包装节点流，减少系统调用（拷贝文件可差几十倍）
  • 大文件用 transferTo（零拷贝）；不要一次性 read 全部进内存（OOM），分块或流式处理
  • 读写文本显式指定字符集（UTF-8），避免依赖平台默认值
  • 序列化敏感字段加 transient；Java 原生序列化有安全漏洞，跨语言场景优先 JSON/Protobuf
「关流用 try-res、提速靠缓冲、大件走零拷、字符定编码」

Q60创建线程有几种方式？为什么说本质只有一种？🔥 高频
  1. 继承 Thread，重写 run()
  2. 实现 Runnable（无返回值，推荐——不占用继承位）
  3. 实现 Callable<V> + FutureTask（有返回值、可抛异常）

Q63线程的中断机制是怎样的？stop() 为什么被废弃？
  • Java 没有强制杀线程的安全手段，中断是「协商式」的：thread.interrupt() 只是设置中断标志位，线程自己决定怎么响应
  • 响应方式：①循环里 Thread.currentThread().isInterrupted() 检查并退出 ②阻塞中的 sleep/wait/join 收到中断会抛 InterruptedException 并清除标志位
  • catch 了 InterruptedException 要么重新 interrupt()，要么向上抛——别吞掉中断信号，否则上层感知不到取消请求
  • stop() 废弃原因：直接杀死线程并立刻释放所有锁，可能让共享数据停在中间状态（转账扣了 A 没加 B），对象损坏不可控；suspend/resume 同理死锁风险而废弃
「中断是商量不是枪毙；标志位 + 异常两条路，别吞信号」
Q64join() 和 yield() 的作用？
  • join()：等待目标线程执行结束——t.join() 让当前线程阻塞直到 t 跑完；经典用法：主线程等所有子任务完成再汇总（join 可带超时）
  • yield()：当前线程暗示让出 CPU 时间片，回到就绪态继续参与竞争——只是建议，调度器可无视；几乎不用于生产（测试复现竞态时有用）
  • 更现代的等待方式：CountDownLatch / Future.get() / CompletableFuture.allOf()，比裸 join 更灵活
「join 等他死，yield 让个座（可能白让）」；生产用 JUC 不用 yield
Q65什么是守护线程？有什么用？
  • 守护线程（Daemon）：为用户线程服务的后台线程——当所有用户线程结束，JVM 直接退出，不等守护线程（守护线程被强行终止）
  • 典型：GC 线程、JIT 编译线程、心跳/日志刷盘线程
  • 设置：t.setDaemon(true)，必须在 start() 之前（否则 IllegalThreadStateException）
  • 注意：守护线程里不要写关键业务/IO——JVM 退出时不会给它收尾机会，可能写一半断掉
「守护线程陪跑，用户线程走光它陪葬」；start 前设置，别放关键逻辑
Q66什么是线程安全？产生线程不安全的根源是什么？🔥 高频

线程安全：多线程访问共享资源时，结果始终正确、行为可预期（不管调度顺序如何）。

三大根源（并发三性）：

  • 原子性：i++ 是「读-改-写」三步，可被中途打断——解法 synchronized / Lock / CAS 原子类
  • 可见性：CPU 缓存导致 A 改了共享变量 B 看不见——解法 volatile / synchronized / final
  • 有序性：编译器与 CPU 指令重排打乱代码顺序——解法 volatile（含内存屏障）/ happens-before 规则

经典案例：双重检查锁单例不加 volatile 时 new 对象的「分配→初始化→赋值」可能重排，别的线程拿到半初始化对象。

「原子被打断、可见隔缓存、有序乱重排」——并发三性，对应三把锁

09并发编程核心

Q67synchronized 的原理是什么？有哪些用法？🔥 高频
  • 底层基于对象头的 Monitor（监视器锁）：字节码层面是 monitorenter / monitorexit 指令（同步方法靠 ACC_SYNCHRONIZED 标志）
  • 三种用法：①修饰实例方法（锁当前对象 this）②修饰静态方法（锁 Class 对象，全类唯一）③修饰代码块（锁指定对象，粒度最细）
  • 特性：可重入（同线程可重复获取自己的锁）、非公平、保证原子+可见+有序（互斥区天然 happens-before）
  • JDK6 后优化：偏向锁、轻量级锁、自旋锁、锁消除、锁粗化——性能已与 ReentrantLock 相当
陷阱：锁实例方法时，不同对象各自有锁互不影响；「Integer 缓存对象」「String 常量」做锁对象时，可能与其他代码意外共享同一把锁。锁对象应为 private final。
「实例锁 this、静态锁 Class、代码块锁指定」；monitor 进出、可重入
Q68描述 synchronized 的锁升级过程？🔥 高频

JDK6 引入，锁信息记录在对象头 Mark Word 中，随竞争激烈程度逐步升级（只升不降）：

  1. 无锁 → 偏向锁：第一个线程访问，Mark Word 记下线程 ID——之后该线程进出无需任何同步操作（只有一个线程反复拿锁的场景）
  2. 偏向锁 → 轻量级锁：第二个线程来竞争，偏向撤销，升级为轻量级锁——线程栈里建 Lock Record，CAS 自旋抢锁（交替执行、临界区极短）
  3. 轻量级锁 → 重量级锁：自旋超限或第三者竞争，膨胀为重量级锁——依赖操作系统 mutex 互斥量，拿不到锁的线程阻塞挂起（用户态 ↔ 内核态切换，开销大）
  • 设计思想：能不加锁就不加、能自旋就不阻塞——按竞争强度花不同代价
  • JDK15 起偏向锁已被废弃移除（维护成本高、收益在现代应用中有限）
「无锁→偏向→轻量自旋→重量阻塞」只升不降，代价层层加码
Q69volatile 的作用是什么？能保证原子性吗？🔥 高频

volatile 两大作用（保证两个，不保证一个）：

  • 可见性：写 volatile 变量立刻刷回主内存并使其他 CPU 的缓存行失效（MESI 协议），别的线程读到的一定是最新值
  • 有序性：编译器/处理器禁止指令重排（插入内存屏障）——典型应用：DCL 单例的实例字段
  • 不保证原子性：i++ 依旧丢数据（读改写三步仍可被打断），计数请用 AtomicInteger / synchronized
public class Singleton {
    private static volatile Singleton instance;  // 防止 new 半初始化对象外泄

    public static Singleton getInstance() {
        if (instance == null) {                   // 1. 第一次检查（免锁提速）
            synchronized (Singleton.class) {
                if (instance == null) {           // 2. 第二次检查（真正防重）
                    instance = new Singleton();   // 分配→初始化→赋值 可能重排
                }
            }
        }
        return instance;
    }
}
「volatile 保可见、禁重排，不管原子」；DCL 双检 + volatile 是标配
Q70什么是 Java 内存模型（JMM）？happens-before 是什么？
  • JMM：Java 定义的内存可见性规则——所有共享变量存主内存，每线程有自己的工作内存（CPU 缓存抽象），操作变量必须先拷到工作内存，改完再刷回——可见性问题的模型根源
  • happens-before：JMM 给程序员的承诺——若 A 操作 happens-before B，则 A 的结果对 B 可见。它是判断数据有无竞争的依据，无需懂底层屏障
  • 核心规则（背这几条）：①程序顺序（单线程内按代码顺序）②监视器锁（解锁 hb 于后续加锁）③volatile（写 hb 于后续读）④线程 start（start 前的操作 hb 于线程内操作）⑤线程 join（线程内操作 hb 于 join 返回后）⑥传递性
「JMM 隔主存与工作内存；happens-before 六条规则锁可见性」
Q71什么是 CAS？有什么问题？🔥 高频
  • CAS（比较并交换）：CPU 原子指令——「内存值 V、期望值 E、新值 N，当且仅当 V==E 时把 V 改成 N，否则失败重试」。JDK 里由 Unsafe.compareAndSwapInt 等本地方法包装
  • 优点：无锁、无阻塞，竞争小性能好——AtomicInteger 自增、AQS 抢锁、ConcurrentHashMap 插空桶全靠它

三大问题：

  1. ABA 问题：值从 A→B→A，CAS 以为没变过——解法：带版本号的 AtomicStampedReference
  2. 自旋开销：竞争激烈时失败重试空耗 CPU——可用 LongAdder 分段计数替代
  3. 只能保证一个变量的原子性——多个变量只能包成对象用 AtomicReference 或加锁
「CAS 比了才换，无锁但自旋」；ABA 靠版本号、竞争大换 LongAdder
Q72AQS 是什么？它是如何工作的？🔥 高频
  • AQS（AbstractQueuedSynchronizer）：JUC 的锁与同步器框架——ReentrantLock、Semaphore、CountDownLatch、ThreadPoolExecutor 的 Worker 全基于它
  • 核心两件套：
    • state（volatile int）：同步状态——0 无锁 / >0 有锁或剩余资源，CAS 修改
    • CLH 双向队列：抢不到锁的线程封装成 Node 挂到队列排队挂起（LockSupport.park），释放时唤醒后继
  • 模板方法模式：AQS 管排队挂起唤醒，子类只需实现 tryAcquire / tryRelease（独占）或 tryAcquireShared / tryReleaseShared（共享）定义「怎么算抢到」
  • 独占模式：ReentrantLock；共享模式：Semaphore（state = 许可数）、CountDownLatch（state = 计数，减到 0 放行）
「一个 state 记状态，一条 CLH 队列排线程，CAS 抢 LockSupport 睡」

Q74线程池的七大核心参数是什么？🔥 高频
  1. corePoolSize 核心线程数：常驻最小线程数（默认不回收，除非 allowCoreThreadTimeOut）
  2. maximumPoolSize 最大线程数：核心 + 临时线程的上限
  3. keepAliveTime 空闲存活时间：临时线程空闲多久被回收
  4. unit：时间单位
  5. workQueue 任务队列：阻塞队列——ArrayBlockingQueue（有界）/ LinkedBlockingQueue（默认无界 Integer.MAX_VALUE）/ SynchronousQueue（不排队直接交接）
  6. threadFactory 线程工厂：自定义线程名、守护属性（排障必备）
  7. handler 拒绝策略：队列满且线程满时的处置

为什么不推荐 Executors 工具方法：newFixedThreadPool / newSingleThreadExecutor 用无界队列（任务堆积 OOM）；newCachedThreadPool 最大线程 Integer.MAX_VALUE（线程爆炸 OOM）——阿里规约要求手动 new ThreadPoolExecutor，明确每个参数。

「核最保时单 + 队厂拒」七参数；Executors 两坑：无界队列、无线程上限
Q75描述线程池的执行流程？四种拒绝策略是什么？🔥 高频

提交任务后的判断顺序（先扩线程、再排队、再扩线程）：

  1. 当前线程数 < corePoolSize → 新建核心线程执行
  2. 核心满 → 任务进 workQueue 排队
  3. 队列也满 且 线程数 < maximumPoolSize → 新建临时线程执行
  4. 队列满 且 线程到 max → 触发拒绝策略

四种拒绝策略：

  • AbortPolicy（默认）：抛 RejectedExecutionException
  • CallerRunsPolicy：让提交任务的线程自己执行——天然限流减速（推荐）
  • DiscardPolicy：静默丢弃新任务（不抛异常，最危险）
  • DiscardOldestPolicy：丢掉队列最老任务，再重试提交
「核心 → 排队 → 临时 → 拒绝」四步；拒绝默认抛异常，限流选 CallerRuns
Q76线程数应该怎么设置？🔥 高频
  • CPU 密集型（计算、压缩、加密）：线程数 = CPU 核数 + 1（+1 防缺页等短暂停顿浪费 CPU）
  • IO 密集型（RPC、DB、HTTP）：线程数 = 核数 × (1 + 平均等待时间/计算时间)——等待越长越多线程填补空档；粗略取 2 × 核数 起步
  • 终极答案：压测调优——没有万能公式，观察吞吐与响应时间拐点
  • 获取核数：Runtime.getRuntime().availableProcessors()
  • 混合型任务应拆分成两个线程池隔离，避免相互拖累（也是舱壁模式）
「CPU 密集 N+1，IO 密集看等待，最终压测说了算」
Q77ThreadLocal 的原理是什么？🔥 高频
  • 每个 Thread 内部有一个 ThreadLocalMap（就是普通 map 结构），key 是 ThreadLocal 对象（弱引用），value 是存的值——数据存在线程自己身上，天然隔离
  • threadLocal.set(v)：以 this（ThreadLocal）为 key 存进当前线程的 map；get/remove 同理
  • 用途：数据库连接/Session 绑定线程、SimpleDateFormat 线程封闭、链路 traceId 透传、Spring 事务的 Connection 绑定、用户上下文 UserContext
  • 父子传递用 InheritableThreadLocal；线程池场景（线程复用会串值）用阿里 TransmittableThreadLocal
「ThreadLocal 是钥匙，数据锁在线程自己的 map 里」；线程封闭，人各一份
Q78ThreadLocal 为什么可能内存泄漏？怎么避免？
  • 引用链：Thread → ThreadLocalMap → Entry（key 是弱引用，value 是强引用）
  • 泄漏机制：ThreadLocal 外部无强引用时，GC 回收 key（变 null），但 value 依旧被 Entry 强引用着——若线程一直活着（线程池！），这些「key=null 的 value」无法回收 → 泄漏
  • 设计弱引用的意义：这是尽力补救而非预防——set/get 时会顺手清理 key 为 null 的 Entry，但不保证及时
  • 规范解法：用完必调 remove()（finally 里），尤其是线程池场景；ThreadLocal 尽量 static final（全局一份 key，避免无谓弱引用失效）
「key 弱 value 强，线程不死 value 活；finally 里必 remove」

Q81死锁的产生条件是什么？如何避免和排查？🔥 高频

四个必要条件（缺一不死锁）：

  1. 互斥：资源一次只能一人用
  2. 持有并等待：拿着 A 等 B
  3. 不可剥夺：不能强行抢走
  4. 循环等待：A 等 B、B 等 A 成环

避免（破坏后三条）：

  • 按固定顺序加锁（破坏循环等待，最常用）——按账户 ID 排序再转账
  • 一次性申请全部资源（破坏持有并等待）
  • 用 tryLock(timeout) 拿不到就放弃已持有的锁（破坏不可剥夺）

排查：jstack <pid> 会直接输出 "Found one Java-level deadlock"；或 jconsole / Arthas 的 thread -b。

「互持不循环」四条件；破循环靠顺序加锁，排查用 jstack
Q82原子类有哪些？LongAdder 为什么比 AtomicLong 快？
  • 基本类型原子类：AtomicInteger / AtomicLong / AtomicBoolean（CAS 实现）
  • 引用类型：AtomicReference（整体替换对象）、AtomicStampedReference（带版本号防 ABA）、AtomicMarkableReference
  • 字段更新器：AtomicIntegerFieldUpdater（volatile 字段的反射式 CAS）
  • 累加器：LongAdder / DoubleAdder、LongAccumulator

LongAdder 原理：高竞争下 AtomicLong 所有线程同一个 value 上 CAS 自旋，失败率飙升；LongAdder 把值拆成 base + Cell[] 数组——不同线程散列到不同 Cell 各自累加（空间换时间），sum() 时再汇总——写多读少的计数场景（如接口 QPS 统计）首选；要精确即时值或 CAS 语义仍用 AtomicLong。

「Atomic 单点自旋，LongAdder 分片累加」；统计计数用 Adder，精确值用 Atomic

Q84堆和栈的区别？

  • 关联：栈里的局部变量表存对象引用，引用指向堆中实体——「栈管运行、堆管存储」
  • 递归太深 → 栈溢出 StackOverflowError；对象太多/泄漏 → 堆 OOM

Q85new 一个对象的全过程是怎样的？对象在内存中如何布局？🔥 高频

  1. 类加载检查：未加载则先触发加载（父类先于子类）
  2. 分配内存：指针碰撞（内存规整）或空闲列表（内存零散）——TLAB 线程私有缓冲避免并发竞争

  5. init 初始化：执行实例代码块与构造器，真正的赋值

Q88什么是双亲委派模型？为什么这么设计？🔥 高频

  • 流程：收到加载请求层层向上委托，父加载器加载不了才向下回退自己加载——「子先问爹，爹办不了再回来」

  • 打破双亲委派的场景：SPI 机制（JDBC 驱动，线程上下文类加载器）、Tomcat 隔离各 webapp（每应用独立 WebappClassLoader）、OSGi / 热部署

Q89如何判断对象可以被回收？GC Roots 有哪些？🔥 高频
  • 引用计数法（Java 不用）：循环引用永远非零，无法回收

  • 方法区中静态变量、常量引用的对象
  • 本地方法栈 JNI 引用的对象
  • JVM 内部引用（基本类型 Class 对象、常驻异常对象、系统类加载器）等

注意：方法区/元空间的类也可以被卸载（该类所有实例已回收 + 类加载器已回收 + Class 对象无引用，三者齐才卸载）。

// 写法一：wait / notifyAll（考察基础）
class Buffer {
    private final Queue<Integer> queue = new LinkedList<>();
    private final int cap = 5;

    public synchronized void put(int v) throws InterruptedException {
        while (queue.size() == cap) {       // 必须 while，防虚假唤醒
            wait();                          // 释放锁等待消费
        }
        queue.offer(v);
        notifyAll();                         // 唤醒消费者
    }

    public synchronized int take() throws InterruptedException {
        while (queue.isEmpty()) {
            wait();
        }
        int v = queue.poll();
        notifyAll();
        return v;
    }
}

class LRUCache<K, V> extends LinkedHashMap<K, V> {

    LRUCache(int capacity) {
        super(16, 0.75f, true);          // accessOrder=true 按访问排序
        this.capacity = capacity;
    }

    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {

    }

// 写法二：HashMap + 双向链表（面试加分，LeetCode 146）
class LRUCache2 {
    class Node {                          // 双向链表节点
        int k, v; Node prev, next;
        Node(int k, int v) { this.k = k; this.v = v; }
    }
    private final int cap;
    private final Map<Integer, Node> map = new HashMap<>();
    private final Node head = new Node(0, 0), tail = new Node(0, 0); // 哨兵

    LRUCache2(int cap) {
        this.cap = cap;
        head.next = tail; tail.prev = head;
    }
    public int get(int key) {
        Node n = map.get(key);
        if (n == null) return -1;
        remove(n); addFirst(n);           // 访问即提前
        return n.v;
    }
    public void put(int key, int value) {
        Node n = map.get(key);
        if (n != null) { n.v = value; remove(n); addFirst(n); return; }
        if (map.size() == cap) {          // 淘汰链尾
            Node last = tail.prev;
            remove(last); map.remove(last.k);
        }
        n = new Node(key, value);
        map.put(key, n); addFirst(n);
    }
    private void remove(Node n) { n.prev.next = n.next; n.next.prev = n.prev; }
    private void addFirst(Node n) { n.next = head.next; n.prev = head; head.next.prev = n; head.next = n; }
}
  • 考点：数据结构选型（HashMap 定位 O(1) + 双向链表维护顺序 O(1)）、哨兵节点简化边界、访问即移到头部
「HashMap 查得快，双向链表管顺序，访问弹到头，满了砍尾巴」
Q116手写一个简单的阻塞队列
class MyBlockingQueue<T> {
    private final Object[] items;
    private int count, putIdx, takeIdx;

    MyBlockingQueue(int capacity) { items = new Object[capacity]; }

    public synchronized void put(T t) throws InterruptedException {
        while (count == items.length) {   // 满则等
            wait();
        }
        items[putIdx] = t;
        if (++putIdx == items.length) putIdx = 0;
        count++;
        notifyAll();                      // 叫醒消费者
    }

    @SuppressWarnings("unchecked")
    public synchronized T take() throws InterruptedException {
        while (count == 0) {              // 空则等
            wait();
        }
        T t = (T) items[takeIdx];
        if (++takeIdx == items.length) takeIdx = 0;
        count--;
        notifyAll();                      // 叫醒生产者
        return t;
    }
}
  • 考点：环形数组（下标取模回绕）、while 判满/空、wait/notifyAll 配对、泛型 + 数组只能 Object[]（类型擦除）
「数组转圈、满了等空了等、放完取完 notifyAll」
Q117手写 equals 和 hashCode（IDEA 自动生成也要会默写）
public class Employee {
    private String name;
    private int age;
    private double salary;
    private Department dept;              // 引用类型字段

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;                       // 1 同一对象
        if (o == null || getClass() != o.getClass())      // 2 空与类型
            return false;
        Employee e = (Employee) o;
        return age == e.age                                // 3 基本类型 ==
            && Double.compare(salary, e.salary) == 0       //   浮点防精度
            && Objects.equals(name, e.name)              //   引用 null 安全
            && Objects.equals(dept, e.dept);
    }

    @Override
    public int hashCode() {
        int result = Objects.hash(name, age);             // 与 equals 同字段
        result = 31 * result + Objects.hashCode(dept);
        return result;
    }
}
  • 考点：五步结构、Double.compare 处理浮点（== 对 NaN 失效）、31 倍增系数（奇数、移位优化、冲突分布好）、equals 与 hashCode 字段必须一致
「一同二判三转型，引用用 Objects，浮点用 compare，hash 同字段乘 31」

CompletableFuture<User> userF =
